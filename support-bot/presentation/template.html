Why mine our own code

Our user guide says how the app is meant to work. It doesn't say why a scan came back empty, or why a password is rejected when it looks right.

That lives in the code. So every answer names the exact file it came from — which also means we can tell when it goes out of date.

How it answers

Four possible outcomes. It picks one — it never mixes them.

It knows

Shows the verified answer, word for word. Instant. Can't be wrong — it isn't writing anything.

It's unsure between two

Reads both and picks the right one. About a second.

It's an admin thing

"That's an admin screen — ask your administrator." Doesn't show something else instead.

It doesn't know

Says so, points to a person, and records the question so we can add it.

Most questions land in the first box — which is why it costs nothing and answers instantly.

What we used

Three choices — and what we turned down each time.

Our own code as the source of every answer

Every answer was written by reading what the app actually does — the real button names, the real error messages, the real time limits.

Not a general AI like ChatGPT. It has never seen RackTrack, so it would invent plausible-sounding answers about our product. That's the one thing we can't allow.

Two kinds of search, together keyword and meaning

Keyword search finds exact things — an error message, a button label. Meaning-based search knows "signed out" and "session expired" are the same question. Both run every time.

Not one or the other. Keyword alone sent "why do I keep getting signed out" to an answer about passwords, because both contain "keeps getting". Meaning alone blurs exact error messages together.

A small AI model on our own server only to choose, never to write

When two answers look equally likely, the model reads both and picks. That's all it does.

Not a paid AI service. Cost per message, and every question would leave our servers. And not a model that writes freely — a model that can write can invent.

The tech

Five pieces. Each one chosen over a more obvious alternative.

Keyword search BM25

Finds answers containing the words the technician typed.

Why thisThe same ranking method inside Elasticsearch, Lucene and Postgres search. Decades of production use. We wrote it in 200 lines with no external library.
Not thisElasticsearch. A whole search server to operate, for 351 documents. Searching all of them directly takes 2 milliseconds — the infrastructure would cost more than it buys.
Meaning search nomic-embed-text · 274 MB

Finds answers that mean the same thing, even with no words in common.

Why thisPurpose-built for search rather than for chat. Small, open, free, and runs on our own server.
Not thisA vector database like Pinecone or Weaviate. Those exist for millions of records. Ours fits in about a megabyte of memory and compares in under a millisecond.
Combining the two Reciprocal Rank Fusion

Merges both result lists into one ranking.

Why thisIt combines by position in each list, so an answer both methods rank highly wins.
Not thisAveraging the two scores. They are different units — one might be 12.4, the other 0.64. Averaging them means inventing a conversion rate that means nothing.
The AI model Llama 3.2 · 3B · 2 GB

Picks between candidate answers when two look equally likely.

Why thisWe tested the larger 8-billion model too. It words things slightly better but takes more than twice as long — and for someone waiting at a rack, the wait costs more than the polish. The bigger model is installed and one setting away.
Not thisChatGPT or a paid AI service. A cost per message that grows with use, and every question leaving our servers. For a job this narrow, it would be wasted.
Where answers are stored one file · 1.2 MB

All __TOTAL__ answers, loaded once when the server starts.

Why thisIt sits in version control alongside the code, so any change to an answer is reviewed exactly like a code change.
Not thisA database. It would make the answers harder to review, not easier — the opposite of what we want.

Is it safe

Three things stop it going wrong.

1. It never guesses

A wrong answer sends a technician down the wrong path for an hour and costs us their trust for good.

So every answer is either taken word-for-word from documentation we verified — or it admits it doesn't know.

2. People only see what they should

Technicians, administrators and internal staff each see a different set of answers.

__INTERNAL__ internal answers are removed before the assistant is even built — not hidden behind a rule telling it to stay quiet. Something never loaded can't be leaked, however the question is phrased.

A person's level comes from their login, never from what they type. Claiming to be an admin in the chat doesn't make you one.

What it won't do

It can't answer questions about pricing, our roadmap, or competitors — that isn't in our code, so it sends those to a person.

And covering every screen isn't the same as answering every question. The honest measure is the log of what it couldn't answer — which only means something once technicians are using it.
