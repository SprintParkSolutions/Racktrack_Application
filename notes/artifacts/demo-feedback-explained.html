What the demo feedback is actually asking for

Nine points came back from the demo. Read individually they look like nine feature requests. Checked against the codebase, they aren't — and the difference changes what you should do next.

The short version

Only two of the nine items are genuinely new engineering, and one of those is half-built already. Three are about how the product was presented, not what it does. Switch login — the very first item — is fully implemented today across five API endpoints; the reviewer simply never saw it.

When a reviewer asks you to “confirm” a feature exists, and separately asks you to “ensure existing capabilities are clearly demonstrated,” they are telling you the same thing twice: RackTrack does more than the demo conveyed. The most valuable fix on this list costs no engineering at all.

Group one

Things that already work

Two items ask for capabilities RackTrack has shipped. Both are visibility problems wearing the costume of feature requests.

F1

Confirm and fully expose switch login

“Confirm and fully expose switch login functionality for all supported devices directly from RackTrack.”

Built, hidden

What they're asking

Let me log into a switch from inside RackTrack, and show me it works for every device you claim to support — not just the one you demoed.

Where RackTrack stands

This is built. The server exposes a full authenticated SSH console today, with an encrypted credential vault behind it:

✓ GET  /api/switch/creds-status
✓ GET  /api/switch/console/intents
✓ POST /api/switch/console/run
✓ POST /api/switch/console/run-auto
✓ POST /api/switch/console/run-auto-stream
✓ server/lib/ssh-creds.js · encrypt-creds.js · connection_profiles.js

Read between the lines

The word “confirm” is the signal. The reviewer wasn't sure the feature existed. A capability nobody can find is, from the buyer's seat, a capability you don't have.

What it takes

No new backend. Put an entry point in the rack view and show per-device state — credentials stored, device reachable, session live — so support is legible at a glance rather than asserted in a slide. This is the cheapest high-impact item on the list.

F7

Review how cable endpoints and paths are presented

“Review how cable endpoints and path information are presented to ensure existing capabilities are clearly demonstrated.”

No code

What they're asking

Make it obvious where a cable starts and ends, and what it passes through. Note that they wrote “existing capabilities” — they are not asking you to build cable tracking. They're asking you to show the cable tracking you have.

Read between the lines

This is F1's twin. Two of nine items independently report the same failure: a real capability that didn't land. When that happens twice, the problem is in the demo, not the backlog.

What it takes

Audit the cable and endpoint views for legibility — is the A-side/B-side relationship readable? Is the port identified? Is the path traceable? Then rehearse it explicitly, alongside F9.

Group two

Things to build

Three items need engineering. Two of them lean heavily on infrastructure you already own, which makes them far cheaper than they first appear.

F2

Quick verification actions, e.g. a Traceroute button

“Add quick verification/troubleshooting actions (for example, a ‘Traceroute’ button) accessible from the rack view.”

Not built

Where RackTrack stands

Nothing exists. Searching the entire codebase for traceroute or tracert returns zero matches.

✗ traceroute — 0 matches across server, client, pipeline

Read between the lines

Traceroute is the example, not the requirement. The real ask is in-context verification: prove this device is reachable, right here, without leaving the rack view and opening a terminal.

What it takes

Less than it looks. You already have an authenticated command channel to the device — the same run-auto plumbing behind F1 — plus a defined console/intents concept. Ping and traceroute can ride that path as new intents rather than as new infrastructure.

Build F1's surface first; F2 then costs a fraction of what it would standalone.

F6

Cross-rack topology visualization

“Consider implementing cross-rack topology visualization, showing logical connections between devices in different racks.”

Half built

Where RackTrack stands

The hard part — the data — is already collected. The easy part — the scope of one endpoint — is what's blocking you.

✗ GET /api/topology/:rackId  ← scoped to a single rack
✓ LLDP neighbor data  server/lib/port_poller.js · client/src/utils/portsProbe.js
✓ rack-group concept  server/app.js · client/src/components/useRackGroup.js

Read between the lines

LLDP neighbor tables are precisely the adjacency data you need to draw a link from a device in rack A to a device in rack B. You are already polling them. The topology endpoint just never asks across a rack boundary.

What it takes

Generalize /api/topology/:rackId to a group scope, then join LLDP neighbors across the racks in that group. The rack-group concept already exists to hang it on. This is the highest-value item on the list that is mostly already paid for — and the most credible answer to the AI-scale story in F3.

Not built

Group three

Things to say differently

Four items ask you to change nothing about the software. Given that three of them describe the same demo, they may be the highest-leverage work on this page.

F3

Lead the pitch with data center pain points

“Revise the product pitch to start with broader data center pain points … before discussing individual features.”

No code

What they're asking

Open on the problem, not the machinery. They even named the problems for you: asset tracking, cabling, procurement, auditing, and AI-scale operations.

Read between the lines

The demo almost certainly opened on rack scanning — the most technically impressive thing RackTrack does. That's the classic feature-first trap: the audience sees a clever capability before they have a reason to care about it.

What it takes

Rewrite the opening minutes so each named pain point maps to the feature that answers it:

  • Asset tracking → rack scanning, device detection
  • Cabling → cable classifier, port detection (see F7)
  • Procurement → SFP advisor, marketplace
  • Auditing → CMDB reconciliation, port history & drift
  • AI-scale operations → cross-rack topology (see F6)

The Executive Overview page in the RackTrack space already drafts parts of this argument.

F4

Reorganize the UI by user goal

“Reorganize the UI into clear categories with intuitive naming and a guided workflow based on the user's goal or pain point.”

No code

What they're asking

Navigation organized by what a person is trying to accomplish, not by how the system is built. Users don't arrive wanting “device detection”; they arrive wanting to know what's in the rack.

A head start you already have

The seventeen feature docs were just grouped into five goal-based clusters for the docs space. That grouping is a ready-made hypothesis for the product's own navigation:

  • Scanning & Capture — getting racks into RackTrack
  • Racks & Ports — what's racked, what's free
  • Network & Discovery — seeing the live network
  • Intelligence & Advice — where RackTrack recommends
  • Admin & Data — accounts, orgs, CMDB

Treat it as a starting point to test with users, not a conclusion.

F9

Refine the demo's story order

“Refine the presentation flow and story order for demos to better showcase the application's value.”

No code

Read between the lines

Taken with F3 and F7, three of nine items are about the demo rather than the product. That is the single loudest signal in this feedback, and it is worth saying plainly: the software under-sold itself.

A story order that follows the evidence

  • Pain — open on the five problems from F3
  • Existing strength — scan a rack, detect devices, show the cabling clearly (F7)
  • Live proof — log into a switch on stage, run a check (F1, then F2)
  • Forward story — cross-rack topology as the AI-scale answer (F6)

Note that this order costs one UI surface and one small feature. Everything else is already built.

F8

Validate firmware / EOL and procurement across more vendors

“Continue validating firmware/EOL and procurement features across additional vendors.”

10 vendors

Where RackTrack stands

Ten vendors are covered in pipeline/all_vendor.py today:

✓ aruba · cisco · dell · fortinet · hpe · huawei · juniper · mikrotik · netgear · ubiquiti
✗ arista · extreme · palo alto · brocade · nokia

Read between the lines

The word is “continue” — this works, and they want more of it. This is not a defect, and it should not compete for attention with F1 or F6.

What it takes

Prioritize by the fleet mix of the customers you're chasing. Arista is the most conspicuous absence given the AI-scale data center story F3 asks you to lead with — that's where those switches live.

How to read this. Item numbers F1–F9 are reference handles in the order the feedback arrived, so the team can cite them. They are not a priority order.

Suggested sequence. F1 (surface what exists) → F2 (rides F1's plumbing) → F3 + F9 (rewrite the story) → F4 (goal-based navigation) → F5 (onboarding onto F4) → F6 (cross-rack, the flagship) → F8 (ongoing).
