RackTrack · Requirements Request · One Network Rack, Two Switches

Tracing a cable end to end — what we can discover, and what we must be told

Your network admin is right to ask for a complete requirement. Here it is — along with the reason the request has to come in two halves, because half of what you need cannot be discovered from a switch at all.

The problem

Patch panels are invisible to the logical layer

You asked about the logical layer. The logical layer is exactly where this breaks — so it's worth being precise about the boundary before asking anyone for anything.

Logical layer — what LLDP, CDP, MAC and ARP return

Switch‑01Gi0/1
Switch‑02Gi0/24

▸ one edge, two endpoints. Complete, correct, and useless for finding the cable.

Physical layer — what the cable actually does

Switch‑01Gi0/1
PP‑Aport 12
PP‑Bport 12
Switch‑02Gi0/24

▸ the two dashed nodes have no MAC, no IP, no power, and no voice. Nothing on the network can see them.

A patch panel is passive copper. It cannot announce itself over LLDP, respond to SNMP, appear in a MAC table, or answer an ARP. Both diagrams above describe the same cable. The logical layer is not wrong — it is complete for what it measures. It simply does not measure cable paths.

This is why no amount of switch access will let you trace through a patch panel, and why “give me read access to the switches” is only half a requirement. The other half is physical records that live in a spreadsheet, on a label, or in someone's head.

Current setup

What RackTrack has today

Both halves already exist in the codebase. Nothing joins them.

Discovered

Logical discovery works. An authenticated SSH console with per-vendor command intents, an LLDP/CDP parser spanning Cisco, Aruba, Juniper, D-Link and TP-Link, interface and MAC polling, plus Netdisco over SNMP.

Topology edges are built from LLDP/CDP only. A port's state is link_active = has_neighbor || mac_count > 0 — meaning a port can be known-active while its far end stays unknown.

Seen, not linked

Physical detection works too. The vision pipeline already classifies Patch Panel as a device type, detects individual ports on a device face, and runs OCR over labels.

So RackTrack can see that a panel is in the rack, and where. It has no idea which front port maps to which rear port, or where either one goes.

Missing

The join. There is no cable record, no passive-node concept, no bulk import for a patch schedule, and no path-resolution service.

The topology endpoint is also scoped to a single rack — GET /api/topology/:rackId — which happens not to matter yet, since you only have one rack.

Scope

What one rack and two switches actually gets you

Be honest with the admin about scope — it makes the ask credible and much easier to say yes to. With login on two switches, the discoverable graph is small and its edges are of three kinds:

  • Switch ↔ switch. If LLDP or CDP is enabled on both, you get this edge precisely, with interface names on each end.
  • Switch ↔ anything that speaks LLDP. Many servers, APs and IP phones do. These appear as proper neighbors with a chassis ID and port ID. Anything that doesn't speak LLDP will not appear as a neighbor, no matter what it is.
  • Switch ↔ a MAC address. Everything else. You learn that something is on port Gi0/7, and from ARP you may learn its IP. You do not learn what it is, and you never learn the cable path. This is the majority of ports in most racks.

Patch panels appear in none of those three categories. That is the whole problem, and it does not get better with more switches.

The changes

What has to change to trace through a patch panel — and why

Five changes. Only one of them is a conversation with the admin, but it's the one everything else depends on.

1  Model passive nodes

Add a node type that is asserted rather than discovered, and a segment record: one physical cable run between two ports.

Why: today every node in the graph got there by announcing itself. A patch panel never will. The data model has to admit facts that no protocol can confirm.

2  Import the patch schedule

A CSV import mapping device:port → panel:port and panel:rear → panel:rear. multer currently accepts image uploads only.

Why: this is the sole source of truth for passive segments. Everything downstream is a rendering of this file. This is the artifact to ask the admin for.

3  Bind vision to the record

Tie the detected Patch Panel — its rack unit, its detected ports, its OCR'd labels — to the imported panel record.

Why: so physical truth is refreshed by re-scanning the rack rather than by re-typing a spreadsheet. This is what makes the whole thing survive contact with reality.

4  Resolve paths

Walk from an active port across segments until the next active port is reached. Return the ordered hops, passive nodes included.

Why: this is the actual feature — “trace this cable” — and it is a graph walk, not a discovery problem. It's cheap once (1) and (2) exist.

5  Reconcile against LLDP

The logical edge says Sw1:Gi0/1 ↔ Sw2:Gi0/24. The resolved physical path must have those same two endpoints. If it doesn't, the documentation is wrong.

Why: patch schedules rot the moment someone moves a cable at 2am. LLDP is the only thing that can catch it. This turns a static document into a monitored one.

6  Agree a labeling standard

Panels and ports labelled consistently — ANSI/TIA-606 is the usual choice.

Why: OCR can only read labels that exist and follow a pattern. Without this, step (3) degrades into manual data entry forever. This is a process change, not code — and it's the real question for your admin.

The request

What to ask for, in two buckets

Splitting the ask this way is the single most useful thing you can do. It shows you understand what he can and cannot give you, and it stops the conversation stalling on the impossible half.

Bucket 1

Things the switches can tell us

  1. A read-only account on both switches, reachable over SSH from the RackTrack host. Privilege level 1 / read-only role. No configuration access is needed or wanted.
  2. The management IP of each switch, and an ACL permitting the RackTrack host. Without the ACL entry, the account is useless.
  3. Confirmation that LLDP is enabled globally and per-interface — and CDP too, if Cisco. This is the one setting that decides whether we see any topology at all. If LLDP is off, every port becomes an anonymous MAC address.
  4. SNMP read-only access — v3 credentials preferred, v2c community acceptable. Netdisco needs this. It's an independent cross-check on what the CLI reports.
  5. Confirmation we may run these read-only commands (Cisco IOS shown; equivalents on other platforms):
show lldp neighbors detail      # the logical edges — the important one
show cdp neighbors detail      # Cisco-to-Cisco fallback
show interfaces status         # which ports are up, speed, VLAN
show interfaces description    # whatever humans wrote about each port
show mac address-table         # the silent devices — MAC per port
show ip arp                    # MAC to IP, so silent devices get names
show vlan brief                # segmentation
show etherchannel summary      # LAG members read as one logical link
show interfaces transceiver    # optics: fibre vs copper, DOM levels
show inventory                 # model and serial, for the asset record

Every one of these is read-only and non-disruptive. Saying so explicitly is usually what gets the yes.

Bucket 2

Things only a human can tell us

Nothing in this bucket can be obtained from a switch. If he cannot supply it, cable tracing through the panels is not possible — and that is a finding worth knowing early rather than late.

  1. The patch schedule — for every switch port in use, which patch panel and port it lands on, and where that panel's rear port goes. Any format: spreadsheet, Visio, a photo of a whiteboard. This is the single most valuable artifact in the entire request. It is the physical layer.
  2. The panel naming and port numbering scheme. Is port 1 top-left or bottom-left? Do panels have unique names? Determines whether OCR of the panel face can be parsed automatically or must be hand-checked.
  3. Whether panel rear ports connect straight through to another panel, or via couplers, cassettes, or MPO breakouts. Each of these is another invisible hop. A single MPO breakout turns one physical run into twelve.
  4. A rack elevation — what occupies each U, top to bottom. We can generate this from a scan, but his version is the check on ours.
  5. Whether cables carry unique IDs, and whether labelling follows a standard. Decides whether this stays accurate on its own, or rots the first time someone repatches.
  6. Which switch ports are trunks or uplinks, and which run to structured cabling rather than direct to a device. A direct-attach cable has no panel in the path at all. Knowing which ports those are saves us tracing paths that don't exist.

How to ask

A message you can send as-is

Lead with what you're doing and why, state plainly what you already understand, then make the ask specific and bounded.

Hi <name>,

We're building an accurate map of the network rack in RackTrack — both the logical topology and the physical cable paths — so we can trace any cable from one end to the other, including what it passes through.

I want to be upfront about one thing so we don't talk past each other: I know the switches can't tell us about the patch panels. Panels are passive, so they'll never show up in LLDP, SNMP, or a MAC table. That means the request comes in two parts — one you can answer from the switches, one only you or your records can.

From the switches (read-only, non-disruptive):

  • A read-only SSH account on both switches, plus their management IPs
  • An ACL entry permitting our host to reach them
  • Confirmation that LLDP is enabled globally and on the interfaces — and CDP if they're Cisco
  • SNMP read-only access (v3 preferred, v2c fine)
  • Sign-off to run: show lldp neighbors detail, show cdp neighbors detail, show interfaces status, show interfaces description, show mac address-table, show ip arp, show vlan brief, show etherchannel summary, show interfaces transceiver, show inventory

From you or your documentation:

  • The patch schedule — which switch port lands on which panel port, and where each rear port goes. Any format at all, including a photo of a whiteboard.
  • The panel naming and port numbering convention
  • Whether panel rears go straight through, or via couplers, cassettes, or MPO breakouts
  • A rack elevation, if one exists
  • Whether cables carry unique IDs, and whether labelling follows a standard such as TIA-606
  • Which ports are trunks or uplinks, and which are direct-attach rather than through structured cabling

Scope is small: one network rack, and only the two switches we can log into. If the patch schedule doesn't exist in any usable form, tell me — that changes the approach, and I'd rather know now than build on a guess.

Happy to walk the rack with you if it's faster than writing it down.

Thanks,
<you>

The plan

Tracing everything, in order

Each phase produces something usable on its own, so a stall in one doesn't strand the others.

PHASE 0

Establish logical truth

With read-only access, pull LLDP, CDP, interface status, MAC and ARP from both switches. Build the logical graph. No RackTrack changes needed — this works today. Output: every active port, its neighbor if it has one, its MAC if it doesn't.

PHASE 1

Capture physical truth

Scan the rack. The vision pipeline already yields the elevation, the Patch Panel detections with their rack units, the ports on each face, and OCR of whatever is printed on them. In parallel, get the patch schedule from the admin. Output: what is physically in the rack, and the claimed cable map.

PHASE 2

Join the layers

Build changes 1, 2 and 3 — passive nodes, patch-schedule import, and the binding from detected panel to panel record. Output: a graph where a passive node sits between two active ports.

PHASE 3

Resolve and verify

Implement the path walk (change 4), then reconcile against LLDP (change 5). Every logical edge should have a physical path with matching endpoints. The mismatches are the deliverable — they are precisely the cables whose documentation is wrong. Spot-check a few with a toner or by watching link state.

PHASE 4

Keep it true

Agree the labeling standard (change 6), and re-scan on a cadence. Reconciliation runs on every poll, so drift surfaces the day it happens rather than the next time someone goes looking.

The one thing to take away. If the patch schedule does not exist, no feature will conjure it. The choice at that point is to create it once by hand — walking the rack, panel by panel — or to accept that tracing stops at the panel face. Establish which it is before writing any code.
