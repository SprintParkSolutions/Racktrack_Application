RackTrack ↔ Switch Access — Diagnostic

Switch access — diagnostic report

Why RackTrack can't reach the datacenter switch, with evidence and the exact fix required.

PREPARED FOR  Network / VPN admin SWITCH  TP-Link JetStream TL-SG2428P SWITCH IP  192.168.1.33 RACKTRACK HOST (VPN)  10.81.234.130
⛔
TCP to the switch subnet is being blocked — only ICMP (ping) gets through.
Every host on 192.168.1.0/24 answers ping, but every TCP port times out — including the switch's SSH (22), HTTPS (443) and HTTP (80), and even the gateway's web ports. RackTrack needs TCP 22 to the switch to read live port/LLDP data; it cannot open the connection. This is a firewall/VPN policy issue, not the switch, the credentials, or the application.

Diagnosis

When ICMP succeeds but TCP fails uniformly across an entire subnet, the cause is a stateful firewall or VPN access policy that permits ping while dropping TCP session setup (the SYN never gets a response). It is not a single-device fault: the switch, the old switch IPs, and the gateway all behave identically. Credentials and SSH being enabled on the switch are irrelevant while the TCP handshake can't complete.

Notably, SSH to these switches worked previously from this same host — RackTrack successfully ran show interface status, show lldp neighbor-information, etc. So this is a change in the network/VPN path, not a new limitation of the switch.

What we need (the fix)

Allow TCP from the VPN client range to the switch subnet.

  1. On the firewall/VPN between the client pool and the office LAN, permit TCP (at minimum tcp/22; ideally also tcp/443 for the web UI) from the VPN client range 10.81.234.0/24 to 192.168.1.0/24 — or specifically to the switch 192.168.1.33.
  2. If access is instead restricted on the switch (a management/access ACL limiting SSH to certain source IPs/subnets), add the VPN client range there.
  3. Alternatively, connect RackTrack on a VPN profile that grants full TCP access to the switch management network (the current profile allows ICMP only).

Quick self-check for the admin: from the VPN client, opening https://192.168.1.33 in a browser will also fail (same TCP block). Once it loads, RackTrack's SSH will succeed too.
