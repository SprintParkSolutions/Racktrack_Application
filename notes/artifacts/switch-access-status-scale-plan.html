Why it is failing

The switch runs out of SSH sessions and never lets go.

TP-Link JetStream switches allow only about one concurrent SSH session. Critically, they do not free a session when the connection drops — they hold it until an idle timeout (~10 minutes) expires.

The old app made this worse on every failure: a 60-second poller plus per-command reconnects and retries kept opening new sessions faster than the switch could release the old ones. So the single session slot stayed permanently occupied by ghosts — and every real probe got turned away at the shell step.

That's why it "keeps happening every time": the failures were feeding themselves.

What needs to happen to recover — right now

  1. Leave the switch completely alone
    Already done — poller off, probes are single-shot. Nothing is adding sessions anymore.
  2. Let the idle timer drain the ghosts
    Give it ~5–10 minutes. With no new sessions arriving, the stale ones finally time out and the slot frees.
  3. (Fastest path, if ever possible) reboot the switch
    A power-cycle clears every session instantly. Not available here — noted for completeness.
  4. Probe once, then use normally
    After it drains, a single probe succeeds. Avoid rapid repeated retries — that's what re-saturated it before.

The permanent solution

Stop connecting per-command. Reuse one long-lived session, and add a circuit breaker.

1 · One persistent session per switch. Instead of open→run→close for every command, keep a single SSH connection alive per switch and funnel all commands through it (behind the existing host lock). One session, reused — the cap is never a problem.

2 · Circuit breaker on saturation. When a switch refuses the shell, back off hard (e.g. 10 minutes) and stop probing it entirely, so failures can never snowball into permanent lock-out again.

3 · Move polling off SSH. The real fix is not to screen-scrape a CLI at all. Poll port status over SNMP (read-only, no session limit, built for exactly this) and keep SSH only for occasional interactive commands.

◆
With full datacenter admin, you don't scale SSH — you replace it.
One rack of SSH probing already hits a session wall. Hundreds of switches over SSH would be permanently broken. At scale the right tools (SNMP, a vendor controller, telemetry) make this class of failure disappear by design.

If you owned the whole datacenter — the setup

▤
Out-of-band (OOB) management network
A dedicated management LAN/VLAN reaching every switch, PDU, and server's mgmt port — so monitoring never depends on a production VPN or the data path it's measuring.
▤
Single source-of-truth inventory
Every device catalogued: IP, vendor/model, role, rack/position, and which credential set it uses. This is what a collector iterates over.
▤
A secrets vault, not saved passwords
Device credentials live in a vault (HashiCorp Vault / AWS Secrets Manager / cloud KMS), issued per-device, rotated, and never returned to a UI. Aligns with the write-only encrypted credential model already in the app.
▤
A collector + time-series store + dashboard
A polling/telemetry service writes to a time-series database; the dashboard reads from that store — you never hammer devices from the UI directly.

How it should be done — pick the right protocol

The whole recurring problem is a symptom of one wrong choice: using an interactive CLI (SSH) as a machine API. At scale, use interfaces built for continuous polling.

ApproachSession limit?Good forVerdict at scale
SSH screen-scraping
(what we do today)		 ~1 session One-off interactive commands Breaks — the wall you're hitting now, multiplied by every switch.
SNMP v3 None Port up/down, counters, health — read-only polling Ideal — designed for continuous polling; TP-Link supports it.
gNMI / NETCONF / RESTCONF Streaming Modern switches — push telemetry & config Best where hardware supports it; devices stream to you.
Vendor controller API
(Omada / DNA / Central)		 One API Fleets of one vendor's gear Excellent — the controller aggregates every switch; you call it once.

TP-Link's own answer is the Omada Controller: it manages all JetStream switches centrally, and you pull the whole fleet's status from a single API instead of SSHing 200 switches one at a time.

Will it fail again?

If you keep SSH → yes, worse.

Every switch has the same ~1-session cap. Many pollers × many switches = guaranteed saturation across the fleet. Scaling the current approach scales the failure.

If you move to SNMP / a controller → no.

These interfaces are built to be polled continuously by monitoring systems. There is no per-connection session slot to exhaust, so this entire failure mode simply doesn't exist.

What we do — a staged plan

  1. Now — harden the SSH we have
    One persistent pooled session per switch + a circuit breaker that backs off on saturation. Buys reliability today without new infrastructure. (This is the Tab 1 permanent fix.)
  2. Next — move polling to SNMP v3
    The biggest single win. Port status/health via read-only SNMP removes the session limit from the hot path entirely; keep SSH only for rare interactive actions.
  3. Then — put it behind a controller
    Deploy the vendor controller (Omada for TP-Link) and pull fleet status from one API. Add an OOB management network so monitoring is independent of production.
  4. Foundation — vault + time-series + dashboard
    Credentials in a vault (per-device, rotated), telemetry into a time-series DB, dashboards read from the store. The UI never talks to a device directly again.
➔
Bottom line
Today's fix stops the bleeding on one rack. To run a whole datacenter, the SSH CLI stops being the data source — SNMP and a controller become the machine interfaces, and this failure never comes back.
