What "moving to the cloud" actually means here

Right now RackTrack lives on one rented computer in a data centre — the Hostinger box behind demo.racktrack.ai. Everything is on that one machine: the app, the customer accounts, every rack photo, every scan result. You update it by copying files to it from this Mac by hand.

"Moving to the cloud" means renting that computer from Amazon or Microsoft instead — but that alone changes nothing. The real prize is what those companies let you do afterwards: take automatic backups, rebuild the whole thing from scratch in an hour if it burns down, and eventually run several copies of the app at once so it does not fall over when twenty technicians scan at the same time.

The honest answer to "is it possible?"

Yes — and I already proved the first part works. I took your actual app, packed it into a sealed box the way a cloud platform requires, and ran it with nothing at all coming from your Mac. It started in ten seconds and worked perfectly. I then deleted the whole thing and rebuilt it — and every account and scan was still there.

But only as one copy. When I ran two copies side by side the way a cloud platform normally would, half of every user's requests failed — while both copies cheerfully reported that they were healthy. That is not a bug I introduced; it is what your app does today, and fixing it is a real engineering project.

The one thing that shapes every decision

This is worth understanding properly, because it is the reason the plan looks the way it does — and the reason a plausible-sounding shortcut would quietly destroy your data.

The obvious shortcut, and why it fails

The tempting idea is: "Put the app on one of those modern cloud container services, and put the database file on a shared network drive so every copy can reach it." Both Amazon and Microsoft sell exactly such a network drive — Amazon calls it EFS, Microsoft calls it Azure Files. On paper it solves everything.

It does not work, and it fails in the worst possible way — silently.

Why, in plain terms

Your database (SQLite) is fast partly because of a trick. When several programs use the same database file at once, they coordinate by leaving tiny notes for each other in the computer's memory — not in the file. Think of a shared kitchen with a small whiteboard on the wall: before anyone touches the fridge, they check the whiteboard.

That whiteboard only exists inside one physical computer. A network drive has no whiteboard. Two machines using the same database file across a network cannot see each other's notes, so they both think they are alone, both write at once, and the file ends up corrupted. There is no error message. It simply becomes wrong.

All three of your databases use this mode. I confirmed it — every one opens with journal_mode = WAL, which is the setting that turns the whiteboard on.

The practical rule

Never put a SQLite database on EFS, Azure Files, or any network drive. If someone proposes running RackTrack on Fargate or Container Apps with a file share, that proposal corrupts your customer data. It will appear to work for weeks first.

One honest caveat about my testing

In my two-copy test, the shared storage was a local disk, where the whiteboard does work — so that test passed. It passed for a reason that would not hold on a real cloud network drive. I am telling you this because it is the one claim in this whole plan that is reasoned rather than measured, and it is also the most consequential. Before trusting any shared-storage design, prove it on the real thing.

Do this first — before choosing a cloud

Four jobs. None of them depends on whether you pick Amazon or Microsoft. Two to four days of work in total, and the first one is urgent.

Job 1

Stop shipping your customer database inside the app

Urgent

What is wrong

When your app is packed into its sealed box, one instruction copies the whole server/ folder in. That folder contains server/data — which is your live database. So every box built on this Mac contains 42 MB of real data: 33 user accounts with their scrambled passwords, four older database backups going back to July, 12 MB of activity logs, and the secret key used to sign login tokens. I verified that key is byte-for-byte identical to your real one.

Why it has not bitten you yet

The server is updated by copying files, and that copy step already excludes server/data. So the box built on the server is clean, and a folder mounted at runtime hides the copy anyway. The exclusion was written for the file-copy step and never mirrored into the sealed-box settings.

Why moving to the cloud makes it dangerous

Cloud deployment works differently: you build the box on this Mac and upload it to a shared registry. Anyone who can download that box gets your users' password hashes and a key that lets them forge valid logins for any account.

The fix — about an hour

Add these lines to .dockerignore:

server/data
!server/data/mock
!server/data/support-kb.json
!server/data/oui-vendors.json

The three exceptions matter. Those files are meant to be included — the mock connector data, the support assistant's knowledge base, and the network-card manufacturer lookup table. A blanket exclusion would break all three features.

Check it worked

docker build -t racktrack:test .
docker run --rm racktrack:test ls /app/server/data
# You should see exactly three entries and no .db files.

Then change the signing key. It has been inside every box built here, so treat it as exposed. Changing it logs everyone out once — that is the correct price, and it is far cheaper than the alternative.

Job 2

Turn on continuous backups — today, on the server you already have

Highest value

This is the single best return on effort in the entire document, and it does not require moving anything. Litestream is a small program that sits beside your database, notices every change, and copies it to cloud storage within seconds.

  • No code changes. Your app does not know it exists.
  • Recovery to any moment, not just to last night.
  • A few dollars a month for storage.
  • Works on Hostinger right now, and carries over unchanged to AWS or Azure later.

The whole configuration

# /etc/litestream.yml
dbs:
  - path: /opt/racktrack-demo/server/data/auth.db
    replicas: [{ type: s3, bucket: racktrack-db-backup, path: auth.db }]
  - path: /opt/racktrack-demo/server/data/racktrack.db
    replicas: [{ type: s3, bucket: racktrack-db-backup, path: racktrack.db }]
  - path: /opt/racktrack-demo/server/data/logs.db
    replicas: [{ type: s3, bucket: racktrack-db-backup, path: logs.db }]

Restoring is one command

litestream restore -o auth.db s3://racktrack-db-backup/auth.db

Practise the restore before you need it. A backup nobody has ever restored is not a backup — it is a hope. Restore into a scratch folder, open the file, count the users. Half an hour, once.

Job 3

Split the sealed box in two

Recommended

Your box is 6.45 GB. Almost all of that is the photo-analysis machinery — the AI libraries and the 403 MB of trained models. The part that serves web pages needs none of it.

  • Web box — roughly 400–600 MB. Starts fast, can be copied many times cheaply.
  • Analysis box — stays large, but you only need a few and only while scans are running.

Why it matters: today, adding capacity for a rush means downloading 6.45 GB before the new copy can serve a single page. After the split it is well under a gigabyte. This also sets up the queue design in Step 2, so if you skip it now, do it first thing then.

Job 4

Write down your settings, and pick a region

Your app reads 180 settings from its environment. Most are development noise; about 30 genuinely matter in production. Before anything moves, list them with three columns: name, where the value comes from, is it secret. These are the ones that cause silent, confusing failures if wrong:

SettingWhat goes wrong if it is not right
JWT_SECRETIf unset, each copy of the app invents its own key and rejects logins issued by the others. Users get randomly signed out.
NODE_ENVMust be exactly production. Your settings reader does not strip comments, so writing production # live silently leaves development mode on — which shows internal error details to the public.
CORS_ALLOWED_ORIGINSNote the exact name. If it does not match your website address precisely, every action in the browser fails while the server looks perfectly fine.

Your team works in Indian time and your technicians upload large photos from the field, so distance genuinely affects how long an upload takes. Choose AWS Mumbai (ap-south-1) or Azure Central India. Both have everything this plan needs. Do not default to a US region because a tutorial did.

AWS · STEP 1

Make it safe: one rented computer, done properly

One machine running the same setup you have now — but with automatic nightly disk photographs, continuous database copying, no way to log in with a stolen password, and the whole thing written down so it can be rebuilt from scratch.

  1. Open the account and lock the front door

    Create the AWS account. Then immediately stop using the account you signed up with — that "root" account can do anything, including delete everything and run up unlimited bills. Create a normal user for yourself, turn on two-factor authentication, and set a billing alert at a number that would worry you. 

    export AWS_REGION=ap-south-1
export ACCT=$(aws sts get-caller-identity --query Account --output text)
echo $ACCT

    Worked if

    That prints a 12-digit number. If it errors, the command-line tool is not connected to your account yet.

  2. Create a private shelf for your sealed boxes, and upload one

    A registry is a private shelf where your built app boxes live so servers can fetch them. Build for arm64 — a processor family Amazon calls Graviton that is roughly 20% cheaper. I already proved your app builds and runs on it. 

    aws ecr create-repository --repository-name racktrack \
  --image-scanning-configuration scanOnPush=true

aws ecr get-login-password | docker login --username AWS \
  --password-stdin $ACCT.dkr.ecr.$AWS_REGION.amazonaws.com

docker buildx build --platform linux/arm64 \
  -t $ACCT.dkr.ecr.$AWS_REGION.amazonaws.com/racktrack:$(git rev-parse --short HEAD) \
  -t $ACCT.dkr.ecr.$AWS_REGION.amazonaws.com/racktrack:latest --push .

    Common mistake

    Tagging only as latest. Then you cannot tell which version is running, and you cannot go back to the one that worked. Always tag with the commit reference too, as above.

  3. Put your passwords somewhere proper

    Secrets Manager is a locked drawer. The server is given permission to open the drawer — it never holds a copy of the key. At startup it reads the values into memory only, so nothing sensitive is ever written to the disk or into the sealed box. 

    aws secretsmanager create-secret --name racktrack/prod \
  --secret-string '{"JWT_SECRET":"...","SMTP_PASS":"...","STRIPE_SECRET_KEY":"..."}'

  4. Launch the machine

    Pick m7g.large — 2 processors, 8 GB memory. That is what I tested and it ran comfortably with room to spare.

    Do not pick a "t" type

    The cheaper t4g family gives you full speed only in short bursts, then throttles. Photo analysis is a long, steady load, so it would run out of credit mid-scan. The symptom is scans that are fast on Monday and mysteriously slow on Friday — miserable to diagnose.

    Three settings that matter more than the machine choice:

    • Two disks, not one. A 30 GB system disk, and a separate 100 GB disk mounted at /opt/racktrack/data holding the database, scan photos and cache. Keeping data on its own disk is what makes the machine itself disposable — you can destroy and rebuild it without touching your data.
    • No SSH, no password, no key. Turn off port 22 entirely and use Session Manager instead. Access is then controlled by your AWS login and every session is recorded. This removes the single most common way small companies get breached.
    • Firewall: ports 80 and 443 only. Nothing else open to the internet.

  5. Turn on nightly disk photographs

    This is the backup fix. Data Lifecycle Manager takes a snapshot of the data disk every night automatically and keeps 14 of them. Restoring means creating a new disk from a snapshot — a few minutes. 

    resource "aws_dlm_lifecycle_policy" "racktrack_data" {
  description        = "Nightly snapshot of RackTrack data disk"
  execution_role_arn = aws_iam_role.dlm.arn
  policy_details {
    resource_types = ["VOLUME"]
    target_tags    = { Backup = "racktrack-data" }
    schedule {
      name        = "nightly"
      create_rule { interval = 24  interval_unit = "HOURS"  times = ["20:30"] }
      retain_rule { count = 14 }
      copy_tags   = true
    }
  }
}

    The timezone trap

    AWS schedules in UTC only. 20:30 UTC is 2:00 in the morning India time, which is what you want. Writing 02:00 would run the backup at 7:30am, during your working day.

  6. Add Litestream for second-by-second database copies

    Snapshots give you last night. Litestream gives you this second. Between them you can recover from a disk failure with essentially no data loss, and from an accidental deletion by rewinding to just before it. Configuration is in the "Do this first" tab — if you already did it on Hostinger, it moves across unchanged.

  7. Copy the scan photos to S3 hourly

    outputs/ is 132 MB today and grows with every scan. Until Step 2 moves it properly, an hourly copy into a versioned S3 bucket gives you a second copy for a few dollars. 

    aws s3 sync /opt/racktrack/data/outputs s3://racktrack-outputs/ --delete-excluded

  8. Keep your existing HTTPS setup and point the domain over

    Reserve a fixed IP address, point demo.racktrack.ai at it, and keep the Caddy container you already use for certificates. It works, it renews automatically, and changing it now adds risk for no benefit. A load balancer would cost about $20 a month and balance a grand total of one machine — add it in Step 2 when there is something to balance.

  9. Deploy from GitHub instead of from your Mac

    Add a job to the automated checks you already run: build the box, upload it, then tell the server to fetch and restart. Use GitHub's OIDC trust so no AWS password is ever stored in GitHub.

    This retires the manual copy step and, with it, the whole category of problem where the server and the code repository quietly disagree about what is running.

  10. Get told when it breaks

    Two alerts are enough to start, and they cover almost everything that actually happens:

    • The machine itself has stopped responding.
    • /healthz has not returned a healthy answer for three minutes.

    Send both to email and Slack. Install the CloudWatch agent so logs and memory usage are collected off the machine — otherwise they are lost exactly when you need them.

  11. Write all of it down as Terraform

    Everything above expressed as files in a repository, applied automatically. The test of whether this step is genuinely finished is not that the site is up. It is that you can deliberately delete the entire machine and rebuild it, from code plus a snapshot, in under an hour.

    Do that once, on purpose, on a quiet afternoon. Until you have, you do not know whether you have backups — you have files you hope are backups.

AZURE · STEP 1

Make it safe: one virtual machine, done properly

  1. Create a resource group and lock down the account

    A resource group is a labelled box holding everything for one environment. Its real value: deleting the group deletes everything inside it, so cleaning up after an experiment is one command with nothing left behind. Use one group per environment.

    Turn on two-factor authentication and set a spending alert before anything else.

    az group create -n rg-racktrack-prod -l centralindia

  2. Create the registry and upload the sealed box

    az acr create -g rg-racktrack-prod -n racktrackacr --sku Standard
az acr login -n racktrackacr

docker buildx build --platform linux/arm64 \
  -t racktrackacr.azurecr.io/racktrack:$(git rev-parse --short HEAD) \
  -t racktrackacr.azurecr.io/racktrack:latest --push .

    Worked if

    az acr repository list -n racktrackacr shows racktrack.

  3. Put your passwords in Key Vault

    Same idea as the AWS locked drawer. The machine is given an identity that Azure itself vouches for, so it can open the drawer without ever holding a password. 

    az keyvault create -g rg-racktrack-prod -n kv-racktrack-prod -l centralindia
az keyvault secret set --vault-name kv-racktrack-prod -n JWT-SECRET --value '...'
az keyvault secret set --vault-name kv-racktrack-prod -n SMTP-PASS  --value '...'

    Small gotcha

    Key Vault names cannot contain underscores, so JWT_SECRET becomes JWT-SECRET. Your startup script has to translate the names back.

  4. Create the virtual machine

    Standard_D2ps_v6 — 2 processors, 8 GB memory, ARM. If you would rather not deal with two processor types, Standard_D2as_v5 is the ordinary-processor equivalent at slightly higher cost. 

    az vm create -g rg-racktrack-prod -n vm-racktrack \
  --image Ubuntu2404 --size Standard_D2ps_v6 \
  --assign-identity --generate-ssh-keys \
  --public-ip-sku Standard --nsg-rule NONE

# a separate 128 GB fast disk for everything that changes
az vm disk attach -g rg-racktrack-prod --vm-name vm-racktrack \
  -n disk-racktrack-data --new --size-gb 128 --sku Premium_LRS

    Do not pick a "B" size

    Azure's B series is burstable, exactly like AWS's t4g, and fails the same way under sustained photo analysis.

    --nsg-rule NONE means no ports are opened by default — you then open only 80 and 443. Get shell access through Azure Bastion or az ssh with your Microsoft login, so there is no key to lose and every session is logged.

  5. Turn on Azure Backup

    This is the backup fix on this side.

    az backup vault create -g rg-racktrack-prod -n rsv-racktrack -l centralindia
az backup protection enable-for-vm -g rg-racktrack-prod \
  --vault-name rsv-racktrack --vm vm-racktrack --policy-name DefaultPolicy

    A genuine Azure advantage

    You can set the backup schedule directly in India Standard Time. AWS only schedules in UTC, so you have to convert and it is easy to get wrong. Set 2:00am IST, keep 14 daily and 8 weekly.

  6. Add Litestream, pointed at Blob Storage

    Identical in effect to the AWS version — same tool, same zero code changes, different destination.

    dbs:
  - path: /opt/racktrack/data/server/data/auth.db
    replicas:
      - type: abs
        account-name: stracktrackbackup
        bucket: litestream
        path: auth.db

  7. Domain, HTTPS, deployment and monitoring

    • Reserve a static IP, point demo.racktrack.ai at it, keep your existing Caddy container for certificates.
    • Deploy from GitHub using workload identity federation — Azure trusts GitHub directly, so no Azure password is stored in GitHub.
    • Install the Azure Monitor agent for logs. Add an availability test that fetches /healthz every few minutes from outside, and alerts if it fails.

  8. Write it down as Bicep or Terraform

    Bicep is Microsoft's own and reads more cleanly for Azure-only work. Terraform is worth it if you might ever use both clouds. Either way, the finishing test is the same: delete the machine on purpose and rebuild it from code plus a restore point, within an hour.

The code work — identical on both clouds

This is what Step 2 really is, and why it is months rather than weeks. None of it depends on which cloud you chose, so it can start before you decide.

2.1

Move the database to PostgreSQL

4–8 weeks

316 places in the code ask the database questions, spread over 25 files and three separate databases. But the count is not what makes this hard.

The actual difficulty

Your current database answers instantly, because it is a file on the same machine — the code asks a question and the answer is simply there on the next line. A real database server sits across a network, so every question becomes "go and ask, and carry on when the answer comes back."

That difference spreads. A function that waits must be called by a function that also waits, and so on all the way up to the web request. So this is not find-and-replace: it changes the shape of a large part of the codebase.

The order that works

  1. Gather the questions. Move all 316 scattered queries behind named functions like users.findByEmail(), still using the old database. Nothing changes behaviourally, and it can be reviewed in small pieces.
  2. Make those functions wait — while still using the old database underneath. This is where the ripple happens. Doing it against a database you already trust means any breakage is definitely your change, not the new database.
  3. Swap in PostgreSQL. Now a contained change behind a boundary you built in step 1.
  4. Move the data. Watch for the small incompatibilities: automatic ID numbering works differently; your login query relies on case-insensitive matching that PostgreSQL does not do by default (get this wrong and people cannot sign in with a capital letter in their email); date handling differs.
  5. Run both side by side for a week, writing to each and comparing, before trusting the new one.

Do not merge steps 2 and 3. Changing the code shape and the database at the same time means that when something breaks you cannot tell which caused it. That is the version of this project that runs six months and gets quietly abandoned.

2.2

Move scan photos to cloud storage

2–3 weeks

234 file operations, 55 references to the outputs folder, 45 places building a outputs/<rack>/ path, and one line serving every scan image straight off the disk.

  • Build one small module with three operations — save a file, read a file, make a temporary link — with a cloud version and a local version for development.
  • Replace the line that serves images from disk with one that checks permission and then redirects the browser to a temporary private link. Users see no difference; the image bytes stop travelling through your app, which makes pages load faster and costs less.
  • Keep the folder naming exactly as it is. It maps cleanly onto cloud storage names, so moving becomes a copy rather than a reorganisation. Reorganising during a migration is how files go missing.
2.3

Make switch polling run in exactly one place

~1 week

Today, every copy of the app starts its own hourly switch-polling loop with no coordination. Two copies means two SSH sessions into every customer switch, every hour, forever — and two sets of records written. That is a problem you would hear about from customers.

  • Add a switch so it only runs when explicitly told to. Web copies run without it.
  • Run it as a scheduled job — once per hour, one instance, using the same sealed box.
  • Add a database-level lock so that even if two ever start, only one proceeds.

Do the same for the ticket poller and the orphaned-record cleanup, which have the same shape.

2.4

Share the upload limits and the busy flags

2–3 days

I measured this directly: with a limit of 20 uploads a minute and two copies running, 40 got through. Each copy counts on its own. Your own code comments already note this and say it needs a shared scratchpad if you ever scale out.

  • Move the counting into Redis so all copies share one tally — or push limiting up into the load balancer, which is cheaper and stops the traffic before it reaches your app at all.
  • Move the eight "already working on this" flags into Redis with expiry times, so two copies cannot start the same expensive analysis twice.

Go-live day

The switchover itself. Same on both clouds. The rule throughout: never remove the old thing until the new thing has proven itself.

Switching to the new server (end of Step 1)

  1. Run it in parallel for a week

    Build the new server completely and run it on a temporary address like new.racktrack.ai. Use it properly — real scans, real accounts, the mobile app. A week is enough for the differences to surface.

  2. Practise the restore before you need it

    Deliberately wipe the data disk on the new server and bring it back from a snapshot plus Litestream. Then count: are all the accounts there? All the scans? All the photos?

    Do not skip this

    This is the step everyone skips and everyone regrets. Until you have restored once, you do not have backups.

  3. Lower the DNS switching time, a day ahead

    Set the TTL on demo.racktrack.ai to 60 seconds. This controls how long the internet caches the old address. Do it 24 hours before, or the switchover takes hours to take effect and rolling back takes just as long.

  4. Move the data, on a quiet evening

    Stop writes on the old server, take a final database checkpoint, copy the database and photos across, then verify counts on both sides match — number of users, number of racks, number of files. Do not proceed on a mismatch.

  5. Flip the address and watch

    Point the domain at the new server. Watch /healthz and the error rate for an hour. Sign in yourself, on the web and in the mobile app, and run one real scan end to end.

  6. Leave the old server alone for two weeks

    Do not cancel Hostinger. Rolling back is just pointing the domain back — but only while that machine still exists. Two weeks covers the problems that only show up on a monthly cycle, like billing or scheduled reports.

Switching the database and storage (end of Step 2)

  1. Write to both, read from the old one

    For a week, every change goes into both the old and new database while the app still reads from the old. A background check compares them and reports any disagreement. This finds the subtle differences with no risk to users.

  2. Copy the photos, then copy the difference again

    Bulk-copy everything to cloud storage in advance, then re-copy just what changed at switchover. The first pass takes hours; the second takes a minute.

  3. Move reads across in small groups, not all at once

    Start with sign-in — it is the most used, so problems appear within minutes rather than days. Then racks, then scans, then reports. Each behind a switch you can flip back instantly.

  4. Only then go from one copy to two

    Run on one copy for a full clean day first. The shared-state bugs appear the moment there is a second copy, and you want to be watching when they do — not discovering it overnight.

  5. Keep the old database, replicated, for 30 days

    Cheap insurance against a problem that only appears at month-end.

Choosing

Pick AWS if

  • Cost matters at this stage — it is cheaper at Step 1 and substantially cheaper at Step 2.
  • You want the largest pool of documentation and people who have hit your exact problem before.
  • Every tool this plan leans on — Litestream, ECS, RDS — is at its most well-trodden here.

Pick Azure if

  • You sell to enterprises already built on Microsoft. Your app already speaks Microsoft sign-in, Graph and Teams — that is a real signal about who your buyers are.
  • Microsoft-estate integration is part of the sales pitch, not an afterthought.
  • Scale-to-zero on photo analysis and the built-in scheduled jobs fit your bursty workload neatly.

My recommendation

AWS, and start Step 1 now — on cost and on how well-trodden every tool in this plan is there.

But the honest headline is that the choice of provider matters far less than the order of the work. Either one fixes the same problems. Only one sequence gets you there without a stalled rewrite.

The Microsoft integration already in your code is the one real argument for Azure, and if selling into Microsoft estates is the strategy, it is not a small one. That is a commercial judgement, not a technical one — which is why it is yours and not mine.

This week, whatever you choose

  1. Fix the sealed box. One hour, and it is a live exposure of real passwords.
  2. Put Litestream on the server you already have. An afternoon. This alone removes the risk of losing everything to one disk failure, and it does not depend on any decision here.
  3. Pick the provider and region, and open the account. Nothing else starts until this does.

Item 2 is the one I would not wait on. Every day without it is a day where a single hardware failure erases every account and every scan you have.
