1Executive summary

Recommendation: migrate fully to AWS (Mumbai region) in three standard phases — Rehost (2 weeks) → Replatform (one focused month) → Refactor (usage-triggered). Azure is a close second, preferred only if Microsoft's startup credit program materially funds year one; the architecture is identical on both by design, so that decision is commercial, not technical.

The application is already containerized and already runs on a cloud server. This migration is a maturity upgrade — automated backups, managed secrets, a professional database, no single point of failure — not a rescue or a rewrite. Costs start near $170/month and reach about $1,400/month at 10,000 users; per-user cost falls 13× as we grow.

Approvals requested: the provider decision (next week, after credit answers), the budget envelope, and one protected engineering month for the Replatform phase.

2Where we are today — and how we know

RackTrack currently runs, in its entirety, on one rented 2-CPU / 8 GB cloud server (demo.racktrack.ai): the website and mobile app backend, the AI scanning pipeline, the user database, and every scan photo. Updates are copied over by hand. There are no automatic backups. It serves demos and testers reliably — and it is one machine away from losing everything, which is the problem this migration solves.

How we know: in August 2026 a full audit of the codebase was completed — every API route was counted (239 registered, ~203 live in production), every AI model file was opened and its architecture verified, the server's deployment files and its own measured performance logs were read, and disk usage was measured directly. A separate three-part security review of the code was run as part of this report (section 10). The detailed technical evidence lives in the Cloud Dossier, with file-level citations.

4The standards this migration follows

  • Migration framework: the industry-standard "7R" model published by both AWS and Microsoft. We use three of its strategies in sequence: Rehost (move as-is), Replatform (swap self-managed parts for managed services), Refactor (multiple app copies + AI acceleration).
  • Architecture standard: each phase is reviewed against the provider's Well-Architected Framework (security, reliability, performance, cost, operations). Both vendors offer this review free with their own engineers; we take it after Phase B.
  • Application standard: Phase B brings the app to the 12-factor shape — config in the environment, state in backing services, processes disposable — which is what makes multiple copies possible.
  • Compliance: both providers hold ISO/IEC 27001, 27017, 27018, SOC 1/2/3, PCI DSS and CSA STAR attestations, and operate MeitY-empanelled datacenters in India — our users' data stays in-country, aligned with the DPDP Act 2023. The application's own DPDP duties (privacy policy, consent, deletion path) are flagged as product tasks in section 11.
  • Portability: a standing rule of this plan — only portable building blocks (containers, PostgreSQL, S3-compatible storage, Redis) in the application's critical path, so changing clouds remains a weeks-scale move and vendor lock-in never becomes leverage against us.

5Azure vs AWS

On trust and compliance they are equals. The decision is about fit, and four differences matter for us:

DimensionAssessmentAdvantage
Security certifications, India data residency, reliability SLAsIdentical portfolios; both reach 99.99% availability at our target architectureequal
Everything in one Indian regionAWS Mumbai carries the full catalog including AI hardware; Azure Central India has limited GPU stock, which could split our architecture across regionsAWS
Migration-path maturityThe exact journey we need (VM → managed DB/storage/queue → container replicas) is AWS's most-documented path, with the largest talent poolAWS
Microsoft ecosystem fitOur app already sends mail and reports via Microsoft services (Teams, Outlook). On Azure those connections use managed identities — removing a class of stored secrets — and our Microsoft-365-centric buyers recognize the storyAzure
Startup creditsMicrosoft's Founders Hub is self-serve and can reach $150k; AWS Activate at meaningful size usually needs an accelerator affiliationAzure

AWS — pros / cons

  • pro Full catalog in Mumbai (residency + latency + one region)
  • pro Most proven path, deepest documentation and hiring pool
  • pro Best AI-hardware economics (widest choice, deepest spot market); CDN with a permanently free first terabyte
  • con Microsoft integrations keep using stored OAuth secrets (managed in a vault)
  • con Meaningful credits need an accelerator relationship
  • con Sharp configuration edges (load-balancer timeouts, private-network fees) — mitigated by infrastructure-as-code

Azure — pros / cons

  • pro First-party fit with our Teams/Outlook/Graph integrations; managed identity removes stored credentials
  • pro Enterprise sales alignment with M365 + ServiceNow buyers
  • pro Most accessible startup credits — can fund year one
  • con GPU stock/quota friction in Central India
  • con Managed-container storage is incompatible with our current database until Phase B (VM-only until then)
  • con Fewer reference implementations of this exact migration

6Recommendation

Primary: AWS, Mumbai region — subject to one condition executed first. This week we apply to both credit programs (free, fast). If Microsoft awards $25,000+ in credits, year one runs on Azure Central India instead — the plan is identical on both clouds by design, so this is a commercial decision, not a technical rework. On merits, AWS wins the two dimensions that carry operational risk for a team our size: everything in one Indian region, and the most-proven migration path.

8Capacity — what the numbers say about 100 → 10,000 users

Assumptions stated so anyone can re-run the math: field-ops usage means 5–10% of registered users active in the peak hour, each running 2–6 scans/hour.

Registered usersPeak-hour scansWhat carries it
10010–60One 8-CPU / 32 GB server (Phase A shape) — measured scan cost says this is comfortable
1,000100–600The ceiling of one box — Phase B must be complete before this point
10,0001,000–6,0002–3 app replicas + one GPU inference node (a single mid-range GPU clears 7,000+ scans/hour)

The honest bottleneck is not the AI scan (3–8 s) but the background label-reading: 1–2 CPU-minutes per scan, currently unlimited in parallel. Capping it is a one-day Phase A task; moving it to a queue (Phase B) and later to GPU (Phase C) turns the app's slowest moment — device names appearing minutes after a scan — into seconds.

Load-test gate (Phase A, on the real server): ramp 1→10 virtual users over 10 minutes, then a 20-minute soak, every request a distinct test image (identical images hit the result cache and measure nothing — a detail from how the app hashes photos). Pass: 95th-percentile scan under 10 s, zero out-of-memory kills, no server errors, OCR backlog drained within 15 minutes. Capacity is measured before users arrive, not assumed.

10Security review

As part of preparing for the migration, an independent three-part review of the code was run: authentication & tenant isolation, input handling & injection, and secrets & deployment hardening. This is the right time — every finding below was caught before the move, not after a breach, and each is scheduled into a phase with an owner.

The good news is the foundation. The application's core security design is genuinely strong for a pre-launch product and was verified sound: encryption of stored switch credentials (AES-256-GCM, correct key handling), password hashing (bcrypt cost 12 with auto-upgrade), login-token handling (algorithm-pinned, revocable, hashed refresh tokens), social-login CSRF protection, database queries (fully parameterized — no SQL-injection paths found), and report generation (all user text properly escaped — no cross-site-scripting paths found). The risk is not the design; it is a specific set of gaps, most of them small fixes.

Critical — must be fixed before opening to customers

#FindingFix
C1Cross-tenant data exposure. A rack-grouping endpoint accepts scan IDs in the request body and skips the ownership check, so any signed-in user can pull another customer's full scan report — devices, ports, images.One ownership check added to the loop (small code change).
C2Unauthenticated file write. A label-OCR endpoint has no login requirement and no ID validation — an anonymous caller can overwrite another tenant's data, and a crafted ID can write outside the intended folder.Add login requirement + ID format validation (small code change).
C3Switch command injection. On four switch-console endpoints the interface name from the request is written straight into a live switch shell — line breaks in it run as extra switch commands, letting a member reconfigure production network gear (without even needing the switch password).Validate the interface name against the format the code already defines elsewhere.
C4Secret leakage. An Apple signing key and some credential files reached pushed git history, and the Docker build packages the user database, the login-signing key, and a plaintext tester list into the image. (Fixable, and the app has no hardcoded secrets in its source — a clean result.)Rotate the exposed keys, fix the Docker ignore list (one line), purge the git history. Order matters — see below.

High — fix during Phase A hardening

FindingFix
Admin checks fail open. Two admin-only actions (delete scan folders, launch retraining) grant access to every user when an optional environment setting is unset — which it is on a fresh deploy.Invert the check to require the owner role (three lines).
Marketplace OAuth linking is forgeable. The eBay/Amazon account-linking flow trusts a user ID passed in the URL, so an attacker can link their partner account to any user. (The social-login flow does this correctly — copy that pattern.)Use a random single-use token, as the social-login code already does.
Five compute endpoints have no login requirement (live viewfinder, image stitch, label OCR, two ticket-scan routes) — anonymous callers can run the AI pipeline and create orphaned records.Add the login requirement their sibling endpoints already use.
Server-side request forgery. Connection profiles and a Discord webhook accept an arbitrary destination address. After migration the server sits next to cloud internal services and a metadata endpoint — this becomes a way to reach them. This one is more important in the cloud than on the current box.Restrict destinations to allowed hosts; block internal/metadata addresses.
Rate limiting collapses behind the proxy. Because the app doesn't trust the proxy header, every anonymous request looks like it comes from one address, so all anonymous traffic shares a single rate-limit bucket — easy to exhaust.Enable "trust proxy" (one line).
Image-access tokens survive logout for up to 12 hours and can't be revoked — a signed-out or removed user keeps image access.Add a version/user stamp to the token and check it.
Secondary git remotes still carry the login-signing key and ServiceNow credentials in history.Rotate and purge across all remotes in one pass.
A config file is world-readable on disk, and the code only sets safe permissions on first creation.Set correct permissions and enforce them on every write.

Medium & hardening (Phase A/B backlog)

Around fifteen defence-in-depth items, none a launch blocker on their own: the container runs as root (add a non-root user); no Content-Security-Policy on the web app (enable one); an end-of-life file-upload library (upgrade to v2); capability tokens travelling in URLs and landing in logs (move to headers, redact URLs); Netdisco inventory visible across tenants (scope it); the dependency-confusion install shape flagged in our own code comments (pin the package index); base images on floating tags (pin by digest); CSV export formula injection (neutralize leading `=`/`+`/`-`/`@`); and a handful of input-validation and rate-limit gaps. All are catalogued with file locations and one-line fixes in the working audit notes.

Remediation order (from the reviews)

  1. Revoke the exposed live keys (Apple, ngrok, Microsoft OAuth tokens) — revocation is instant and defuses the leaks immediately.
  2. Rotate the signing key, mail/Netdisco/ServiceNow credentials, and any switch passwords.
  3. Fix the Docker ignore list (C4) — a one-line change that stops the image leak — and the four small code fixes (C1, C2, C3, fail-open admin).
  4. Purge git history across all remotes in one coordinated pass; verify the automated secret-scanner in CI actually runs.
  5. Then the hardening backlog, folded into Phase A and B.

Items 1–3 are the pre-launch blockers and are all fast. This review is exactly why a standards-led migration is worth doing deliberately rather than in a rush — the findings are ordinary for a product at this stage, and catching them now is the process working as intended.
