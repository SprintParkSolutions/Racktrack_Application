Azure vs AWS for RackTrack

Every realistic way to run RackTrack on each cloud — evaluated against what the app actually is: resident 2.5 GB CV workers, SQLite until the Postgres migration, 340 MB uploads, an SSE stream, and 1–2 minute background OCR jobs. Prices are current on-demand list rates (US regions; add ~5–10% for Mumbai / Central India). Companion to the Cloud Dossier.

Why Azure is genuinely in the running for this app

RackTrack is already half-married to Microsoft: report sharing goes through Teams and Outlook via Microsoft Graph, mail uses MSAL app registrations that exist today in your Entra tenant, and the buyers you're courting (ServiceNow + M365 shops) live in that ecosystem. Azure adds three concrete things on top: first-party Graph/Entra integration (managed identities instead of client secrets in env files), an enterprise sales story ("runs in our Azure tenant" opens doors at M365-heavy datacenter operators), and Microsoft for Startups Founders Hub credits — $1k–5k almost on signup, up to $150k with progression, which can cover year one entirely.

The Azure blueprint, phase by phase

Phase A · 100–300 users · days of work

One VM, same compose files

  • Compute: Standard_D8as_v5 (8 vCPU / 32 GB) — ~$251/mo on-demand, ~$172/mo on a 1-year savings plan. Region: Central India (Pune) for your users; South India as fallback.
  • Disk: 256 GB Premium SSD (~$20/mo) — SQLite and outputs/ stay local and fast.
  • Unchanged: the demo's exact docker-compose.demo.yml + Caddy for TLS. Raise RACKTRACK_WORKERS to 5–6, cap OCR at 1–2 concurrent.
  • Azure Backup nightly VM + a scripted auth.db dump to Blob (~$5/mo). Key Vault for JWT/SMTP/OAuth secrets from day one.
  • NSG open on 80/443/SSH only; Entra-based VM login instead of shared SSH keys.
Phase B · before 1,000 users · the migration phase

Managed state, two VMs, object storage

  • Postgres: Azure Database for PostgreSQL Flexible Server — start B2ms (~$60/mo + storage), move to D2ds_v5 (~$140/mo) as load grows. Zone-redundant HA doubles it — defer HA until Phase C.
  • Redis: Azure Cache for Redis Basic C1 (~$41/mo) for rate limits, queues (BullMQ), job dedupe.
  • Storage: Blob Storage Hot LRS (~$0.018/GB) for uploads + scan outputs; lifecycle rule to Cool at 90 days. Models live here too, versioned, pulled at boot.
  • Compute: split — D4as_v5 API VM (~$126 / $86 reserved) + D8as_v5 inference VM. The queue between them replaces the in-process worker pool dispatch.
  • Edge: Front Door Standard (~$35 base + egress) for CDN/WAF — or keep Caddy and add Blob-backed asset serving; skip Application Gateway (a ~$180+/mo cost trap this app doesn't need).
  • Ops: Azure Monitor + Managed Grafana on the existing Prometheus /metrics; ACR Basic ($5) + GitHub Actions OIDC deploys; a staging slot of everything at B-series sizes (~$60/mo).
Phase C · 1,500–10,000 users

Replicas, GPU, HA

  • API: 2–3 replicas on Container Apps (post-Postgres this is clean) or a VM Scale Set behind Front Door.
  • GPU inference: NC4as_T4_v3 (T4 16 GB) ~$0.53/hr ≈ $385/mo on-demand; spot ~$0.10–0.16/hr ≈ $75–120/mo with a CPU fallback pool for evictions. NV6ads_A10_v5 (~$0.45/hr) is the step up. caveat GPU quota defaults to zero and Central India GPU stock is thin — request quota early; be ready to place GPU in South India or Southeast Asia (+~20–40 ms).
  • DB: flip Postgres to zone-redundant HA (×2 cost); PITR backups already included.
  • OCR: unpin GPU in code, run OCR on the GPU node — the 1–2 min lag becomes seconds; else an autoscaled CPU OCR VM pool eating spot instances.
  • Front Door WAF policy, DDoS network protection is included at the standard tier.

Azure gotchas specific to this codebase

  • Azure Files ≠ SQLite. Any managed-container path mounts SMB shares; better-sqlite3 over SMB risks corruption and kills the event loop on latency. VM-only until Postgres.
  • Application Gateway is the wrong LB here — expensive, and its default timeouts clash with the SSE stream and 120 s scan requests. Front Door (raise origin response timeout to ≥240 s) or plain Caddy.
  • GPU quotas are zero by default on new subscriptions — the quota ticket takes days; file it the week you decide, not the week you need it.
  • Egress: first 100 GB/mo free, then ~$0.087/GB. At 10k users serving multi-MB scan images, route downloads through Front Door/CDN pricing and lifecycle old artifacts aggressively.
  • Azure Cache for Redis Basic has no SLA — fine for rate limits and queues (the data is disposable), just don't put anything durable in it.

Why AWS fits this app

Three practical reasons: Mumbai (ap-south-1) is a deep region — every instance family, GPU stock included, close to your users; the cheapest credible GPU rung anywhere among hyperscalers (g4dn spot at ~$0.16/hr); and the most worn path for exactly this migration — VPS-shaped EC2 today, ECS + RDS + S3 + CloudFront tomorrow, with the largest pool of docs, tooling, and people who've done it. AWS Activate credits ($1k self-serve, up to $100k via accelerators/partners) are real but harder to reach than Microsoft's program.

The AWS blueprint, phase by phase

Phase A · 100–300 users · days of work

One box, two flavors

  • Budget flavor: Lightsail 32 GB bundle — $164/mo flat, 6 TB transfer included, snapshots for backup. Fastest possible landing.
  • Growth flavor (recommended): EC2 r7i.xlarge + 256 GB gp3 (~$21/mo) + Elastic IP, Route 53 for api.racktrack.ai, ACM certs if you later front with an ALB (Caddy does TLS until then). ~$215/mo on-demand, ~$150 with a 1-yr Compute Savings Plan — and it upgrades in place forever.
  • Same compose files; workers 5–6; OCR capped; AWS Backup plan for EBS + nightly auth.db sync to S3; Secrets Manager (or SSM Parameter Store, free tier) replaces .env secrets.
Phase B · before 1,000 users · the migration phase

Managed state, split compute

  • Postgres: RDS db.t4g.medium — $47/mo single-AZ + ~$12 storage. Multi-AZ waits for Phase C (×2).
  • Redis: ElastiCache cache.t4g.micro ($12/mo) → small ($24) — rate limits, BullMQ queues, dedupe.
  • Storage: S3 ($0.023/GB) for uploads/outputs/models with lifecycle → Infrequent Access at 90 days, Glacier at 1 year — the "disk grows forever" problem becomes a $10 line item.
  • CDN: CloudFront in front of the SPA + scan images — the first 1 TB/mo of egress is free forever, which at ~8 MB per scan view is a meaningful subsidy.
  • Compute: m7i.large API node (~$74) + r7i.xlarge inference node; queue between them.
  • Ops: ECR + GitHub Actions OIDC deploys; CloudWatch alarms on the existing /metrics (or Amazon Managed Grafana); a t3.medium staging copy (~$30).
Phase C · 1,500–10,000 users

Replicas, GPU, HA

  • API: ALB (~$25–40/mo — set idle timeout ≥300 s or the SSE console stream and long scans die) + 2–3 m7i.large in an ASG or ECS service.
  • GPU inference: g4dn.xlarge (T4) $0.526/hr ≈ $385/mo on-demand, spot ~$0.16–0.21/hr ≈ $120–155/mo; g6.xlarge (L4) $0.805/hr ≈ $588 when you want headroom. One T4 clears the entire 10k-user YOLO load; run 1 on-demand + spot for burst. G-instance vCPU quota defaults to 0 — request it early.
  • OCR: unpin GPU in code and co-locate on the GPU node, or an ECS spot fleet of CPU OCR workers scaled on queue depth.
  • DB: RDS Multi-AZ (~$95–190 depending on size), automated PITR; WAF on ALB/CloudFront; AWS Budgets alerts at every phase.

AWS gotchas specific to this codebase

  • ALB idle timeout (default 60 s) silently kills the SSE switch-console stream and can cut off 120 s scan requests — raise it the day the ALB appears.
  • Never route uploads through API Gateway (10 MB cap). ALB and CloudFront pass 340 MB bodies fine.
  • The NAT Gateway tax: $32/mo + $0.045/GB processed. This app scrapes vendor firmware sites and calls Graph/ServiceNow constantly — keep egress-heavy instances in public subnets with strict security groups at small scale; add NAT only when compliance demands private subnets.
  • Mumbai premium: ~5–10% over us-east-1 list; still the right call for India-based users (the viewfinder endpoint is latency-sensitive at 180 req/min).
  • gp3 EBS baseline (3,000 IOPS) is plenty for SQLite + outputs; don't pay for io2.

The dimensions that actually decide it

Raw price AWS

Lightsail entry, cheaper managed Redis/Postgres at small sizes, CloudFront's free TB, and the best spot-GPU market. Azure's reserved pricing closes most — not all — of the gap.

Your users' latency AWS

Mumbai has everything in one region, GPUs included. Azure Central India is fine for CPU but may push your GPU to another region, splitting the architecture.

Microsoft integration Azure

Graph mail and Teams/Outlook shares get managed identities instead of secrets; Entra app registrations you already own sit next to the infra; M365-shop customers recognize the story.

Free money Azure

Founders Hub is self-serve and generous — realistic odds of running Phase A+B on credits for a year. AWS Activate at meaningful size usually needs an accelerator affiliation.

Migration path maturity AWS

The exact path this app needs (EC2 → RDS/ElastiCache/S3/CloudFront → ECS+ALB) is AWS's most-documented journey; hiring and debugging help is easiest here.

Post-Postgres container DX Azure

Container Apps is the pleasant way to run 2–3 API replicas; ECS is more powerful but more assembly required.

Non-differentiators (don't let them decide)

  • Reliability: at this architecture (LB + replicas + Multi-AZ DB) both clouds deliver the same nines.
  • Security services: WAF, DDoS shielding, secret stores, IAM — equivalent capability, different names.
  • The app code: nothing in RackTrack is cloud-specific; the entire Phase B migration (Postgres, Redis, S3-compatible storage, queue) is portable across both — and back to a budget host. Keep it that way: use S3-compatible SDK paths and plain Postgres, no proprietary services in the hot path.

The recommendation

Build on AWS Mumbai (ap-south-1). Sequence one thing first: apply to Microsoft for Startups Founders Hub and AWS Activate this week — and if Founders Hub lands $25k+ in credits, run year one on Azure Central India instead. The architecture below maps one-to-one across both clouds, so the credit outcome changes the logo, not the plan.

Why AWS on merits: your users are in India and Mumbai has the full catalog including in-stock T4 GPUs; the entry rungs are cheaper (Lightsail, $12 Redis, $47 Postgres, CloudFront's free terabyte); and the exact migration this app needs is the most-trodden path in cloud computing. Azure's genuine advantages — Graph managed identity, Container Apps, easier credits — are worth taking if they're paid for in credits, but they don't outweigh Mumbai's GPU availability and the price gap at list.

What you have today

Your whole app lives on one small rented computer (the demo server). That one computer does everything: it shows the website, it runs the AI that reads rack photos, it keeps the list of users, and it stores every scanned photo. It's like running a restaurant where one person is the waiter, the cook, the cashier, and the storeroom keeper. It works fine because there are only a few customers.

What "hosting in the cloud" means

Instead of that one small computer, you rent computers from a big company — Amazon (AWS) or Microsoft (Azure). They own giant buildings full of computers, and you pay monthly rent for the slice you use. The big advantage isn't just bigger computers — it's that they also rent you ready-made helpers: a professional database service, a photo warehouse, automatic backups, security guards. You stop maintaining those things yourself.

What's a GPU, and do you need one?

A GPU is a special chip that does AI math very fast. Your app was deliberately built to work without one — a normal computer does a scan in 3–8 seconds, which users find fine. You'll want a GPU later for two reasons: when there are so many scans per hour that you'd otherwise need 3–4 extra normal computers (that happens around 3,000–5,000 users), and to make the label reader fast (minutes → seconds). Renting one GPU computer costs about $120–400/month depending on how you buy it. For retraining your AI models, you rent a GPU by the hour — a whole training run costs about the price of a coffee.

Azure vs AWS, in one breath each

AWS (Amazon) is the biggest computer-renting company. Its Mumbai location has everything you need — including GPUs — close to your users, its starter options are cheaper, and more people have walked this exact path, so answers to any problem are a search away.

Azure (Microsoft) rents essentially the same things. Its special appeal for you: your app already sends mail and reports through Microsoft's services (Teams, Outlook), and those connections get simpler and safer inside Azure. Microsoft also has a startup program that hands out free credits — sometimes enough to cover a whole year of rent.

Our pick: AWS Mumbai — unless Microsoft gives you serious free credits, in which case take Azure for year one. The plan is identical on both; only the shop names change.

The two mistakes that sink apps like this

  • Waiting too long: piling users onto the single computer until it runs out of memory during a customer demo, and then doing the Phase-B renovation in a panic. Do it calmly, early.
  • Jumping too far: building the fancy 10,000-user setup while you have 200 users — you'll spend months on plumbing instead of the product. The phases exist so each month's work matches that month's real need.

What to actually do this week

  1. Apply to both free-credit programs (Microsoft for Startups, AWS Activate). Free money decides the vendor.
  2. Decide the permanent web address for the API (like api.racktrack.ai) — the phone apps have it baked in, so pick once, keep forever.
  3. Ask AWS/Azure for GPU permission now (new accounts start at zero; approval takes days and costs nothing).
  4. Fix the safety list: backups that actually restore, secrets out of the code, every data folder protected from redeploys, all six AI model files safely stored in two places.
