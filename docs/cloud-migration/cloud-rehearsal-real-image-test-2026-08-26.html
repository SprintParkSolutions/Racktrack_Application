The rig

What was built, and why it is a fair test.

Your production Dockerfile deliberately leaves Models/ out and expects a host bind-mount. That works on a VPS you rsync to; it is impossible on a managed platform, because there is no host to mount from. So the rehearsal image bakes the 403 MB of weights in — which also makes the container genuinely self-contained. That property is the whole point: if it reads nothing from your Mac, it would read nothing from a cloud host either.

The load balancer does plain round-robin with no session affinity, on purpose. Sticky sessions would hide exactly the failures worth finding, and "turn on stickiness" is not an architecture.

One obstacle that is not RackTrack's fault. This office LAN (gateway 10.10.1.1) returns 403 on plain HTTP to deb.debian.org and TLS-intercepts it on HTTPS, so apt-get inside any build fails with exit 100. Your image only builds today because it is built on the VPS, not here. I routed around it via debian.osuosl.org in a rehearsal-only Dockerfile. Any CI runner you put on this network will hit the same wall.

Three scenarios, in order of cloud-nativeness

Same image every time. The only variable is where state lives.

Scenario A

Lift and shift

One replica, no host mounts, all mutable state on a managed volume. The ECS + EFS / Container Apps + Azure Files shape.

Works — unmodified 
/healthz          10/10  200
POST /api/auth/login     200  — bearer token issued
GET  /api/auth/me 10/10  200  → owner
GET  /api/racks   10/10  200

# then: destroy the container entirely, as a platform replaces a task
docker compose rm -sf app-a   →  container gone, volume survives
docker compose up -d app-a    →  healthy
POST /api/auth/login          →  LOGIN OK — state survived

This is the honest headline: your app runs on a managed container platform today, with no code changes. It survives the platform destroying and replacing the container, which is the behaviour that kills naive migrations.

Scenario B

Scale out

Two replicas sharing one filesystem, behind the load balancer.

Passes here — misleads about EFS 
/healthz           5x app-a  5x app-b
GET /api/auth/me   5x app-a → owner   5x app-b → owner
GET /api/racks     both replicas agree
app-a writes /app/outputs/RK-CROSSTEST → app-b sees it
auth.db inode      250877 on both — one file, two writers
SQLite lock errors 0

# 60 concurrent logins (each writes audit + refresh rows)
  20x 200 via app-a      20x 200 via app-b
  10x 429 via app-a      10x 429 via app-b   ← limit applied twice

Sessions and data hold up. But two real defects surface. The upload rate limit is configured at 20/min and 40 got through — each replica keeps its own in-memory bucket. Your own source already says so: "Single-process only… if we ever scale horizontally, this needs Redis."

Do not read this row as "EFS will work." A shared Docker volume is a local filesystem, where SQLite's WAL mode is fine. EFS and Azure Files are NFS/SMB, where WAL is not supported — it needs shared memory the network filesystem cannot provide. All three of your databases open with journal_mode = WAL. This is reasoned, not measured: I could not test NFS locally, and it is the single thing I would prove before trusting a shared mount.

Scenario C

The platform default

Two replicas, no shared storage — what Fargate, Cloud Run and Container Apps give you out of the box.

Breaks, intermittently 
GET /api/auth/me
  5x  via app-b  200  → owner
  5x  via app-a  401  → "User no longer exists"

GET /api/racks
  5x  via app-b  200
  5x  via app-a  401

# meanwhile, what the platform's health check believes:
  :8081 /healthz  ok=True        rte-app-a=healthy
  :8082 /healthz  ok=True        rte-app-b=healthy

Half of every user's requests fail, at random, while the deployment shows green on both replicas. /healthz checks that the process is up — it never checks that this replica can see the data. That combination is the worst kind of outage to diagnose: users report being "randomly logged out" and every dashboard says the service is fine.

What has to change, and how much of it there is

Measured against the current tree, not estimated.

25 files · 3 DBs		 auth.db, racktrack.db, logs.db Single-writer, file-local. Every replica needs the same rows; WAL rules out a network share. This is the Postgres migration.

Rate limiter is per-process measured 2× at 2 replicas server/lib/rate_limit.js In-memory token bucket. Your effective limit multiplies by replica count — the file's own docstring calls this out.
In-flight dedup sets are local 8 module-scope Maps/Sets server/app.js OCR, cable enrichment and topology regeneration guard against duplicate work per process. Two replicas can run the same expensive job twice.
JWT secret generated per instance 1 line server/auth.js:37 Unset JWT_SECRET and each replica writes its own jwt.secret, so tokens minted by one are rejected by the other. Config, not code — but it must be set.

Found on the way — fix this before any registry-based build

Your image ships the live user database and the token signing key

.dockerignore excludes active_learning_Cache/data and server/uploads — but not server/data. So COPY server/ ./server/ bakes 42 MB of live state into every image layer: 

/app/server/data/
  auth.db            33 users · 33 password hashes · 24 refresh tokens
  auth.db.bak-*      four historical copies, back to 10 July
  logs.db            12 MB of operational logs
  jwt.secret         sha256 identical to your local key

Today this is masked: the VPS deploy excludes server/data from the rsync (deploy/demo-rsync-excludes.txt:46, commented "Host-specific and secret"), so the build context on the box never has it, and the bind-mount shadows it at runtime. The exclusion was written for rsync and never mirrored into .dockerignore.

Moving to cloud is exactly what removes the mask. A registry workflow builds on a developer Mac and pushes to ECR or ACR — and anyone who can pull that image gets your password hashes and a signing key that mints valid tokens. The fix is one line in .dockerignore, plus rotating jwt.secret since it has been in every local image built so far. I have not touched your repo; say the word and I will.

What I would actually do

Two steps, in this order. They are not the same project.

STEP 1 — weeks, not months

One replica on a managed platform, with a managed volume

Proven working above, unmodified. Azure Container Apps or AWS App Runner / ECS, sized at roughly 2 vCPU and 8 GB per replica. This fixes three of the four problems from your own deck — automatic backups, a rebuildable box, and repeatable deploys instead of hand-rsync. It does not fix scale, and it should not pretend to. Set JWT_SECRET explicitly, and settle the SQLite-on-network-storage question before choosing the volume.

STEP 2 — a real project

Postgres, object storage, a singleton worker

This is what buys horizontal scale, and the table above is its scope: 316 query sites to port, 55 output paths to move behind object storage, the poller lifted out into one scheduled worker, and the rate limiter moved to Redis or the proxy layer. Worth doing when concurrent scan load — not availability — is the thing hurting you.

One number to carry into either step: the image is 6.45 GB. That is registry storage, pull time on every cold start, and a real constraint on how fast a platform can scale you out. Splitting the CV pipeline into its own image would cut the web tier to a fraction of it.
