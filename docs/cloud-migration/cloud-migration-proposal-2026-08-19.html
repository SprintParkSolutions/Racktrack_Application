RackTrack Cloud Migration Proposal

Response to the directive to move RackTrack fully to the cloud. This proposal follows the industry-standard migration framework, assesses our application's compatibility honestly, compares Microsoft Azure and Amazon Web Services on standards — compliance, reliability, data residency, ecosystem fit — and ends with a recommendation, a phased plan with go/no-go gates, a risk register, and the specific approvals requested.

Executive summary

Recommendation: migrate to AWS (Mumbai region) in three standard phases — Rehost → Replatform → Refactor — reaching full cloud-native operation within one quarter of engineering time. Azure is a close and credible second, preferred only if our Microsoft-partnership strategy or startup credits outweigh AWS's advantages in region depth and migration maturity. Both providers exceed every compliance and reliability standard we require; the decision is about fit, not capability.

Our application is already containerized and already runs in a cloud VPS today — this is not a rescue project but a maturity upgrade: from one hand-managed server to a standards-compliant architecture with automated backups, secret management, high availability, and room to grow from 100 to 10,000 users without re-planning.

Asks: provider sign-off (pending credit-program outcomes), a monthly budget envelope of $170 → $1,400 as users grow 100 → 10,000, and a protected 3–6 week engineering window for the Replatform phase.

1The standard we will follow

Cloud migrations are classified by the industry-standard "7R" framework (used by both AWS's and Microsoft's Cloud Adoption Frameworks). Of the seven strategies — Rehost, Replatform, Refactor, Repurchase, Relocate, Retain, Retire — three apply to us, in sequence:

Phase7R strategyWhat it means for RackTrackDuration
ARehost ("lift and shift")Move our existing Docker deployment onto a properly sized cloud VM, unchanged. Add the operational standards we currently lack: automated tested backups, secrets in a managed vault, monitoring with alerts, infrastructure as code.~2 weeks
BReplatformSwap self-managed components for managed cloud services: our file database → managed PostgreSQL, local file storage → object storage, in-memory job handling → a proper queue. This aligns the app with the 12-factor application standard and removes every single point of failure.3–6 weeks eng.
CRefactor (targeted)Run multiple stateless application replicas behind a load balancer, add GPU-accelerated inference, CDN delivery, and multi-zone database availability. Triggered by usage metrics, not dates.2–4 weeks, later

Each phase will be reviewed against the provider's Well-Architected Framework — the five/six-pillar standard (security, reliability, performance, cost optimization, operational excellence) both vendors publish and audit against. Both offer a free Well-Architected review with their solution architects; we will take it at the end of Phase B.

Azure — pros & cons

  • pro Native fit with our existing Microsoft integrations; managed identity eliminates a whole class of stored credentials.
  • pro Sales alignment: our target customers run Microsoft 365 + ServiceNow; "deployable in your Azure tenant" is a door-opener.
  • pro Most accessible startup credits — can materially fund year one.
  • pro Container Apps offers the smoothest path for our Phase-C application replicas.
  • con GPU capacity and default-zero quotas in Central India — our AI acceleration may have to live in a second region.
  • con Its managed-container storage (SMB file shares) is incompatible with our current database until Phase B completes — VM-only until then.
  • con Fewer reference implementations of our exact migration; smaller hiring pool locally.

AWS — pros & cons

  • pro Mumbai region has every service we need — GPUs included — keeping data, users, and compute in one Indian region (residency + latency + simplicity).
  • pro The most mature ecosystem for our exact roadmap: managed PostgreSQL, object storage, queues, container orchestration are its flagship services.
  • pro Deepest documentation, community answers, and hiring pool — lowest operational risk for a small team.
  • pro Best economics for AI compute when we need it (widest GPU choice, deepest spot market).
  • con No native Microsoft integration — our Graph/Teams connections keep using stored OAuth secrets (managed properly in a vault).
  • con Meaningful startup credits usually require an accelerator relationship.
  • con Sharper configuration edges (load-balancer timeouts, private-network costs) demand discipline — mitigated by infrastructure-as-code and the free Well-Architected review.

4Recommendation

Primary: AWS, Mumbai region. On standards both providers qualify fully; AWS wins on the two dimensions that carry operational risk for a team our size — everything we need in one Indian region, and the most-proven path for exactly this migration. Condition: we apply to both credit programs first (one week, no cost). If Microsoft's program awards $25k+, the balance tips to Azure for year one — the architecture is identical on both by design, so this is a commercial decision, not a technical rework.

Either way we protect portability as a standing standard: containers, PostgreSQL, S3-compatible storage, Redis — no proprietary service in the application's critical path. That keeps future negotiating leverage and makes the choice reversible.

7Approvals requested

  1. Provider: AWS Mumbai as primary, subject to the credit-program outcomes (decision point: end of Week 0).
  2. Budget envelope: ~$170/month at launch, scaling with users to ~$1,400/month at 10,000 users; plus a one-time ~$100–200 for migration-window duplication.
  3. Roadmap protection: a 3–6 week Replatform window (Weeks 5–10) with a feature freeze during cutover.
  4. Domain: confirmation of the permanent production API domain before mobile builds.
  5. Support plan: provider business-tier support (~$100/month) from Phase B onward — standard practice once production SLOs exist.
