Moving RackTrack to AWS

A plan to move RackTrack off its single hand-managed server and onto Amazon Web Services. The key insight: this migration is not a separate project — it is how you deliver the "operations" and "data safety" gaps from the audit, done properly. The database, backups, monitoring, staging, safe deploys and scaling we flagged as missing are exactly what a real cloud setup provides.

What "complete cloud on AWS" buys you: the app stops depending on one machine, data is stored safely and backed up automatically, it scales up when many technicians scan at once, you get alerted the moment anything breaks, and — importantly — it lays the groundwork for the SOC 2 / ISO certificates enterprise buyers ask for, because AWS provides the compliance building blocks.

Part 2 · the one genuinely AWS-specific decision

Where the AI computer-vision runs

The AI scan (PyTorch + YOLO) is the heaviest, most expensive thing RackTrack does, and it wants a GPU. It is also bursty — busy when technicians scan, idle otherwise. That combination drives the single most important cost decision in the whole migration. Three options:

Async queue + auto-scaling workers RECOMMENDED
SQS → SageMaker Async / GPU ECS · scale-to-zero

A scan drops a job on a queue; GPU workers spin up to process it and shut down when idle. You pay for GPU only while actually scanning — ideal for bursty use. Best cost-to-capability fit for RackTrack.

+ cheapest for bursty load, scales to zero
− scans are processed a moment after upload, not instantly
Always-on GPU endpoint
SageMaker real-time / g4dn ECS

A GPU server always running, ready to answer instantly. Simplest mental model and lowest latency, but you pay for the GPU 24/7 even when nobody is scanning.

+ instant results, simple
− expensive (GPU billed around the clock)
CPU-only, no GPU
Fargate CPU workers

Run inference on ordinary CPU. Cheapest to run and simplest, but each scan is much slower. Fine to start with while volumes are tiny; revisit once scan volume grows.

+ cheapest, simplest to launch
− slow per scan; won't hold up at volume
Recommendation: start CPU-only if scan volume is still small (cheapest, fastest to launch), and design the queue so you can swap in GPU auto-scaling workers later without rearchitecting. The async-queue shape is the right foundation either way — it also stops a burst of scans from ever taking the app down.

Part 3 · the migration, phased so nothing breaks

The roadmap

Move in stages, each shippable on its own, lowest-risk first. The app keeps running throughout — you switch pieces over one at a time, not in a big-bang cutover.

STAGE AFoundation~1 week

Set up the AWS account safely before moving anything.

  • ▸AWS account structure, IAM roles, billing alarms, and a private network (VPC across 2 zones).
  • ▸Pick Terraform or CDK and define everything as code from the start.
  • ▸Container registry (ECR) and Secrets Manager for keys.
STAGE BMove the stateless parts~1–2 weeks

Lift the pieces that hold no data — lowest risk, immediate resilience win.

  • ▸API server → ECS Fargate behind a load balancer.
  • ▸Web app → S3 + CloudFront; DNS & TLS via Route 53 + ACM.
  • ▸Run it side-by-side with the old server; cut traffic over only when green.
STAGE CMove the data — the big safety win~2–3 weeks

This is the highest-value stage: it ends the "no backups / a crash can lose data" risk for good.

  • ▸Migrate SQLite → RDS PostgreSQL; rewrite the scan save so images + owner commit as one atomic action.
  • ▸Move scan folders → S3 (versioned).
  • ▸Turn on automatic backups + point-in-time restore, and do one practice restore.
STAGE DThe AI pipeline~1–2 weeks

Move computer-vision to the queue-based design from Part 2.

  • ▸Scans post a job to SQS; workers process and write results back.
  • ▸Start CPU-only or GPU auto-scaling per the volume decision.
STAGE EPipeline, monitoring & staging~1 week

The automation and eyes-on that make it operable — this is Phase 2 of the enterprise plan.

  • ▸Automatic deploys (CodePipeline) with one-click rollback + a staging environment.
  • ▸CloudWatch dashboards, alarms → phone alerts; error tracking.
STAGE FHarden & optimise~1–2 weeks

Security, cost control, and the enterprise-login groundwork.

  • ▸WAF firewall, Cognito for company sign-in (SSO), container image scanning.
  • ▸Right-size compute, set budgets/alerts, and (later) an EU region for data-residency customers.

Part 5 · the honest trade-offs

What to weigh before committing

AWS is powerful but not free or simple. It adds real monthly cost, and it adds complexity — it genuinely needs someone comfortable with AWS, or a deliberately simple subset, or you trade "one server to babysit" for "twenty services to understand." Go in with eyes open.

You don't have to use everything at once. The single biggest wins — a real database, backups, and getting off one fragile machine — come from just RDS + S3 + ECS/Fargate. A lean start (or even the simpler App Runner instead of full ECS) captures 80% of the value for a fraction of the complexity. Add Cognito, WAF, GPU auto-scaling and the rest as real need appears.

This is the operations plan, cloud-native. Stages C and E here are Phases 2 and 3 of the enterprise roadmap (database + backups, monitoring, staging, safe deploys, SSO). So this isn't extra work on top — it's the same work, done on infrastructure that scales and that auditors already trust.

It makes later compliance easier, not automatic. AWS gives you the building blocks and its own certifications to inherit from, which shortens your SOC 2 / ISO path — but the certificate is still your program to run.

My recommendation: do Phase 1 of the enterprise plan first (the quick wins, tomorrow's work), then run this AWS migration as Stages A–C to get the database, backups and resilience — that's the ~4-week core that removes the scariest risks.
