Cloud migration plan · for review & decision

RackTrack in the cloud:
AWS vs Azure, side by side

Today RackTrack runs on one server we manage by hand. This is the plan to move it to a proper cloud — the same move on both AWS and Azure, compared like-for-like, so we can pick a direction and start.

1 · Why move at all

One server is
the weak point

Everything today depends on a single machine we update by hand. That's fine for a demo — it's a real risk for real customers.

No backups — one dead hard drive erases every customer's data, permanently.
One point of failure — if that server goes down, the whole product is down.
Can't handle a rush — no way to scale up when many technicians scan at once.
Updated by hand — no test copy, no undo if a change breaks something.

2 · What the cloud gives us

The same five wins,
either way

Whichever provider we pick, moving to the cloud delivers the exact gaps we need to close. This is why the move matters more than the brand.

Automatic backups we can actually restore.
No single point of failure — it runs across multiple machines that heal themselves.
Scales on demand — quiet at night, more power during a busy morning.
Built-in monitoring & alerts — we know the moment anything breaks.
Safe, one-button deploys with an undo — and a groundwork for the certificates later.

3 · The two options

Both are excellent. They differ in one thing that matters to us.

AWS
Amazon Web Services — the largest, most mature cloud.
Its edge for us The widest, most cost-effective options for heavy AI (GPU) work, and the most mature machine-learning tooling. RackTrack is an AI-first product — so this is exactly our biggest need.
Azure
Microsoft's cloud — does everything AWS does.
Its edge for us An equally capable all-rounder. Its usual advantage — native "Sign in with Microsoft" — doesn't apply to us, since our users are technicians on company accounts, not Microsoft users. Best pick mainly if our own team already lives in the Microsoft world.

Deep dive · running the app

Where the app itself lives

The plain difference: both clouds run our app inside "containers" — self-contained packages that copy themselves when busy and restart themselves if one crashes. AWS calls its service Fargate; Azure calls its Container Apps. They do the same job.

Why it matters for us: either one ends the "one server, and if it dies we're down" problem. This is not a deciding factor — it's a tie.

AWS · Fargate
How it works The most battle-tested option, with the biggest community and the most examples to copy. A few more moving parts to set up the first time.
Azure · Container Apps
How it works Newer and a little simpler to start, with "scale to zero" built in (it can idle down to nothing when unused). Slightly smaller community.

Deep dive · the data

The database and the scan photos

The plain difference: there basically isn't one. Both give us a proper managed PostgreSQL database with automatic backups, and rock-solid storage for the scan images. Same capability, same safety.

Why it matters for us: this is the fix — no more risk of losing everything. It's delivered equally well on either cloud, so it shouldn't drive the choice.

AWS
How it works RDS for PostgreSQL (the database, with backups & failover) + S3 for the scan photos — the most widely used storage on the internet.
Azure
How it works Azure Database for PostgreSQL + Blob Storage for the photos. Feature-for-feature equivalent to the AWS pair.

Deep dive · running it day to day

Knowing when it breaks, and fixing it safely

The plain difference: both give us live dashboards, alerts to our phones, and a safe "one-button" way to ship updates with an undo. AWS pairs CloudWatch with CodePipeline; Azure pairs Azure Monitor with Azure DevOps.

Why it matters for us: this is the "get told the moment it breaks, and never push a broken update" part. Again — equivalent on both.

AWS
How it works CloudWatch for dashboards & alarms, CodePipeline for automatic deploys with rollback. Deep, mature, lots of knobs.
Azure
How it works Azure Monitor + Application Insights (nice, friendly dashboards) and DevOps deploy slots for instant, safe swap-and-rollback.

Deep dive · are we locked in?

Can we change our mind later?

The plain difference: if we build on open, standard pieces — containers, PostgreSQL, a normal job queue — most of the app can move to the other cloud later without a rewrite. The lock-in risk is real but small, and the same on both.

Why it matters for us: we shouldn't "marry" a cloud. The plan is to keep the design portable so this choice isn't a one-way door.

AWS
The practical angle The biggest ecosystem, the easiest to hire for and get help with, and the cheapest heavy-AI (GPU) power — which is our biggest workload.
Azure
The practical angle Tightest fit if our own team already works in the Microsoft world. Our users being non-Microsoft removes the usual Azure advantage.

5 · The one big cost decision

Where the AI runs

The AI scan needs a powerful, expensive processor (a GPU), and it's bursty — busy when technicians scan, idle otherwise. How we handle that drives most of the monthly cost, on either cloud.

Our recommendation: a "wake-up-when-needed" setup — the AI powers up to process a scan, then shuts down when idle, so we only pay while actually scanning. Start on ordinary processors if volume is small.

AWS
How it runs SageMaker or GPU containers, fed by a job queue (SQS). Widest choice of GPU types and often the cheapest — AWS's strong suit.
Azure
How it runs Azure ML or GPU Container Apps, fed by a queue (Service Bus). Fully capable; a slightly narrower GPU menu than AWS.

6 · How we move

In stages —
nothing goes down

The migration is the same shape on either cloud. We move one piece at a time, running old and new side by side, and only switch over when each piece is proven.

Run beside the old server; switch traffic only when green.

8 · How to choose

A simple rule for the decision

Our product is AI / computer-vision heavy (GPU) — which is exactly RackTrack
→ AWS
Our users sign in with company accounts, not Microsoft / Google
→ identity is neutral
Our own dev team already knows one cloud well
→ that one
Backups, monitoring, scaling, safe deploys
→ both, equally

The honest truth: the capability gap is small and mostly identical either way. The one factor that actually leans it is our AI/GPU workload, which favours AWS — the Microsoft-identity angle simply doesn't apply, because our users aren't Microsoft accounts.

9 · Our recommendation

Lean AWS — we're an AI-first product

For RackTrack specifically, AWS is the more natural fit. Our heaviest, most expensive workload is the AI computer-vision scanning — and AWS leads on GPU choice, GPU cost, and mature machine-learning tooling. The reason teams often lean Azure, native "Sign in with Microsoft," doesn't apply to us: our users are datacenter technicians on company-issued accounts, not Microsoft or Google users. Azure stays a fully valid alternative — mainly if our own team already lives in the Microsoft world.

Recommendation: start on AWS, keep the design cloud-neutral so nothing locks us in. Either way, the winning move is to decide and begin.

10 · What we need

One decision, then we start

The plan is ready and the same shape either way. All we need from this room is a direction — AWS or Azure — and the go-ahead to begin Stage A. The first stage is low-risk foundation work; the app keeps running throughout.

The ask: pick a cloud, and approve starting the migration with Stage A (Foundation).
