1 / Where we stand

Strong code.
Weak setup.

RackTrack is a well-built car that hasn't been insured or fitted with alarms. The engineering is sound. The things that let you rely on it every day aren't in place.

The code
  • Clean and error free, held to published standards
  • 240 tests, all passing
  • Every screen works on a phone
  • No open security issues
  • No secrets anywhere in the code
The setup
  • No backups. One disk failure loses everything
  • No alerts. We'd hear it from a tester
  • No company login. Blocks corporate buyers
  • One server, updated by hand, no undo
  • Never load tested. Capacity unknown

3 / The verdict

Code: proven.
Setup: not yet.

Enterprise level isn't about cleaner code. We've just proven the code. It's about whether a large organisation can safely depend on us. Is the data backed up. Does someone get alerted when it breaks. Can a departing employee be locked out.

Today those answers are no. That's a stage we're at, not a flaw in what we built.

The gap

Three
blockers.

Fix these and we cross from demo to dependable.

These exist because we built RackTrack to prove an idea and get it to testers. For that, one simple server was the right call.
1BackupsEverything sits on one server with no second copy. If that disk fails, every customer scan and account is gone permanently.
2MonitoringIf it goes down at 2am, we find out when a tester complains the next morning.
3Company loginStaff need to sign in through their own organisation's system, so IT can cut off access when someone leaves. Without it, many companies aren't permitted to buy.

in order.

The first move

The cloud fixes
two of three.

Moving off one server onto AWS or Azure gives us the real database, the automatic backups, and the monitoring in one piece of work. It isn't a separate project. It is how we close those gaps.

This removes the scariest risk we have. Right now one dead hard drive could erase everything, permanently.
·A real databasesaves a scan and its owner as one action, so a crash can't half save it
·Automatic nightly backupsstored away from the server
·A tested restoreproof we can actually bring the data back
·Alerts and safe deployswe know within a minute, and can undo

6 · Explicitly out of scope

Stated so the boundary of this audit is not mistaken for a broader assurance. Code auditing does not validate scanning accuracy, device detection, rack-unit correctness, or CMDB reconciliation. Those depend on functional and machine-learning evaluation against known-correct data, a separate exercise, tracked as the AI accuracy report, which requires a live environment to run meaningfully.

Equally, code auditing cannot assess operational readiness, backups, monitoring, disaster recovery, which are matters of infrastructure rather than source code, and are tracked on the enterprise-readiness roadmap.

Conclusion. Nine audit types were performed across every layer of the system using seventeen tools. Six findings were identified and all six resolved. No issues remain open. Critically, every check is now enforced automatically on each code change, so this report describes a maintained standard rather than a moment in time.
