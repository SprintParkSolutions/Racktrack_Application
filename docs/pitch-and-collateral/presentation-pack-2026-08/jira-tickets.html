TASK 1Complete code audit of RackTrack
Title
Complete code audit of RackTrack across all layers
Description
Audit the whole RackTrack codebase against recognised industry standards, so we can say with evidence whether the code is production and enterprise ready rather than relying on judgement. Scope: our own source code (React app, Node API, Python AI pipeline), the third party libraries we depend on, the container we ship in, the full git history, and the running application. Deliverables: - Nine audit types executed using industry standard tooling - Every finding triaged, with false positives confirmed by hand - All genuine findings fixed - Checks wired into CI so the position is maintained, not a one off - A written audit report with the raw tool output as evidence Definition of done: all audits pass, no findings left open, and the checks run automatically on every code change.
Comment
Finished this. Ran nine types of audit using seventeen tools, covering our code, our dependencies, the container, the git history and the running app. Everything came back clean. Zero code errors, zero real security findings, zero leaked secrets, all 240 tests passing and all 13 screens working. The scanners did raise some alarms and I went through every one by hand, they were all false positives. It found six genuine issues and I've fixed all six. None were critical or high severity. I'd rather report six found and six fixed than claim it found nothing, because an audit that finds nothing usually means it wasn't looking hard enough. The important part is that all these checks now run automatically on every change, so this isn't a snapshot of one good day. Full report attached.

SUBTASK 1.2Application security scan (SAST)
Description
Scan our own source for the classic attack routes: database injection, file path manipulation and unsafe command execution, measured against the OWASP risk list. Use two engines deliberately, since pattern matching and data flow analysis catch different classes of problem.
Comment
Done with Semgrep and CodeQL. I used two on purpose because they work differently, one matches known bad patterns and the other traces how untrusted data moves through the code. They raised alarms and I checked every single one by hand. All false positives, mostly log messages the tool mistook for database queries, and file paths that are already protected by strict ID validation and an ownership check. No real holes.
Your notes
SUBTASK 1.3Python security scan
Description
Scan the Python AI pipeline specifically for insecure patterns: weak cryptography, unsafe subprocess calls and unvalidated input handling. Review and document any exemptions rather than silently disabling rules.
Comment
Done with Bandit. Clean at medium severity and above. Three categories were flagged and I reviewed each one individually. SHA-1 is only used to name cache files and never for security, model loading only ever reads our own files, and two outbound calls lack an explicit timeout. All three are documented in pyproject.toml with the reason, so anything new in those categories still gets caught.

SUBTASK 1.6Container audit and SBOM
Description
Scan the container image we deploy for operating system level vulnerabilities, which are separate from our own code. Review how the application runs inside the container. Generate a software bill of materials listing every component we ship.
Comment
Done with Trivy, and this one turned up a genuine finding. The app was running as root inside the container, meaning full administrative rights. If anyone ever got in, that gives them maximum reach. TASK 2Cloud migration research: AWS vs Azure
Title
Cloud migration research and platform recommendation (AWS vs Azure)
Description
RackTrack currently runs on a single hand managed server with no backups, no monitoring and no ability to scale. Research moving to a managed cloud platform and produce a recommendation the team can decide on. Evaluate AWS and Azure across the areas that matter to our product rather than on feature lists: hosting, data and backups, the AI and GPU workload, identity, monitoring and deployment, and cost. Also consider alternatives beyond the two main providers. Deliverables: - Area by area comparison with an assessment for each - Honest account of where each platform genuinely leads - Alternatives considered, including staying where we are - A clear recommendation with the reasoning, and the conditions that would change it - A comparison report suitable for presenting to the team Definition of done: a documented recommendation the team can make a decision from.
Comment
Research done and the comparison report is attached. Short version, they're both genuinely strong platforms. I compared nine areas, each leads in three and three are tied, so this isn't a case of one being better than the other. It comes down to fit. My recommendation is AWS, for one main reason. The heaviest and most expensive thing we do is the AI scanning, which needs GPUs, and AWS has the widest choice, the best pricing and the most mature AI tooling. That's where our money will actually go. Azure leads on hybrid deployment, compliance breadth and identity. I've been clear about that in the report rather than glossing over it. The reason those don't decide it is that our users are datacenter technicians signing in with their own employer's accounts, not Microsoft accounts, and we're building a hosted service rather than shipping into customer datacenters. I've flagged three things that would change my answer, and one needs a product decision rather than an engineering one, whether customers will want RackTrack running on their own hardware. If that's likely, Azure becomes the stronger choice.

SUBTASK 2.1Compare AWS and Azure across everything that matters to us
Description
First establish what the move actually has to solve, based on the risks in our current single server setup, so the comparison is grounded in our needs rather than a generic feature checklist. The four problems to fix: no backups, a single point of failure, no way to scale under load, and updates copied by hand with no undo. Then compare AWS and Azure against those needs across every relevant area: - Hosting and running the application - The database, scan image storage and automatic backups - The AI and GPU workload, including how each handles a bursty pattern that is busy during shifts and idle otherwise - Company sign in and identity - Monitoring, alerting and safe deployment - Running cost For each area, record which platform leads or whether they are genuinely tied, judged on what RackTrack would actually use rather than on feature lists.
Comment
Compared across nine areas. Each platform leads in three and three come out tied, so this genuinely isn't a case of one being better than the other. Hosting and data are even. AWS Fargate is more battle tested, Azure Container Apps is quicker to stand up. For data, RDS PostgreSQL plus S3 versus Azure Database for PostgreSQL plus Blob Storage are equivalent feature for feature. Good news really, since the single most important fix we need is solved equally well either way. The AI and GPU workload is where they actually differ, and it's our biggest cost. AWS has the wider GPU choice, better pricing and more mature tooling in SageMaker. Azure is fully capable through Azure ML and is excellent if you build on Microsoft AI services, but we don't, so that strength isn't one we'd use. Our scanning is also bursty, so the design I'd recommend has GPUs wake for a scan and shut down when idle, meaning we only pay while scanning. On identity, credit where it's due, Microsoft Entra is genuinely the better of the two. If our users signed in with Microsoft accounts that alone might decide this. They don't, they're datacenter technicians using accounts their own employer issues, so we'd never draw on it. Monitoring is close, Azure's dashboards are friendlier out of the box while AWS gives deeper control once you know it, which is a comfort difference rather than a capability one. Cost is level pegging and both offer startup credits. Those figures are research estimates rather than quotes, and I'd want a proper costing before we commit.

SUBTASK 2.2Consider the alternatives, and what would change the answer
Description
Make sure the decision isn't artificially narrowed to two providers. Evaluate the realistic alternatives: Google Cloud, staying on the current server and simply adding backups, moving to a simpler managed platform, and a hybrid approach that moves only storage and backups. Separately, identify and document the specific conditions under which the recommendation should change, so those can be raised and settled by the team rather than discovered later.
Comment
Looked at four alternatives so we're not pretending it's a two horse race. Google Cloud is genuinely strong for AI work, I left it out mainly because enterprise buyers ask about AWS and Azure by name, not because it's weaker. Staying where we are and just adding backups is the cheapest and fastest option, it fixes the data risk but not the single server problem or scaling. A simpler managed platform would be easier and cheaper to run but gives buyers less of the paperwork they expect. A hybrid, moving only storage and backups, is a reasonable halfway step. My view is still a major cloud, mainly because enterprise buyers ask who hosts us and recognise these names. But if cost or simplicity matters more, the middle two are legitimate choices. Three things would change my recommendation, and I'd rather raise them than have them raised at me. First, if customers will want RackTrack running on their own hardware rather than connecting to our service, Azure is clearly stronger for that and I'd switch. That's a product and sales question I don't have visibility on, so I'd genuinely like the team's read. Second, if we're targeting heavily regulated buyers, Azure's compliance breadth starts to matter more. Third, if our own team is already fluent in Microsoft tooling, familiarity beats any feature comparison. Whichever we pick, I'd build on standard components so most of it could move later. I don't want this to be a one way door.
