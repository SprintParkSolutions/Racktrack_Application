What is genuinely good

These are not opinions. Each one has a tool behind it and a tab on this page showing the output.

  • Nothing is left open. Six problems were found across nine audits. All six are fixed. There is no list of known issues we are living with.
  • The serious security flags were actually read. Not waved through, not counted and summarised - each of the ten opened in the source and checked. That is the difference between a real audit and a screenshot of a green tick.
  • It cannot quietly get worse. Every check runs automatically on every change, and a failure stops the change going in. This is a standard we now hold, not a photograph of one good day.
  • The app is tested as a person meets it, not just in pieces. A robot walks every screen at phone size, because we have been caught before by a build where every test passed and the app was visibly broken.
  • Nothing was silenced to get these results. No line anywhere in the code is marked "ignore this". The three scanner rules we turned off are named on their tab with the reason for each.

The bottom line

If the question is “is the code any good?” - yes, and there is evidence rather than reassurance. It is written to published standards, it is scanned by the same tools a customer's own security team would use, it is tested, and every one of those checks now runs by itself on every change.

If the question is “can a large company depend on this tomorrow?” - not yet, and the reason has almost nothing to do with the code. It is that the product runs on one server, updated by hand, with no backups and nobody being alerted when something breaks. That is fixable, it is well understood, and it is the first thing on the plan.

The useful way to put it: the engineering is sound; the operations around it have not been built yet.

A-01 · quality & standards

Code quality & standards

Why we do this: to show the code is written to a real published standard, not just to our own taste - and to catch the kind of mistake you can spot by reading the code, without ever running it.

Question asked
Is it written to a recognised standard, and free of obvious mistakes?
How
Ruff, ESLint and Prettier check and tidy the code · mypy warns only
Standard used
PEP 8 · PEP 257 · 217 rules
Verdict
0 errors · 1 process finding, fixed

Why this one matters

Not for neatness. Messy code hides bugs, and code written five different ways makes every review slower than it needs to be. It also matters commercially: when a buyer's engineer opens our code, the first thing they decide is whether it looks well kept.

The important word is published. Saying "our code is clean" is an opinion. Saying "it meets PEP 8 and PEP 257, and here is what the tool printed" is a fact somebody else can check.

How the checks work

  • A linter reads every line without running it, and points at anything wrong or odd - a value that is set and never used, a reference to something that does not exist, a function called the wrong way.
  • A formatter does not ask anyone's opinion. It rewrites spacing, line breaks and quote marks to one fixed style. Nobody argues about layout, and every change then shows real edits instead of moved spaces.
  • A type checker confirms that something declared to be a number is never handed a piece of text.

On the Python side, 217 separate rules are switched on. They cover layout, documentation, the order things are listed in, up-to-date syntax, likely bugs, and security.

The finding

CA-06ProcessFIXED The Python AI code was held to no enforced standard

The AI pipeline had tests, but nothing checking how it was written - no formatter, no linter, no type checker, no security scanner. We could say the code followed the standard. Nothing was actually making it, and over time it had slipped.

Fixed: Ruff, mypy and Bandit were added to the automatic checks. The first run tidied 35 files and corrected 173 problems. Python code can no longer go in without meeting the standard.

Where we deliberately went easy - and why

We switched the rules on sensibly rather than all at once. A group of noisy rules about older code - mostly missing notes and old-fashioned naming - is turned off for now. Switching everything on together would have meant one huge change nobody could review.

Every rule we left off is written down in pyproject.toml with the reason next to it, as a to-do. The rules only ever get stricter. Nothing is quietly dropped.

Python - lint and format

ruff check pipeline All checks passed! ruff format --check pipeline 38 files already formatted

217 rules switched on across 38 files. Nothing broke a rule, and every file already matched the required layout - nothing needed rewriting when we audited it.

JavaScript - lint

npm --prefix client run lint ✖ 564 problems (0 errors, 564 warnings) npm --prefix server run lint 0 errors

Read this honestly. 564 warnings is a real number and we are not hiding it. Warnings are notes, not faults - something imported but never used, a missing item in a list. They stop nothing, and none of them is a bug. Errors are what stop a build, and there are none. Bringing the warning count down is ordinary tidying up: on the list, not urgent.

Type checking - warns only

This one is not clean, and it is not meant to be yet. The pipeline was written without labelling what kind of value each thing holds, so the checker has plenty to say - 61 complaints across 19 of 33 files. It only warns: reported every time, but it never stops the build. Making it a hard rule today would stop all work until the whole engine was labelled up. It is being tightened one file at a time, and this number is how we track progress.

A-02 · quality & standards

Accessibility

Why we do this: to make sure the app can be used by someone who cannot see the screen, or cannot use a mouse. Big organisations ask about this before they buy - and it decides whether the app works for everyone it is meant for.

Question asked
Can a screen-reader or keyboard-only user actually operate it?
How
eslint-plugin-jsx-a11y, run over every screen's markup
How much
all client screens
Verdict
4 issues found · 4 fixed

Why this one matters

Two reasons, and the money one is not the interesting one. Large companies and public bodies usually ask about this before they buy, so having an answer is worth money.

The better reason is who uses RackTrack: technicians standing in a cold aisle, holding a phone one-handed, often in poor light, sometimes wearing gloves. Most of this work makes the app better for them too - bigger buttons, clearer labels, and nothing that needs a precise tap.

What the checker looks for

  • Is every box properly labelled? Not a label that just sits near the box - a label actually joined to it, so a screen reader can say what the box is for.
  • Does every picture have a useful description? And is it genuinely useful, rather than repeating something already read out.
  • Can everything be reached with a keyboard? Anything you can click has to be reachable by pressing Tab, and usable by pressing a key.
  • Do our own custom controls say what they are? A dropdown we built ourselves has to announce that it is a dropdown, or it is read out as meaningless text.

The findings

Four real problems - more than any other audit here found. That is normal, because these are exactly the mistakes that look completely fine on screen.

CA-03MediumFIXED Three form labels were not connected to their fields

On screen these forms looked perfect - label above, box below. But the label and the box were never actually joined together in the code. To a screen reader that is three boxes with no names: the user is told to type into "edit text" and left to guess what it wants.

Fixed: two labels joined to their boxes, and one custom dropdown given a proper spoken name.

CA-04LowFIXED An image description repeated itself

One picture had a description that repeated something the screen reader already says by itself, so it was read out twice.

Fixed: description corrected.

Where it runs

npm --prefix client run lint # jsx-a11y rules run inside the standard lint pass 0 errors (564 style warnings, none accessibility)

These rules are not a separate job. They run inside the normal lint that already checks every change, so a new problem is caught the day it is written rather than at the next audit.

Findings by type

What this audit cannot tell you - important

An automatic checker finds the mechanical faults: a missing label, a button you cannot reach, a bad description. It cannot tell you whether the app makes sense when used with a screen reader - whether things are read out in a sensible order, whether you are told when something goes wrong, whether a rack diagram means anything at all if you cannot see it.

That needs a person testing it properly, and that has not been done. It is the honest reason this page says "the automatic checks are clean" and not "the app is accessible". Those are two different claims, and only the first one is backed up here.

A-03 · security

Application security

Why we do this: to read our own code the way an attacker would and find any way in - and then look at every single thing the scanners flag, instead of just quoting a headline number.

Question asked
Is there a route into our own code an attacker could use?
How
Semgrep (pattern) + CodeQL (data-flow) - two engines, different blind spots
What the tool said
39 flagged · 388 rules · 463 files
Verdict

Every high-severity finding, opened and read

Semgrep flags 39 things. Calling that “zero” without explaining would be exactly the kind of summary this audit exists to avoid. So all ten of the most serious ones were opened and checked against the actual code. Here is the verdict on each, and why.

RulenLocationAssessment
tainted-sql-string4server/app.jsThese are not database queries at all. They are lines that write to the log. The scanner got these wrong.
tainted-sql-string2server/auth.jsPuts a list of ID numbers into the query. Those numbers come out of our own database, never from a user. The code even says so in a comment.
tainted-sql-string2server/marketplace_routes.jsBuilds part of the query from column names written into our own code. Anything a user sends is passed separately as data, never as part of the query itself. A caller can only pick from our fixed list of columns.
gcm-no-tag-length1server/lib/ssh-creds.jsThe encryption is done correctly, and it is checked properly when unscrambled. The rule wants one extra setting spelled out; the code is safe without it.
detect-child-process1server/worker-pool.jsStarts our own Python program. The command and its inputs are passed separately, so nothing can be smuggled in - the safe way to do it. The rule fires just because the call exists, not because anything is wrong.

Every row above was checked by opening the file and reading the code around it, not by taking the tool's word for it either way.

What the scanners hunt for

  • Injection - someone types database commands into an ordinary form box, and our code runs them instead of treating them as plain text.
  • Escaping the folder - a specially built filename that gets out of the folder it was meant to stay in and reaches other files on the server.
  • Unsafe display - text a user typed is put into a page and treated as instructions rather than as words.
  • Unsafe calls - handing something a user controls to a part of the system powerful enough to do real damage.

Two engines, on purpose

  • Semgrep looks for shapes. It knows what dangerous code looks like and searches for that. It is fast, so it runs on every change, checking against the industry list of the ten most common web attacks plus rules written for the exact tools we build on.
  • CodeQL follows the data. It builds a searchable map of the whole program, then follows information from the moment it arrives from a user to wherever it ends up. That catches problems that build up over several steps, where something is harmless when it arrives and dangerous a few steps later.

They are built differently, so they miss different things. Running both costs us a few minutes of build time; missing something costs a lot more. CodeQL also runs again every week on code that has not changed, so a new check published next month gets applied to code written last year, without anyone having to remember.

Being straight about the number

The short version of the table above: an attacker could not use any of them. Four are log messages the scanner mistook for database queries. Two put ID numbers from our own database into a query. Two build a list of column names that are written into our own code, with everything a user sends passed separately as data. The last two are correct encryption and a correctly written program call that the rules flag on sight.

The one thing we have not checked one by one

Of the 29 less serious warnings, 17 are about how the server handles file paths - the "escaping the folder" risk above. Three more are the cache-filename use explained under A-04, and the rest are one-offs.

Those 17 have not each been opened and followed through the way the ten serious ones were. They are warnings rather than errors, and CodeQL - which is the better tool for exactly this question - finds nothing wrong on those paths. But calling them cleared would be wrong. The honest words are not yet checked one by one. It is the one piece of work still open on this tab.

The finding

CA-02LowFIXED Text in a generated report was not escaped before display

One printable report put an internal error message straight into the page without cleaning it up first. If that message ever contained characters a browser reads as instructions rather than words, the page would follow them.

Rated low, and fairly so: the only person who can see that report is its owner, and the message comes from our own system rather than from anything a user types. It is a bad habit in a spot where the damage would be tiny - but the same habit somewhere else is how real break-ins start, which is why it was fixed rather than just noted.

Fixed: the text now goes through the same cleaning step that every other value in that report already used.

Python security

Why we do this: to check the AI scanning engine against the mistakes that are specific to Python - the ones a general scanner is not looking for.

Question asked

How

Verdict

Why a Python-specific scanner

The scanning engine - the part that reads a photo of a rack and works out what is in it - is written in Python, and it is the most valuable code we own. The general scanners in A-03 cover it, but Python has its own well-known ways to get into trouble that a tool covering many languages will not look for.

What it checks

  • Weak or out-of-date encryption - a method that was fine years ago and can now be broken.
  • Building a system command out of text - if any part of that text came from outside, an attacker gets to choose what the server runs.
  • Opening a file that can run code as it loads - several common file types carry instructions, not just data.
  • Hiding errors - a failure nobody is told about is a failure nobody fixes.
  • Unsafe temporary files, weak random numbers, files left readable by anyone - the quiet ones.

Reading the result honestly

The headline is nothing found at medium seriousness or above, which is the line the build checks against. Below that line the scanner also noted 29 minor things, and it was confident about all of them. They are shown opposite rather than left out.

Minor hits like these are almost always small things, such as deliberately ignoring an error we do not care about, or a check used inside a test helper. Worth knowing about, not worth stopping a build over - which is exactly why the line is drawn where it is.

A-05 · security

Secret scanning

Why we do this: to be sure no password or key has ever been saved into the code. Deleting a password from a file does not remove it from the history - and a leaked password is the easiest possible way to lose everything.

Question asked
Has a key ever been saved into the code, at any point in the project's life?
How
Gitleaks over the complete history, plus a pre-commit check
How far back
every save ever made
Verdict
0 leaks · stops the build

Why this one is different from the others

This is the audit most people underrate, so it is worth explaining properly.

Our code lives in Git, and Git keeps every version of every file ever saved. That is the point of it - you can go back and see exactly what the code looked like on any day in its life.

It also means that if someone saves a password on Monday and deletes it on Tuesday, the password is still sitting there in Monday's version, readable by anyone who has a copy of the project. Today's files look spotless. The history does not. Getting rid of it properly means rewriting that history - and you cannot rewrite what you have not found.

So the only check worth doing is one that reads every save ever made. That is what this is.

How it runs, at two points

  • In the automatic checks: the full history is downloaded on purpose - not just today's version - and every save is scanned. This one stops the build, because a leaked password costs far more than a failed build does.
  • On the developer's own machine: the same tool checks the work before it is even saved. In the normal case the password never reaches the history at all, which is far better than finding it later.

The honest history of this control

The settings file for secret scanning sat in this project for a long time with nothing actually running it. So it caught none of the passwords that got out earlier in the project's life. Hooking it up was part of this audit, and the full history was scanned properly afterwards.

Related tidying done at the same time: the tester account list was taken out of the project entirely, so that file cannot become tomorrow's leak.

Where this result comes from

Gitleaks runs as part of the automatic checks, with the full history downloaded. It is not installed on the development machine, so this tab points at that run instead of showing a terminal - and says so, rather than showing output we did not produce.

A-06 · supply chain

Dependencies

Why we do this: to stay ahead of security holes in code we did not write. When a hole is found in a public library, it is announced publicly - so attackers hear about it the same day we could. The only question that matters is whether we find out.

Question asked
Do any borrowed libraries have publicly known security holes?
How
pip-audit and npm audit check our libraries against the public list of known holes; Dependabot watches all the time
Areas watched
5 - app, server, tests, Python, build
Verdict
no known holes

The trade we have made

Every modern app is built on hundreds of free, shared libraries - for handling images, talking to databases, drawing screens. Nobody writes all that from scratch, and nobody should.

The trade-off is that we are now responsible for code we did not write. When a hole is found in one of those libraries, it gets published on a public list. That is right and necessary - it is also how the hole becomes common knowledge.

How the three tools divide the work

  • pip-audit checks our Python libraries against the public list on every change, and stops the build if it finds a known problem with no patch applied.
  • npm audit does the same for the JavaScript side.
  • Dependabot is the one that works while nobody is looking. It watches all the time and prepares the update for us the day a security fix is published - the fix arrives ready to go. It also does a routine weekly pass for ordinary updates.

It is set up for all five parts of the project: the phone app, the server, the browser tests, the Python engine, and the build system itself. That last one matters, because if the build gets taken over it can do anything the build can do.

Why this one can never be finished

Unlike the others, this result is only about today. A library that is clean this morning can have a serious hole published this afternoon, without us doing anything at all. Nothing in our code changes, but the answer does.

That is exactly why the answer here is an automatic check rather than a certificate. A one-off check is close to worthless two weeks later. A check on every change, plus something that prepares the fix the day it exists, is the real protection.

What a container actually is

It is how modern software is shipped: everything the app needs packed into one box that behaves the same on any machine. Inside that box sits a small operating system with its own parts - and its own security holes, which have nothing to do with our code and everything to do with our risk.

How the check works

  • It builds the real thing. The check makes the actual box we ship - not a copy, not a description - and scans that.
  • It fails the build on anything critical that has a fix available. Problems with no fix yet are reported instead of blocking, because there is nothing anyone could do about them today.
  • It publishes an ingredients list. Every build writes out a list naming every part inside the box, in a standard format. Big buyers increasingly ask for one - and it means that when the next big security scare hits the news, we can answer "are you affected?" in minutes rather than days.

The finding

CA-01MediumFIXED The app ran as root - the unrestricted administrator account

Inside its box, the app ran with full administrator rights. On its own that is not a way in, and nothing had gone wrong because of it. What it changes is how bad it would be if anyone ever did get in some other way: they would arrive already holding every permission there is.

The plain version: it is the difference between a burglar reaching the hallway and a burglar being handed the keys to every room in the building.

Fixed: the box now switches to a limited account before the app starts. If something is ever broken into, it can only reach what the app genuinely needs to do its job.

The scan of the operating system parts themselves came back clean.

Where this result comes from

Run in the build, not on a laptop

Trivy builds and scans the box as part of the automatic checks. It is not installed on the development machine, so this tab points at that run instead of showing a terminal - and says so, rather than showing output we did not produce.

Why the ingredients list is worth having

It is the difference between a straight answer and a scramble. When a big security problem hits a common library, the question every customer asks that afternoon is "are you affected?" With an ingredients list written on every build, that is a quick look-up. Without one, it is days of work and an awkward silence in the meantime.

Why the distinction matters

Each library comes with a licence - the terms you accept by building on it. Most ask for essentially nothing. A small number come with real strings attached, and can require anyone who hands the software on to publish their own source code too.

For a product we mean to sell, that is not a small detail. It is also a standard question when a big company is deciding whether to buy: what licences are in your product, and what do they make you do? We should be able to answer without a scramble.

The single LGPL component

It is the image-handling library we use for photos - no surprise, given what RackTrack does.

It is fine for the way we use it, because we call the library from the outside rather than changing it or building it into our own program. That difference is exactly what this licence hangs on. It is not a problem to solve. It is something we should be able to answer clearly if a lawyer asks - which is why it is written down here rather than left for someone else to discover.

The finding

CA-05ComplianceFIXED Our own three packages declared no licence at all

The licence field on all three of our own packages was empty. To any checking tool - ours, or a possible buyer's - an empty field does not mean "ours, private". It means unknown, which is a worse answer than a strict one, because nobody can tell what they are allowed to do.

Fixed: all three are now clearly marked as ours and private. A scan of our product now states our position instead of raising a question.

Part one - the automatic tests

Each test runs a real piece of the code with a known input, and checks the answer against what it should be. If someone changes the code and the answer changes, the test fails and says what broke.

  • 101 on the AI pipeline - port numbering, making patch-panel counts add up, loading settings, matching device models.
  • 86 on the server - the connections to the app, permissions, handling data, and telling one kind of failure from another.
  • 55 on the phone app - safe links, checking uploaded photos and video, saving things locally, vendor login links, profile pictures.

The pipeline tests deliberately cover the parts that need no graphics card and no trained model - the shapes, the look-ups, the arithmetic. That is what lets all 101 run anywhere, on every change, in about two seconds. The heavy AI work is checked separately, on a real machine.

Part two - the browser sweep

A robot opens a real browser, signs in as an owner, and walks all 13 screens at phone size. All the data is faked inside the browser, so it needs no server, no database and no internet - just the finished app, which is exactly what we ship.

Why the sweep exists - a true story

The build, the lint and over 200 tests all passed, green across the board, while every icon in the product was showing as its own name in plain text - "logout", "edit", "dns" scattered across every screen. Every test was perfectly happy. To anyone who opened the app, it was completely broken.

That is the gap ordinary tests cannot close: they check the pieces, not the finished app as a person actually meets it. The sweep is the check that would have caught it, which is exactly why it was built. It spots that particular failure by shape - a real icon is roughly square, whereas the word "logout" is several times wider than it is tall.

What it still does not prove

That the AI is right. These tests prove the app runs, the screens work and the logic behaves. They say nothing about whether RackTrack looks at a photo of a rack and picks out the right devices in the right positions. That is a separate job - real photos with known-correct answers, scored for accuracy - and it needs a real machine to mean anything.
