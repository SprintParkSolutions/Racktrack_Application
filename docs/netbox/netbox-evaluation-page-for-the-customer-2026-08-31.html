The pipeline you asked to see

Camera scan, device and port recognition, read the switches over SNMP and LLDP, reconcile the two with a person confirming the match, then write to NetBox. This is the whole flow, end to end.

NetBox integration

Yes, native. RackTrack writes directly to the NetBox REST API. It is idempotent: every object carries a stable id in a custom field, so a re-scan updates records in place instead of duplicating them. Every write is preceded by a Preview that reads NetBox and shows the exact diff first. Tested against NetBox 4.6.9. If the API path is ever blocked, the same data exports as files.

Cables carry both ends. A cable is created only when both terminations resolve to a specific port. A one-ended link is kept as a note, never exported as a cable. Roadmap and honest notes

  • !

Asking the switches

A managed switch can answer questions about itself over the network. The language for this is SNMP. Here it is strictly read-only: the app only asks, it can never change a switch setting. Think of it as the switch reading out its own spec sheet on request.

What a switch can tell us

  • ✓

    What it is

    Its make, model and serial number, straight from the device.

  • ✓

    Its ports

    How many, their names, their speed, and which are live right now.

  • ✓

    Its neighbours

    Using LLDP, where switches announce themselves to each other, it can say "my port 12 connects to that switch's port 24." That is a proven cable, not a guess.

What is missing, and why

  • !

    Model and serial come back blank

    The standard "describe your parts" question (called ENTITY-MIB) is empty on these switches. The model is actually sitting inside the switch's text description, and the serial is only reachable through a brand-specific question the app does not ask yet.

  • !

    Vendor shows as a number

    The two TP-Links currently read as enterprise 11863 instead of "TP-Link". 11863 is TP-Link's registered code; it just needs one fresh read to resolve to the name.

  • !

    Only switch-to-switch cables are found

    LLDP only exists between managed switches. An unmanaged switch or a patch panel cannot announce itself, so those links are not captured this way.

The fix, step by step

  1. Read the model from the description

    When the standard question is empty, take the model out of the text description. This works today: the D-Link already returns "WS6-DGS-1210-52". Files: collect.js, reader.js.

  2. Ask the brand-specific question for the serial

    D-Link and TP-Link each expose the serial under their own code. Pick the right one from the vendor we already know, and ask it. File: collect.js.

  3. Place end devices from the address tables

    Use the switch's MAC and ARP tables (already reachable) to say which computer or server sits behind which port. Files: collect.js, reconcile.js.

Reading the photo

The camera cannot ask anything. It looks. A vision model (trained image recognition) finds each box in the photo, works out which shelf it is on, and draws a box around every port.

A rack is divided into numbered slots called U (rack units), counted from the bottom. "U10" means the tenth slot up. That is how a device's position is recorded.

What the photo gives us

  • ✓

    Where every device sits

    All 11 identified devices placed from U18 down to U1, including patch panels that span two slots. Unrecognised boxes are not shown.

  • ✓

    Every port, boxed and separated

    The port count on the table always matches the boxes drawn, and no two boxes overlap.

  • ✓

    The brand from the label

    Where the logo is legible, it reads the make: D-Link, TP-Link.

What is missing, and why

  • !

    The model number cannot be read

    In a photo of the whole rack, each device is only about 116 pixels tall. That is enough to read a big logo, but not the small model number printed beside it.

  • !

    The serial cannot be read

    The serial is on a small sticker, usually as a barcode. Same problem: too small in a wide shot.

  • !

    Ports under cables are missed

    Cables physically cover ports on the busy switches. The camera cannot box a port it cannot see.

Why a "52-port" switch showed 56 sockets

This one is not a bug, and it is worth understanding. The D-Link is a "52-port" switch, but you can count 56 sockets on it. Both are right, because of combo ports.

The camera counts sockets, so it reads 56. The switch counts port numbers, so it reports 52. When the two are merged, the switch's 52 logical ports are what goes to NetBox, with the 4 combo ports noted.

The fix, step by step

  1. Take a close-up of each device

    A second, closer photo of each faceplate, where the model number is big enough to read. Feeds the same recognition.

  2. Read the serial barcode

    Decode the barcode on the serial sticker directly, and use a stronger text reader for the model. Then a device with no network access still gets an exact model and serial.

  3. Model the patch panels fully

    Pair each front port with its rear port so a cable can be traced all the way through the panel, not just to its front.
