Is the field mapping right?

The NetBox research is good. The sheet is built the wrong way round, so half the objects are missing.

18 September 2026 · 489 field rows checked · NetBox claims checked against netbox-4.6.10-openapi.json · CMDB claims checked against the tables our own code writes
What is right, and should be kept

The NetBox column is complete. For all 8 object types it covers it lists every field NetBox has, with the right API name. Of 261 names, 254 are exactly correct. Cable, IP Address, Subnet, VLAN and VRF are perfect. That is the expensive part and it does not need redoing.

Also correct, and I expected it to be wrong: rack_units for rack height. Our own seed script uses that exact field.

The problems, in order

  1. It covers 8 object types. RackTrack makes 16. Missing Nine kinds of object have no table at all.
  2. Patch panels are missing completely. Missing Front ports and rear ports. This is how a cable is traced through a panel, and it is the one thing no network scan can ever find on its own. It is one of our strongest selling points and it is not in the sheet.
  3. Power ports and power outlets are missing. Missing What a device draws power through, and the PDU socket it draws from.
  4. Manufacturer, device type, device role, site and location are missing. Missing The sheet treats these as columns on a rack or device, written as "via Rack Type". In NetBox they are separate objects that must be created first, in order. An engineer working from this sheet would not know they exist.
  5. Seven NetBox fields do not exist. Wrong cooling_capability, cooling_capacity, cooling_method, cooling_intake_count, cooling_outflow_count, channels, channel_id. None of them appear anywhere in NetBox 4.6.10, which is the version we run.
  6. Two model number rows point at nothing. Wrong rack_model_number and device_model_number say "via Rack Type" and "via Device Type", but a NetBox rack type only has model. A device type has part_number, which is probably what was meant.
  7. It says cables need a paid ServiceNow plugin. They do not. Wrong Every cable row is marked "TNI plugin only". A cable works fine as a relationship row, cmdb_rel_ci with the Connects to type, which is what our code already does. The sheet even uses cmdb_rel_ci to say a rack contains a device, then refuses to use it for a cable. As written this tells a customer we cannot export their cabling without buying a plugin.
  8. Four CMDB tables we write to are missing. Missing cmdb_ci_port for panel ports, cmdb_ci_netgear for the panels, cmdb_ci_server and cmdb_ci_pdu. A port is mapped only to cmdb_ci_network_adapter, which is right for a switch NIC and wrong for a panel port.
  9. Custom fields go to the wrong place. Wrong The sheet sends them to attributes. In ServiceNow a custom value goes in a u_ column. We already write u_racktrack_scan_id and read it back.
  10. Owner is mapped two different ways. Wrong NetBox owner goes to managed_by_group in one table, while owned_by is listed as CMDB-only. Both cannot be right.
  11. VRF gets 19 rows for something we never make. Extra Fully researched, and RackTrack does not produce VRFs and never has.
  12. The names are copies, not decisions. Structure In 431 of the 489 rows, 88 percent, the name is just the object plus whatever the other column already called the field. rack_serial comes from NetBox serial. port_poe_mode comes from poe_mode. So the name column adds nothing.
  13. It quietly proposes RackTrack should hold 400 more fields. Structure Because the names are copied from both systems, the sheet ends up saying a rack has 107 fields, a device 119 and a port 134. That means storing a rack's outer depth, a device's virtual chassis priority, a CI's cost centre. That is a product decision, not something to inherit from a join.
  14. Only 65 of the 489 rows actually map. Structure The other 424 say "this exists in one system and not the other". Useful research, but not a mapping. The last table in the document already knows this, it keeps the 65 and drops the rest.
  15. Nothing of RackTrack's own is in it. Missing No row for the evidence level, the confidence score, the provenance, our stable id, the port fingerprint, or the conflict record. They could never appear, because a name copied from NetBox or ServiceNow can only describe NetBox or ServiceNow. These are the fields a customer asks about in the second meeting.
  16. One sheet is right, but it needs a "How" column. Structure Two sheets would drift apart, so keep one. But the two systems are shaped differently, not just named differently. "This device is in this rack" is a field in NetBox and a relationship row in ServiceNow. That is why the sheet has to write "Related Items (Contains::Contained by)" in a column meant for a field name. Add a column saying direct field, reference, relationship row, custom field, or not supported, and the problem goes away.

What to change

  • Start from RackTrack's 16 objects, not from NetBox's tables. One row per RackTrack field.
  • Add the nine missing object types. Front and rear ports first.
  • Delete the seven fields that do not exist, and change the two model number rows to part_number.
  • Fix the cable row to use cmdb_rel_ci Connects to, and drop the plugin-only claim.
  • Add the four missing CMDB tables.
  • Add a How column for each side.
  • Add the RackTrack-only fields, writing "not supported" honestly where that is the answer.
  • Remove the VRF table, or mark it as future scope.
  • Move the one-sided rows to a second sheet called "fields we do not carry".
