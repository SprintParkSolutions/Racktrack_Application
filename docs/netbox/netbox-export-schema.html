RackTrack · Reference

NetBox export schema

Every object a rack scan writes into NetBox, what it is called on each side, and the order it has to be created in.

16 object types NetBox 4.x Verified against 4.6.9

01

Two things every object carries

NetBox has no native place for either of these, and nothing in the export works without them.

uid → custom_fields.racktrack_uid

Our own stable id for the object, written into a NetBox custom field.

NetBox has no upsert. Without this, re-scanning a rack duplicates every object in it. Instead we look the object up by this field, then create it or patch it.

The custom field is created automatically on first export and widened to cover every object type we write.

evidence → status

What proved this object exists. Never guessed, never invented — if nothing observed it, it is not created.

Confidence is a property of the method, not a feeling. It maps onto NetBox's own connected and planned, so the customer filters for what we were unsure about inside their own tooling.

EvidenceConfidenceWhat it meansBecomes
manual1.00A person looked and typed it.connected
lldp_both1.00Both ends report each other. A proven cable.connected
snmp0.98The device said so about itself, from its own inventory.connected
lldp_one0.90One end reports it, the other is silent.connected
mac_arp0.75MAC table plus ARP. Good enough for end devices.connected
cv_ocr0.60Read off the photograph.planned
cv_only0.50Seen in the photograph, nothing on the network confirms it.planned
conflict0.00The sources disagree. This is a finding for a person, not a fact.never exported

The line is at 0.75. At or above it the object is written as connected; below it, planned. A conflict is held back entirely and reported instead.

02

Creation order

NetBox refuses out-of-order creates: you cannot rack a device whose type does not exist, or cable two ports that were never made. The writer walks exactly this sequence.

1manufacturers 2deviceTypes 3deviceRoles → 4sites 5locations 6racks → 7devices → 8interfaces 9rearPorts 10frontPorts 11powerPorts 12powerOutlets → 13vlans 14prefixes 15ipAddresses → 16cables

The device

The actual physical box in the actual rack. This is where the photograph and the network finally meet.

Device

/api/dcim/devices/

09

The one thing that is never exported

Conflict

not sent to NetBox

Two sources disagreed. This is the most valuable thing the system produces: a disagreement between the camera and the switch usually means somebody repatched a cable and never updated the documentation — the exact problem the customer bought this to find. We surface it and never pick a winner.

subjectUid—which object the disagreement is about
field—which field they disagree on
cvSays—what the photograph said
telemetrySays—what the network said
note—anything that helps a person judge it
10

Traps

Things NetBox accepts without complaint and then does not do. Every one of these was found the hard way.

role vs device_roleDevice role is role in NetBox 4.x. It was device_role in 3.x. Get it wrong and the device is created with no role at all.
rear_portsFrom 4.6, a front port's link to its rear port is the list rear_ports. The old flat rear_port and rear_port_position are ignored silently, and a cable trace then stops dead at the patch panel. Verified against 4.6.9.
mac_addressAn interface MAC is a plain string up to 4.1. From 4.2 MACs became their own object. If the pinned version moves past 4.1, the interface mapping has to be revisited.
'' not nullNetBox wants an empty string for an absent string field. A null is rejected on choice fields such as cable type and length_unit.
u_heightOn a rack, omit the field entirely when the height is unknown. NetBox then applies its own default. An explicit null is rejected.
faceNetBox rejects a face on a device with no position, so the face is sent as an empty string whenever the device is not racked.
asset_tagUnique across the entire install, not per site. Two racks that each have an "01" sticker will collide, so tags are prefixed.
object_typeA cable termination wants dcim.frontport. dcim.front-port fails. The string is carried through verbatim rather than being generated.
no upsertNetBox has no create-or-update. Every write is a lookup by racktrack_uid followed by a create or a patch, which is the only reason re-scanning a rack does not duplicate all of it.

Field names track NetBox 4.x, which the docker-compose pins. The full mapping lives in server/lib/netbox/mapping.js, the object shapes in server/lib/netbox/model.js, and the writer that walks them in server/lib/netbox/writer.js.

The writer holds four rules: every write is idempotent through racktrack_uid; a dry run produces exactly the diff the real push would apply; nothing is ever deleted, only reported; and confidence sets status rather than being discarded.
