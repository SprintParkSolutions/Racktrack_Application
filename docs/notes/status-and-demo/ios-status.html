2

Signed build on TestFlight

What we did
Built & Apple-signed the app, created its store listing, uploaded it, cleared the encryption question, and set up the tester group. Now on build 4.
How it works
The shared web app is wrapped into a native iPhone app, signed with the company’s Apple certificate, and uploaded. TestFlight then delivers it to invited testers.
What we’re using
Apple Developer (SPRINTPARK LLC) · App Store Connect · TestFlight · Transporter · Capacitor build.
Effect
Any invited tester installs RackTrack on a real iPhone with one tap — no cables, no setup.
To keep stable
Each fix needs a new build number + re-upload (normal). The real stability item is the backend address — see #8.
3

Scan is no longer lost when you switch apps

What we did
Previously, leaving the app mid-scan lost the scan and dumped you on the upload screen. Now it reconnects and shows the finished result.
How it works
Each scan gets a hidden ticket the app remembers. The scan still finishes on the Mac even if the phone pauses the app; on return, the app asks the server for that ticket and jumps to the result (“Bringing your scan back…”).
What we’re using
A small job-ticket tracker on the Mac server + resume logic in the app.
Effect
No lost scans and no wasted re-scans — removes a common, frustrating failure.
To keep stable
Stable as-is. A fuller version would be a full background-job queue, but the current fix covers the real-world case.
4

“Load failed” during scans — fixed

What we did
Testers were hitting “load failed” while scanning. We found and fixed the cause.
How it works
The Mac’s dev-runner was set to restart whenever a data file changed. Our new scan feature writes such a file on every scan — so the server restarted mid-scan and dropped the connection. We changed it to restart only on real code changes.
What we’re using
The Mac server (Node) + its file-watcher settings.
Effect
Scans now complete reliably; the connection is no longer dropped mid-scan.
To make stable
Run the backend as a proper always-on service (plain node, not the auto-restart dev runner) — part of the always-on-server step in #8.
5

Back buttons never get stuck

What we did
On some screens the back button could do nothing. Now it always goes somewhere sensible.
How it works
A smart-back helper: if there’s history, go back; if not (e.g. opened fresh), go to a sensible default screen.
What we’re using
In-app navigation logic (applied across the main screens).
Effect
Users never feel trapped on a screen.
To keep stable
Stable — no further work.
6

First-time walkthrough + UI polish

What we did
Added a 4-step intro for new users (scan → review → ports). Made the Ports screen top compact, and the Network screen now says “No switches detected” instead of showing blank.
How it works
The walkthrough shows once per device on first launch (skippable), then never again. The Network screen now has a clear message when nothing is found.
What we’re using
In-app screens + a saved “already seen” flag.
Effect
New testers understand the app instead of guessing; screens never look empty or broken.
To keep stable
Stable — content can be expanded later if we add features.
7

The backend & the temporary tunnel ← the important one

What it is
The app doesn’t do the heavy work itself — it talks to our Mac, which runs the AI and reads the switch, over an internet link.
How it works
The app has a web address baked in. That address points, through a Cloudflare tunnel, to the Mac’s server. The server runs the AI and reads the switch (read-only).
What we’re using
Mac server (Node) · a temporary Cloudflare tunnel · the TP-Link switch.
Effect
Works well while the Mac + server + tunnel are running. But the address is random and changes if the Mac restarts — then every installed app can’t reach the server and we must rebuild & re-upload.
To make permanent & stable
See the plan below — a fixed address + an always-on server.

⚠ To make it permanent & stable

  1. Fixed web address. Point api.racktrack.ai (our GoDaddy domain) to a permanent Cloudflare tunnel. The address then never changes — a Mac restart no longer breaks the apps, and we stop rebuilding just for the address.
  2. Always-on backend. Run the server as a proper service (auto-starts, auto-restarts on crash) instead of the developer runner. This also permanently prevents the “load failed” class of issue.
  3. Move off the Mac (later). Put the backend + AI on a dedicated always-on machine so the app doesn’t depend on this Mac being awake and online at all.
  4. Real-device sign-off. Testers confirm on real iPhones: scan-resume, walkthrough, and scrolling.
