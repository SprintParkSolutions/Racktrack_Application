1Overview & the big picture

This guide documents two network racks the way a careful engineer would: first the physical picture, then every port and its state, then the cables — including the ones that cross between the racks — and finally the power. Everything is shown twice: as a method you can repeat on your own racks, and as a filled-in worked example you can copy and adapt.

The example site is SPP-DC1, a small server room with two adjacent 42U racks standing side by side in Row R. Rack R1 is the distribution rack (it holds the main switch that everything else hangs off). Rack R2 is an access rack for nearby users and devices. Each rack holds two managed switches (one Cisco, one TP-Link), two patch panels (copper and fibre), and a pair of power strips (PDUs). The two racks are joined by a fibre trunk and a couple of copper cross-connects.

What "a port's state" means hereThroughout this guide every port is one of five states, always shown with a colour and a word/icon so it is never colour-only: Up (a device is connected and the link is live), No-link (a cable is plugged in but there is no link), Err (the port faulted itself, e.g. a security violation), Reserved (deliberately shut down, usually no cable), and Free (empty and available).

How this guide is organised

Sections 3–4 answer "what is in the racks and what is every port doing?". Section 5 is the command reference — the exact CLI to type on Cisco and TP-Link and the output to expect. Sections 6–8 answer "where does each cable go?", building from protocol discovery (LLDP/CDP) to a full physical trace, and then to the cables that run between the two racks. Sections 9–11 cover the passive world — labels, patch panels, power — and the tools for tracing a cable you cannot see. Section 12 is a reusable checklist and blank templates.

2Getting admin access — safely

You cannot document what you cannot log into. There are three normal ways onto a managed switch, and a short list of habits that keep an audit from causing an outage.

Three ways in

1. Console (out-of-band). A rollover or USB-C cable from your laptop to the switch's CON port. Always works, even if the network is down. Terminal settings 9600 8-N-1 (Cisco) — TP-Link consoles are usually 38400 8-N-1.

2. SSH (in-band). ssh admin@10.10.0.11 to the switch's management IP over the network. The everyday method once the switch has a management address on VLAN 99.

3. Web GUI (HTTPS). https://10.10.0.12 in a browser. TP-Link switches are often managed this way first; Cisco Catalyst also offers a web UI, but the CLI is faster for auditing.

Golden rule — read firstEvery command in Section 5 is read-only (show…). None of them change anything. Do your whole audit with show commands before you ever type configure terminal. On Cisco, enter privileged mode with enable; the show commands are safe from there.
Safety notes that matter physicallyNever attach a tone generator to a live switch or PoE port (voltage can damage the toner and the port) — see §11. Treat "blink/locate" and "shut/no shut" as change-control actions. If you re-patch anything, update the cable schedule (§9) the same day, or the documentation silently rots.

4Port inventory & status maps

This is the heart of the audit: for every switch, how many ports exist, which are live, which have a cable but no link, which are faulted, which are deliberately off, and which are free. Each switch gets a colour-coded port map plus four or five summary tiles. The maps are built directly from the show interfaces status / show power inline output in §5.

How to read a port cell

7● Up — live link, device connected TT1⇅ Trunk/Uplink — link to another switch 9◍ No-link — cable in, no link 30✕ Err — port faulted/disabled itself 20▢ Reserved — admin shut, usually no cable 16○ Free — empty, available

The small letter in the top-right corner is the port's role, independent of colour: P = PoE power is being delivered, T = trunk/uplink, L = member of a link-aggregation bundle (LAG), M = management. "Cabled / in use" counts any port with a cable in it (Up, Trunk, No-link, or Err). "Free" and "Reserved" are the ports you can hand out to new devices — Free immediately, Reserved after someone confirms why it was shut.

Decode the statesconnected = Up (green in §4). notconnect = no link even though the port is enabled → our No-link/amber (Gi1/0/9). disabled = someone ran shutdown → Reserved/grey (Gi1/0/20). err-disabled = the port shut itself (here a port-security violation on the CCTV port) → Err/red (Gi1/0/30). The a- prefix means auto-negotiated; a gigabit device stuck at a-100/half is the classic bad-cable signature.

LLDP needs feature lldp first; CDP is on by default.

5bCommands & expected outputs — TP-Link

TP-Link JetStream switches (here ASW-B2, and ASW-A2 for PoE) run a Cisco-like CLI, but with enough differences to trip up an auditor. The web GUI (standalone or Omada) reaches the same data — paths are tabled at the end. Everything below is read-only.

Five ways TP-Link differs from Cisco 1. Enter config with configure, not configure terminal.   2. The enable password is often blank by default — just press Enter to reach Switch#.   3. Interfaces are gigabitEthernet 1/0/1 (unit/slot/port) — you must type the media word; int gi1/0/1 shorthand is not accepted.   4. Many show commands need the interface keyword (e.g. show lldp neighbor-information interface gigabitEthernet 1/0/24).   5. 6Neighbour discovery — building the map

Before tracing a single cable by hand, let the switches tell you how they are wired. LLDP (vendor-neutral) and Cisco's CDP make every switch announce who is on the other end of each port. Walk the command on all four switches and you have the whole backbone map — no ladder, no toner.

The method (repeat on every switch)

  1. Run show lldp neighbors (Cisco) / show lldp neighbor-information (TP-Link).
  2. Each line is one edge: local port ↔ remote device + remote port.
  3. Add show cdp neighbors detail on Cisco for neighbour IP, platform and duplex.
  4. Repeat on the neighbour you just found, until you reach the edge (a host).

Two things LLDP will not show

Passive panels. Patch panels and trunks have no chip and no MAC — they are invisible. LLDP reports the two switches as "directly connected" even when two patch panels sit between them. You fill those in from the cable schedule (§9).

Silent hosts. A server or camera only appears if it runs an LLDP agent — most do not. For those, use the MAC address-table (§7).

Trace B — follow a host across three switches (MAC + LLDP)

Goal: where is SRV-B-07 (IP 10.10.10.77) physically, and what is the full path to its gateway? We never leave the keyboard. Each step names the command and what it revealed.

  1. Turn the IP into a MAC. On the gateway CSW-A1: show ip arp | include 10.10.10.77 → MAC 8c16.4522.0207.
  2. Ask the gateway where that MAC is. show mac address-table address 8c16.4522.0207 → VLAN 10 on Te1/1/1 — an uplink (many MACs), so the host is downstream. Follow Te1/1/1.
  3. Te1/1/1 goes where? show lldp neighbors | include Te1/1/1 → ASW-B1 Te1/1/1 (across the inter-rack fibre from Trace A). Hop to ASW-B1.
  4. On ASW-B1: show mac address-table address 8c16.4522.0207 → learned on Gi1/0/23, also an uplink. show lldp neighbors → Gi1/0/23 ↔ ASW-B2 Gi1/0/24. Hop to ASW-B2.

Trace-any-cable recipeProtocol first: LLDP/CDP for switch-to-switch, MAC table for hosts, iterate toward the edge. Physical second: for the passive middle (panels, trunks) read the labels and the cable schedule; if a label is missing, fall back to the toner or the port-blink locate in §11. Validate: on fibre, confirm the Rx light (§5.4) is in range end-to-end.

9Structured cabling & labels

Every trace above only works because the passive world is labelled and recorded. Two things make that possible: a consistent label scheme (so a technician reads the same identifier at both ends and in the record) and a cable schedule (one row per cable). This is the ANSI/TIA-606 discipline, kept deliberately simple.

Reading a label

Our scheme is Rack.U-Device:Port — self-describing, so a label tells you where to stand without opening a database:

Formal TIA-606 (for larger sites)

The standard's horizontal-link format is Floor/Space.Rack-position:Port, e.g. 1A.AD03-40:14 = floor 1, room A, rack grid AD03, panel at U40, port 14. A permanent link is written near-end / far-end: 1A.AD03-40:14 / 1A.AD07-40:14.

Identifier "classes" scale it: Class 1 = one room, Class 2 = one building, Class 3 = campus, Class 4 = multi-site.

Two philosophies — pick one

Self-describing (used here): R1.U39-CSWA1:Te1/1/1. Human-readable, but must be relabelled when re-patched.

Stable cable ID: CBL-A047 — never changes; the meaning lives in the schedule/DCIM. Better for large or frequently-repatched racks. Many sites use both: a stable ID on the jacket, a self-describing label on the port.

TP-Link locate

Standalone JetStream and Omada expose a Locate / LED flash in the UI rather than a per-port CLI beacon: in Omada, Devices › [switch] › ⋯ › Locate flashes the system LED so you can find the chassis in a row.

For the port itself, use the physical link LED: unplug/replug the far end (or toggle it with a tester) and watch which port LED changes.

Safety — do not tone a live portNever attach a tone generator to a switch port, a PoE port, or any cable that may carry voltage — the injected signal (and any PoE voltage) can damage the toner and the port. Toning is for de-energised, disconnected copper only. Unplug the run at both ends first, or use a digital-signature toner rated to reject live-line voltage — and even then, unplug the switch end. Treat beacon, shutdown/no shutdown, and re-patching as change-control actions with a note in the schedule.

12Master checklist & templates

Run the audit in this order on any pair of racks, then fill the two blank templates. Do it once and you have living documentation; repeat quarterly and you catch drift before it becomes an outage.

Audit run-order

  • Access — reach each device read-only (console / SSH / web); record every management IP and how you got in. (§2)
  • Identity — show version · show inventory (Cisco) / show system-info (TP-Link); note model, firmware, serial, optics. (§3, §5)
  • Ports — show interfaces status (+ TP-Link show interface configuration); paint the colour map, tally free vs. cabled. (§4, §5)
  • Neighbours — LLDP on every switch (CDP too on Cisco); build the adjacency table. (§6)
  • Depth — MAC table, optical light (transceiver), PoE, VLAN, LAG, and error counters on each switch. (§5)
  • Trace — walk the key links end-to-end; fill the passive middle from labels + schedule. (§7)
  • Inter-rack — record every run between racks and its spare capacity. (§8)
  • Label & schedule — verify/repair labels; complete the cable schedule. (§9)
  • Power — read PDU load, map outlets, confirm dual-feed balance. (§10)
  • Findings & save — list issues, export/back up configs, store the schedule in a DCIM or shared sheet.
What this worked example surfacedA real audit produces a punch-list. Ours found: Gi1/0/30 err-disabled on CSW-A1 (port-security violation on the CCTV drop — investigate before clearing); Gi1/0/13 climbing FCS/align errors (re-terminate that run); SNMP community "public" on the PDUs (move to SNMPv3); and X-CU-02 physically present but previously undocumented (now recorded as a spare). None are outages today — all are cheap to fix now and expensive to discover later.
