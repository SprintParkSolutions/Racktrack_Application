Why OCR Missed Make and Model
RackTrack · Pipeline diagnosis · 8 September 2026

Why OCR missed make and model

OCR was never slow and never misconfigured. Two separate bugs were throwing away finished work — one of them silently, on every single read, since the repository's first commit. Both are fixed and committed. What remains is not a bug: on a 1U rack slice the model number is printed in the smallest text on the faceplate, and there are not enough pixels of it to read.

One correction to what I told you earlier. I reported a 0.68 s warm label read. That was a cache hit, not a read — re-running the same file now returns in 0.66 s because its result is stored against the image's hash. An honest warm read of a new photo is 7.9 s at 2.6 MP and 13.3 s at 12.2 MP. The fix removed the 8–14 s cold-start that used to be paid on every call, so the real gain is roughly 2×, not 40×. The make/model figures above are unaffected: those were measured on freshly encoded images.
Bug one · fixed in 179b85d

A one-line image shim broke every label read for the life of the repo

The warm worker replaces cv2.imread for the whole process, so that Ultralytics does not route file reads through np.fromfile. Every library loaded beside it inherits that replacement — including easyocr.

The replacement did one thing extra: when a decode came back as a two-dimensional grayscale array it added a third axis, turning (h, w) into (h, w, 1). Nothing in RackTrack's own code reads grayscale that way, so it looked harmless.

easyocr does. It asks for a grayscale read and takes OpenCV's contract literally, unpacking exactly two values. Every label read inside the worker died on that line.

Why it presented as slowness, not failure

The server caught the exception, logged it, and fell back to spawning a fresh Python process per photo — re-importing torch and rebuilding the easyocr reader every time. The answers were correct, so nothing looked broken. They just took 15–27 seconds each.

Because IMREAD_COLOR — the default, and what the Ultralytics callers use — already decodes to three channels, that branch could only ever fire on the grayscale read it broke. The shim now returns exactly what cv2.imread returns.

Bug two · fixed in 791308e

The rack-wide pass did all the reading, then threw it away on its last line

This is the one that actually answers your question. pipeline.ocr_devices.run() is the pass that reads make and model for every device in a rack photo. It built the complete result — sixteen devices, 153 text detections — and then stamped it with datetime.UTC.

datetime.UTC was added in Python 3.11. This pipeline runs on 3.10.0. So the function raised AttributeError on its final statement, after roughly nineteen seconds of real OCR work, and wrote no file. Nothing downstream had anything to sync. Make and model never arrived from a rack scan on this interpreter — not once.

The linter put the crash there, and would do it again

The explanation was already sitting in a comment directly above the crash. Someone diagnosed this, wrote up the fix — and then a ruff --fix reverted the code and left the comment behind as an orphan.

Ruff's target-version said py311 while the runtime is 3.10, so pyupgrade's UP017 rewrites datetime.timezone.utc into datetime.UTC on sight. Worse, ruff check in CI fails the correct code until that setting matches what we deploy on — and CI installs 3.11, so nothing caught the runtime break either.

The setting is now py310: the floor the code must run on, not the newest version we test against. Code that is safe on 3.10 still lints and runs clean on 3.11.

The mechanism, stated plainly

A vendor wordmark is set large, in high contrast, because it is branding. A model number is set small, often in thin white-on-black silkscreen, because it is a specification. In a 1U slice the wordmark survives at 1.00 confidence and the model string is six to ten pixels tall.

That is why the pattern is always the same shape: make often, model rarely. It is also why the 204-pixel case matters most — the reader did find the model text and got it almost right. "USW Ro Mas" is two characters away from "USW Pro Max". The pixels were nearly enough; the matching step is what gave up.

Why upscaling cannot rescue it

The pipeline already upscales, sharpens, binarises and gamma-corrects each crop and merges the results. Interpolation cannot restore detail the camera never captured. I ran all three presets over the same seven crops to confirm it: identical recall, more time spent.

The finding I would act on first

A returned model is not proof the label was read

Look again at the crop that "worked". It returned D-Link / DGS-1010MP at 0.744 confidence. Now read the text the OCR actually produced from that image:

The string DGS-1010MP does not appear in it. Neither does any model number. The faceplate says only "D-Link" and "Gigabit Switch"; cables hide the rest. The model was inferred from the vendor plus visible features, not read off the device.

Two consequences follow, and both are visible in my measurements:

  • The same photograph returns DGS-1010MP under one engine and DGS-1100-10MP under another. Different devices, same confidence band.
  • On a second rack, the pass returned SP-R1-U18-SW04 as a device's model. That is a printed asset label — a name your team wrote and stuck on the rack, promoted to a hardware model number.

For a CMDB this is worse than a blank field. A blank field prompts someone to go and look; a confident wrong model number gets written down, syncs onward to Netdisco, and is trusted.

Measured and rejected

Two obvious fixes that make things worse

Both are things the codebase or common sense recommends. I installed, measured and reverted each one rather than assume.

PaddleOCR — recommended in the code, wrong for this workload

switch_ocr logs "For the best results on tiny/blurry text run: pip install paddleocr paddlepaddle" on every close-up, and the tuning in config.py is written for it. So I installed it.

It is 4–5× slower, breaks your 5–10 second window on three of seven crops, finds exactly the same 1 in 7, and changes the model it reports. I have uninstalled it; requirements.txt was never touched. That recommendation message is actively misleading and should be deleted.

Downscaling big photos — buys speed, sells labels

The obvious way to get the 13.3 s label read under budget is to shrink the upload. It works, and it is not free: each step down roughly halves the labels found. This is a real trade, not a fix, and it should be made deliberately rather than by picking a convenient maximum dimension.

Solutions

What to do next, in the order I would do it

The two bugs are already fixed and committed. Everything below addresses the remaining gap: turning "nearly read" into "read", and making a returned model trustworthy.

1

Match read text against the vendor catalogue by edit distance

"USW Ro Mas" is two substitutions from "USW Pro Max"; "WIRCLEBS AC BERVICE ROUtER" is a handful from the real string. The reader is already finding the model text and the identifier is discarding it for failing an exact match. A bounded fuzzy match against the known model list — scoped to the vendor once the wordmark is read, which is the easy part — converts near misses into answers at no latency cost.

no new latency
highest recall gain
2

Never present an inferred model as a read one

Require the model string to actually appear in the OCR text before returning it as the model. If it does not, either leave it blank or return it in a separate inferred field with its own confidence, so the UI can say "probably a DGS-1010MP" instead of asserting it. This is what stops asset labels being promoted to model numbers and stops the answer changing with the engine.

small change
fixes CMDB trust
3

Route every unread device into the close-up flow

The close-up path already works and already returns in 1.5–2.5 seconds — it is the one surface where the pixels are real, because the tech walks up and frames the label. When the rack pass comes back make_only or failed for a device, prompt for that one photo instead of leaving a blank field. This converts a physics limit into a ten-second task.

app-side change
uses what exists
4

Move the label pass off the user's clock instead of shrinking the photo

13.3 seconds at 12.2 MP is over budget, but downscaling costs half the labels. The rack-wide device pass already runs fire-and-forget after a scan; the label pass should too, at full resolution — or be tiled so resolution is kept without one 12 MP inference. Note this path reads rack and asset labels, not make and model, so it is not blocking your stated requirement today.

keeps 121 labels
no user wait
5

Delete the PaddleOCR recommendation and pin the engine

The log line telling operators to install PaddleOCR is wrong for this hardware: measured 4–5× slower for identical recall. Worse, engine selection is auto, so anyone who follows that advice on the server silently quadruples every make/model read and breaks the 5–10 second budget with no code change and no warning.

one message
protects the budget
6

Make CI run the interpreter you deploy on

target-version is now pinned to the 3.10 floor, which stops ruff reintroducing 3.11-only calls. But CI still installs 3.11 while the runtime is 3.10, so the next 3.11-only API to appear will also pass CI and fail in production. Either add a 3.10 job or upgrade the runtime to 3.11 deliberately — the current split is what let a crash ship unnoticed.
