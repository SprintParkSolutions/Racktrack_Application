What switch access we need — and how to grant it

RackTrack only ever reads from your switches — it never changes anything. We tested this on your TP-Link: a plain read-only account works. Admin access is not required.

The ask, in one box

1. One read-only account per switch. On TP-Link, create it with the User role — tested and confirmed: it runs every command we need and is refused configuration access.

2. SSH reachability — TCP port 22 from the RackTrack server to each switch's management IP.

3. That's it. No agent, nothing installed on the switch, no write access, no SNMP write, no config-backup rights.

The key distinction: we need privileged READ, not write. Every read goes through enable because that is how TP-Link exposes show commands — but the account we recommend (User) is blocked from config mode, so it can look at everything and change nothing.

Tested: which role can do what

We created three non-Admin accounts on your switch (User, Power User, Operator) and ran every command RackTrack sends — the full audit, the per-port console reads, ping, and traceroute — then checked the decisive question: can the account change anything?

RoleLoginPrivileged (enable)All our readspingtracertCan run configure?
UserYesYesALL ✓YesDeniedNO — refused 🔒
Power UserYesYesALL ✓YesYesYES — can change config
OperatorYesYesALL ✓YesYesYES — can change config
Decision — use the User role. It reads everything RackTrack needs (identity, ports, PoE, VLANs, MAC table, LLDP, per-port console reads, counters) and can ping — and the switch refuses it configuration access. It is the only genuinely read-only role.

The single thing User cannot do is traceroute. Traceroute is not essential, so we have removed it from the product — ping covers reachability. Result: admin access is not needed, and no functionality is lost.
Why not Power User / Operator? They can traceroute — but they can also change the switch configuration. That defeats the entire purpose. We take the least privilege that works: User.
Note on enable: the User account still enters privileged mode (enable → #) to run the show commands — that is simply how TP-Link exposes them. It is privileged read, not write: config mode stays blocked. RackTrack needs the account password (and the enable password, if one is set).

How to set it up — TP-Link JetStream

  • SYSTEM › User Management › User Config — add a user, e.g. racktrack.
  • Set User Type = User (the lowest role — not Admin, Operator or Power User).
  • SECURITY › Access Security › SSH Config — ensure SSH is enabled.
  • Give us the username, password (and the enable password if one is configured).
  • Do not use Admin, Operator or Power User — those can change the configuration.

How to set it up — Cisco IOS (true read-only works)

Grant a low privilege level only the show commands we use. The account then literally cannot do anything else.

Cisco IOS · read-only via privilege level
conf t
username racktrack privilege 5 secret <password>

! allow only the reads we use
privilege exec level 5 show version
privilege exec level 5 show interfaces
privilege exec level 5 show vlan
privilege exec level 5 show mac address-table
privilege exec level 5 show lldp
privilege exec level 5 show power inline
privilege exec level 5 ping
privilege exec level 5 traceroute

line vty 0 4
 transport input ssh
 login local
ip ssh version 2
end
Prefer central control? If you run TACACS+ / RADIUS, just authorize the account for show, ping and traceroute only. Same result, managed centrally — and this is the cleanest way to give RackTrack read-only access at scale.

How we handle the credentials

  • Stored encrypted (AES-256-GCM) in a per-host credential vault.
  • Write-only — once entered they cannot be read back out of the app, by anyone.
  • Scoped per switch, and used only to run the commands listed above.

Bottom line: RackTrack needs to look, never to touch — and that is now proven on your hardware. A TP-Link User-role account runs every command we need and is refused configuration access. Admin access is not required on either vendor.
