From a laptop demo to a system testers can use

What we built over two days, how it's now deployed, and the reasoning behind each decision — in plain terms.

What RackTrack does

You take a photo of a server rack. RackTrack reads it and produces a full, labelled map of everything inside — every device, where it sits, and its details. It also connects to the network switch to show live port information: which ports are free, which are in use, and what's plugged into them.

The phone doesn't do the heavy work. It sends the photo to a server, which runs the AI and talks to the switch, then sends the answer back. That server is the part this report is really about — because where it runs decides whether the app is a demo or something a team can rely on.

Day 1

Yesterday — getting it into testers' hands

The goal for day one was simple: turn the working prototype into a real, installable app on both phone platforms.

  • Put our real RackTrack branding and logo on the app.
  • Built and signed it as a proper iPhone app and published it to Apple TestFlight, so invited testers can install it like any App Store app.
  • Built the Android version as well.
  • Refined the experience based on early testing — the scanning flow, navigation, and a short first-time walkthrough so new users know what to do.
The problem we were left with At the end of day one, the app still depended on my laptop being switched on and connected — because that's where the server was running. A laptop can't stay on around the clock, and its internet address kept changing. That meant testers could only use the app when my machine happened to be awake. Not workable for real testing.
Day 2

Today — moving it onto real infrastructure

Today was about fixing that dependency for good, and it's the most important change of the two days.

We moved the entire backend onto the Windows workstation

The server now runs on the office Windows machine with the graphics card (GPU). This was deliberate, for three reasons:

ReasonWhy it matters
It stays onThe machine runs around the clock, so testers can use the app anytime — not only when my laptop is awake.
It's fasterThe GPU runs the AI far quicker than a laptop's processor, so scans come back faster.
Same network as the switchThe live port-and-cable features need to reach the switch directly. The Windows machine is on the same office network, so that works.

My laptop is now out of the loop entirely for running the app. It's only used to build the iPhone version, which Apple requires to be done on a Mac.

We gave it a permanent address

Every app needs a fixed web address to reach its server. Before, that address was random and changed on every restart — which broke the installed apps. We set up a permanent address that stays the same, so the app keeps working through restarts and reboots. This was the single biggest source of fragility, and it's now solved.

We polished the app and simplified it

  • Simplified the camera down to Photo and Video only, with a clear, obvious capture button.
  • Removed unused features to make the app lighter and let it install on a wider range of phones.
  • Added profile pictures.
  • Tightened the overall experience so a scan carries through cleanly to the results.

We automated how the app reaches testers

Until now we were sharing the app file by hand in the group every time. We set up automatic delivery: testers install once, and every new version arrives on their phone by itself, with a notification — the same way Apple's TestFlight already works for iPhone.

Why we deployed it this way

Two questions decided the whole setup, and both had a clear answer:

Why not keep it on the laptop / in the cloud?

The live switch features must talk to equipment sitting on the office network. A cloud server somewhere on the internet can't reach that switch. The Windows machine can, because it's physically on the same network — and it has a GPU, so it's also the fastest option we have. Keeping the backend in the office, on an always-on machine, was the only choice that supports every feature.

Why a permanent address?

The address is what the app uses to find the server. If it changes, every installed app breaks and has to be rebuilt and re-sent. Making it permanent means we stop chasing that — the app is built once and keeps working.
