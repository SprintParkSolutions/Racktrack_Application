Shipping to TestFlight — what works, what won't, and what to do

An honest assessment of the app as it stands today, the one thing that would kill the build on launch, and the exact path to a working beta.

Verdict today: a TestFlight build would install and launch — and then fail on every screen. The app has no backend to talk to (the production build bakes in localhost). Separately, the entire live-switch half of the product cannot work for remote testers unless the server sits on the same network as the switch. Both are fixable — see “What to do”.

The blockers — why it wouldn't run

#BlockerWhy it breaks
1API points at localhost
.env.production.local → VITE_API_BASE=http://localhost:3001		 Vite's .local file overrides .env.production. In a packaged app, localhost is the phone itself — there is no server there. Every API call fails.
2No hosted backend The Node server and the Python vision pipeline (the AI models) run server-side. They can't run on the phone — TestFlight ships only the web bundle in a WebView.
3ATS wide open
NSAllowsArbitraryLoads = true		 Permits plain HTTP. External TestFlight needs Beta App Review, and this is commonly flagged. Ship HTTPS and drop the exception.

Why — the thing that's easy to miss

The phone never touches the switch. The server does.

📱 iPhone (TestFlight) ──HTTPS──▶ ☁️ Backend ──SSH──▶ 🔌 Switch (192.168.1.33) ▲ this hop must be on the switch's network

So the live-switch features work only if the backend can reach the switch — no amount of app-side work changes that.

What to do — Phase 1: make it run

  1. Decide where the backend lives (see Phase 3 — this choice also decides whether live-switch features work).
  2. Point the app at it. Delete or override .env.production.local, and build with a real HTTPS host:
    client/.env.production
    VITE_API_BASE=https://api.racktrack.example.com
  3. Tighten ATS — remove NSAllowsArbitraryLoads from ios/App/App/Info.plist and serve the API over HTTPS only.
  4. Build & sync & ship:
    terminal
    cd client
npm run build              # produces dist/
npx cap sync ios          # copies dist into the iOS app
npx cap open ios          # opens Xcode
# In Xcode: set Team + signing, bump version/build,
#           Product ▸ Archive ▸ Distribute ▸ App Store Connect

Fast path: use internal TestFlight testers first — no Beta App Review, installs within minutes of upload. Good enough to demo the whole app.

Phase 3: making the live-switch features actually work

Option A — Beta / demo (works this week)

Keep the backend on a machine that has VPN access to the switch, and expose it publicly with an HTTPS tunnel (e.g. Cloudflare Tunnel). Then:

📱 TestFlight app ──HTTPS──▶ 🌐 tunnel ──▶ 💻 your server ──VPN──▶ 🔌 switch
  • Pro: every feature works, including Ports / Cables / Trace / Drift. Set up in an afternoon.
  • Con: depends on that machine + VPN + tunnel staying up. Fine for a beta or a client demo; not production.

Option B — Production architecture

Split the product: a cloud backend (auth, scans, AI, reports) plus a small on-prem collector that runs inside the customer's network, reaches their switches, and reports back over an outbound connection. This is the standard pattern for infrastructure tools — and it's the only way the live-switch features work for real customers who won't put their switches on the internet.

Decide this before the beta gets serious. The photo half of the product ships to TestFlight today. The live-switch half needs the collector — that's a real piece of engineering, not a config change.
