Deployment requirements and runbook

RackTrack Private Deployment

Where RackTrack runs today, what ships in the package, what a customer-owned installation must have, what has to change, how to do it step by step, and how we keep track of every installation afterwards.

Every statement is either Verified with the evidence under "Read more", or marked Estimate or Recommendation. Nothing else is claimed.

Private deployment means: the same RackTrack that runs on our demo server, installed on a server the customer owns, with their hostname, their mail, their NetBox, and phone apps rebuilt to point at it. No product feature has to be rewritten. Everything below is verified; the proofs are in tabs 1 to 6.

Today

One deployment exists: the public demo at demo.racktrack.ai, on a small rented server with 2 cores and 7.8 GB. Nothing runs on customer hardware. It has no backups and no version stamp.

What ships

One Docker image (7 GB) with the web app, API and detection workers. Plus the model weights (483 MB), the NetBox stack beside it, and iOS and Android apps at build 61.

The customer must provide

1. A Linux server with Docker (4 cores, 16 GB minimum; no GPU needed).
2. A hostname with an HTTPS certificate the phones trust.
3. An SMTP mail relay.
4. Technician Wi-Fi that reaches the switches on UDP 161.
5. One administrator to do the DNS, certificate, mail and firewall.

We must bring

The image, the model weights, the OCR weights, fresh secrets, a compose file and Caddyfile for that customer, the phone builds, and the owner login.

What must change

Per customer: configuration only (hostname, mail, timezone, worker count, app address). In the repo, about two days: a private compose template, OCR weights and the PDF browser baked into the image, a build stamp, a sign-up disable switch, and a hand-over bundle script.

How long Estimate

Three working days for the first install: server and app, then NetBox and mail proof, then phone builds and hand-over. Faster after the repo work is done.

Our firm positions

  • Certificate: a public DNS name with a DNS-challenge certificate, or the customer's own CA. Nothing else for a rollout.
  • Mail: the customer's SMTP relay. Our Microsoft identity never sends for a customer.
  • Accounts: invitation only. We seed the owner once; the owner invites everyone else.
  • One server per customer. No GPU.
  • Works without internet, except vendor spec and firmware lookups, cloud language models, social sign-in, and Slack or Teams sharing.

Not possible today

The phone doing everything alone, with no server. The phone uploads the photo and the server's workers run the models. That would be a new product effort.

Found while checking

Firmware check cannot work in any container, OCR weights download during the first scan, the demo has no backup job, and a leftover sign-up endpoint accepts only Gmail. Each has a fix in tab 4.

RackTrack has exactly one deployment: the public demo at demo.racktrack.ai. It runs on a small rented server (a VPS) at Hostinger with two processor cores and no graphics card. It is updated by hand from the Mac. It runs the complete product inside Docker containers, which matters because a private deployment is a move of these same containers onto a customer's hardware, not a new build of the product. No customer hardware runs RackTrack today, and no customer has their own separate data.

1.3

How it is set up, in plain terms

Verified

Where the data is. Accounts, sites, organisations, the audit trail and the record of NetBox exports are in SQLite files under server/data. Rack photos, the detection overlays, device maps, HTML reports and PDFs are files under outputs/. Both directories are mounted from the host into the container, so a rebuild of the image does not lose them. The model weights (Models/) and the mail identity (token/) are mounted read-only.

How mail is sent. The server tries Microsoft Graph first, sending as racktrackteam@sprintpark.com using a refresh token stored in the mounted token/ directory. If Graph is not configured it falls back to an SMTP server, and then to a second fallback SMTP server. On the demo only Graph is configured; there are no SMTP settings.

How people get accounts. There is no public sign-up page. The app's /signup route redirects to the login page, which tells visitors who to write to. People get in with a login an administrator issued, or through an invite link of the form /invite/<code>. The server still has a sign-up endpoint left over from the public-testing period, and that endpoint only accepts @gmail.com addresses. Continue with Google is configured in the demo's environment file.

How the phone apps find the server. The address https://demo.racktrack.ai is compiled into the iOS and Android apps at build time. The project files for both platforms are at build 61, committed on 7 September.

How switches are read. The phone talks to the switches directly over SNMP, on UDP port 161, using version 2c or version 3 at the noAuthNoPriv level. Authentication and encryption for version 3 are not implemented yet, so credentials cross the Wi-Fi in clear text. The server does not talk to switches at all.

Ask DOT. The support assistant answers word for word from its verified knowledge base. It can also phrase answers with a language model, in this order: OpenRouter, Groq, Gemini, then a local Ollama. None of those is configured on the demo, so it runs in verbatim mode.

Demo-only switches that are on. RACKTRACK_DEMO_DATA makes the Network view answer from an invented four-device network, and the server logs a warning at every start while it is on. LIVE_SWITCH_OFF_NETWORK makes the live-switch pages say plainly that the VPS cannot reach a switch. Only one computer-vision worker runs, because two workers next to NetBox ran the box out of memory during a scan.

2.4

What a build needs from the internet

Verified

Running the product needs no internet for its core features (tab 3, section 3.7). Building the image does. Whoever builds must be able to reach:

  • Docker Hub for the python:3.11-slim, node:20-slim and caddy:2-alpine base images.
  • Debian's package mirror for the system libraries. On our office LAN the gateway blocks deb.debian.org, so a local build must pass --build-arg APT_MIRROR_HOST=debian.osuosl.org.
  • PyPI and the PyTorch CPU wheel index for the Python dependencies.
  • The npm registry for Node dependencies, during which Puppeteer downloads Chromium.

Solution for a customer that cannot allow any of this: we build the image on our side, save it to a file with docker save, and hand it over with the weights. The customer only runs docker load.

Read more: proof
Dockerfile: FROM python:3.11-slim; COPY --from=node:20-slim; ARG APT_MIRROR_HOST with the comment "The office LAN's gateway blackholes deb.debian.org"; pip install --extra-index-url https://download.pytorch.org/whl/cpu -r requirements.txt; cd server && npm ci --omit=dev with the note that "Puppeteer downloads its own Chromium during npm ci".

These are our requirements. They are not negotiable, because each one is tied to how the product works. Five things the customer must provide, six things we must bring, and three things decided per customer. The core product works without internet. Only lookups against vendor websites, cloud language models, social sign-in, and Slack or Teams sharing need it.

3.1

What the customer must provide

Firm

1. A Linux server with Docker

A physical server or a virtual machine on their network, or a private VPS they rent. Sized by section 3.6. Ubuntu LTS is what we recommend and what the demo runbook was written for. No GPU: the image is CPU-only and cannot use one.

If they cannot host a server: we rent a private VPS in their name, which is exactly the demo set-up with their own hostname and data.
Read more: proof
Dockerfile:112 installs torch from the CPU wheel index; pipeline/runner.py:258 load_cable_model(…, device="cpu"). docs/setup/DEMO-VPS-SETUP.md installs Docker with curl -fsSL https://get.docker.com | sh.

2. A hostname the phones can resolve, with HTTPS

The phone apps have the server address compiled in, and iOS refuses plain HTTP. So there must be a DNS name that resolves on the office Wi-Fi, and a certificate the phones trust. Section 3.4 gives the three ways to get that certificate.

Our position: a public DNS name (for example racktrack.customer.com) pointing at the internal address, with a Let's Encrypt certificate obtained through the DNS challenge. No inbound internet is needed for that.
Read more: proof
client/src/utils/api.js:3-6 "In the APK build, we set VITE_API_BASE=https://<public-host> so the WebView can reach the real backend". client/.env.production.example: "it MUST be https:// (iOS ATS / Android cleartext policy block plain http)".

3. A mail relay

The server sends sign-up verification codes, password-reset codes and invitations by email. It supports any SMTP server, with a second SMTP server as automatic fallback. Without any transport it accepts the request, answers success, and sends nothing, so users wait for a code that never comes.

Our position: the customer's own SMTP relay (host, port 587 or 465, a user and password, a from-address). We do not send on a customer's behalf from our Microsoft identity.
Read more: proof
server/auth.js:470-476 "PRIMARY SMTP_HOST / SMTP_PORT / SMTP_USER / SMTP_PASS / SMTP_FROM · FALLBACK SMTP_FALLBACK_HOST …", nodemailer, port 465 = SSL, 587 = STARTTLS. deploy/demo.env.example: "the server accepts a forgot-password request, answers 200 … and sends NOTHING."

4. Phone Wi-Fi that reaches the switch management network

Reading a switch's ports, PoE and neighbours is done by the phone itself over SNMP, UDP port 161. The phones must be on a Wi-Fi network that can route to the switches' management addresses. The server needs no route to the switches.

Our position: a technician Wi-Fi with a firewall rule allowing UDP 161 to the management VLAN, and an SNMP v2c read-only community or a v3 user. Because v3 authentication is not implemented yet, the management VLAN must be one the customer already treats as trusted.
Read more: proof
client/src/utils/snmpClient.js is part of the phone bundle (lines 10, 250-254, 342). deploy/demo.env.example explains the demo's LIVE_SWITCH_OFF_NETWORK flag with "a VPS cannot route to anyone's private LAN".

5. One administrator on their side

Someone who can add DNS records, issue or approve the certificate, create the mail account, open the firewall rule, and receive the owner login. Every step in tab 5 that touches their network goes through this person.

Our position: named before the install date, with the DNS, certificate and mail items done before we arrive.

What we must bring

Firm

The image or the code

Either the repo copied by rsync and built on their box (needs internet at build time), or a pre-built image saved to a file (needs nothing). The hand-over bundle in tab 4 makes the second option routine.

Models/, 483 MB

3.4

The certificate: three ways, one recommendation

3.5

Mail: what the server can do

Verified

The server tries, in order: Microsoft Graph (if MS_CLIENT_ID and MS_TENANT_ID are set and a token exists), then the primary SMTP server, then the fallback SMTP server. A send that errors on one moves to the next, so no single provider can block sign-in codes.

For a private deployment we set only SMTP. Graph stays unset, so our Microsoft identity is never involved. If the customer has two relays, the second goes in the SMTP_FALLBACK_* settings.

Test it before hand-over: request a password reset for the owner account and confirm the code arrives. That is the only test that proves the whole chain.

3.8

If the customer requires no internet at all

Path exists, adds work

An air-gapped installation is possible with four changes to the normal path: we build the image on our side and deliver it as a file; the OCR weights are baked into the image first; the certificate comes from the customer's CA; and the five internet-only features in 3.7 are hidden for good. Per deployment, only configuration changes. In the repo, seven small pieces of work. No product feature has to be rewritten to run privately. The one product-level item is accounts: private customers get in by invitation, which already works for any email domain.

4.2

Accounts on a private box

Verified

How it works today. The app has no public sign-up page; /signup sends people to the login page. Accounts are created in two ways: the seed script creates the owner, one organisation admin and a batch of member invite codes, and administrators create invite links from the console. Accepting an invite creates the account from the invited email address, whatever its domain.

What is left over. The server still answers POST /api/auth/signup, and that endpoint only accepts @gmail.com addresses. It is unreachable from the app's screens but reachable by anyone who calls the API directly.

Our position for private deployments: invitation only. The owner and the organisation admin come from the seed script; everyone else gets an invite link from the admin. Set AUDIT_ADMINS to the owner's username so the organisation-wide audit view works.

Solution for the leftover endpoint: add a setting that disables POST /api/auth/signup entirely, on by default for private builds. Until that exists, it is a low risk: the endpoint still requires email verification and creates a member in a fresh organisation, not access to the customer's data.

4.4

Security points to settle on every private box

SNMP credentials in clear Verified

The phone speaks SNMP v2c and v3 noAuthNoPriv only, so the community string or user name crosses the Wi-Fi unencrypted.

Solution: read-only SNMP credentials on a management VLAN the customer already trusts. Implementing v3 authPriv on the phone is the product fix; the code already reserves the place for it.

Secrets never in the image Verified

All secrets come from server/.env and the mounted directories at run time. The image can be handed to a customer without leaking anything.

Keep it that way: the hand-over bundle carries an env template, never a filled-in env file.

Non-root, rate-limited, secure cookies Verified

The process runs as user id 10001. Credential endpoints and uploads are rate-limited. Session cookies are HTTP-only, and marked secure automatically in production.

Nothing to change. Keep NODE_ENV=production exactly.

Ten steps, in order, each with a check that proves it worked. Steps 1, 3 to 7 and 10 mirror the demo runbook, which has been carried out for real on the VPS. Step 2's certificate route and step 9's app distribution are the parts that differ per customer. Estimate three working days for a first install: host and app on day one, NetBox and mail proof on day two, phone builds and hand-over on day three. Later installs are faster once the repo work in tab 4 is done.

1

Prepare the host

Install Ubuntu LTS and Docker. Open only SSH and 443 in the firewall. Create the directories the app writes to and give them to user id 10001, because the container runs as that user.

curl -fsSL https://get.docker.com | sh
ufw allow OpenSSH && ufw allow 443/tcp && ufw --force enable
mkdir -p /opt/racktrack/{outputs,server/data,active_learning_Cache/data,server/uploads}
chown -R 10001:10001 /opt/racktrack/{outputs,server/data,active_learning_Cache,server/uploads}

docker --version answers, and ufw status shows 22 and 443 only.

2

Hostname and certificate

The customer's administrator adds the DNS name pointing at the server. Then pick the certificate route from tab 3, section 3.4, and write it into the Caddyfile site block. For a customer CA, the two files go beside the Caddyfile and are mounted into the Caddy container.

racktrack.customer.com {
    tls /etc/caddy/certs/fullchain.pem /etc/caddy/certs/privkey.pem   # customer CA only; omit for automatic
    encode zstd gzip
    request_body { max_size 350MB }
    reverse_proxy racktrack:3001
}

a phone on the office Wi-Fi resolves the name: nslookup racktrack.customer.com from a laptop on the same Wi-Fi returns the server's address.

3

Copy the code and the weights

The repo is private and the box has no GitHub access, so the code goes up by rsync with the same exclude list the demo uses, and Models/ goes up once on its own.

rsync -avz --exclude-from=deploy/demo-rsync-excludes.txt ./ admin@HOST:/opt/racktrack/
rsync -avz Models/ admin@HOST:/opt/racktrack/Models/

Hand-over without our Mac: build once, docker save racktrack:private | gzip > racktrack.tar.gz, and deliver the file with Models/, the compose file and the Caddyfile. The customer runs docker load.

ls /opt/racktrack/Models shows six files, 483 MB in total.

4

Write server/.env

Start from deploy/demo.env.example. Delete RACKTRACK_DEMO_DATA, LIVE_SWITCH_OFF_NETWORK and LIVE_SWITCH_NOTE. Generate a fresh secret. Fill in the customer's SMTP. Do not put comments after values; the loader takes everything after the equals sign.

JWT_SECRET=<output of: openssl rand -hex 32>
SMTP_HOST=smtp.customer.com
SMTP_PORT=587
SMTP_USER=racktrack@customer.com
SMTP_PASS=…
SMTP_FROM=RackTrack <racktrack@customer.com>
AUDIT_ADMINS=<owner username, set after step 8>

the file has no RACKTRACK_DEMO_DATA line and no line contains a "#" after its value.

5

Compose file, validate, start

Copy docker-compose.demo.yml to docker-compose.private.yml. Change the image name, CORS_ALLOWED_ORIGINS, TZ, REPORT_TZ and RACKTRACK_WORKERS. Validate the Caddyfile before starting; Caddy refuses to boot on a typo and takes the whole site down rather than one setting.

docker run --rm -v "$PWD/deploy/caddy/Caddyfile:/etc/caddy/Caddyfile:ro" caddy:2-alpine caddy validate --config /etc/caddy/Caddyfile
docker compose -f docker-compose.private.yml up -d --build
docker compose -f docker-compose.private.yml logs -f racktrack     # wait for "worker N ready"

curl -I https://racktrack.customer.com/healthz returns 200 and the browser shows no certificate warning.

6

NetBox beside it

Clone netbox-docker on the box. Reuse the demo's override file with the network name changed to the new compose project's network. Set BASE_PATH and CSRF_TRUSTED_ORIGINS for the new hostname if NetBox is to be browsed under /netbox. Start it, create the superuser, and create an API token.

docker exec racktrack curl -s http://netbox:8080/api/status/ returns JSON from inside the app container.

7

Seed the first accounts

Run the seed script once, on the empty database only, because it wipes users, organisations, racks and invites. Copy the printed owner and admin passwords immediately; they are shown once. It also writes member invite links to server/data/racktrack-invites.json.

docker compose -f docker-compose.private.yml exec racktrack node server/scripts/seed-racktrack.js
docker compose -f docker-compose.private.yml restart racktrack

the owner can sign in at the hostname on a laptop, and the password can be changed from the profile page.

8

Connect NetBox and prove the product

Signed in as the owner, add the NetBox URL and token under Data Sources for the customer's organisation. Then prove five things before anyone else touches it: one real rack scan end to end, one PDF download, one password reset code arriving by email, one export landing in NetBox, and one switch read from a phone on the office Wi-Fi.

all five succeed. If the scan hangs, check memory with docker stats and lower RACKTRACK_WORKERS.

9

Build and distribute the phone apps

On the Mac, set the hostname in client/.env.production, build the bundle, sync it into the native projects, then archive the iOS app in Xcode and the Android app in Android Studio. Distribute by TestFlight, an ad-hoc build for named devices, or the customer's device management. The web app needs nothing extra; it is served by Caddy at the hostname.

echo "VITE_API_BASE=https://racktrack.customer.com" > client/.env.production
cd client && npm run build && npx cap sync

a phone signs in through the app and completes a scan.

10

Backups, updates and hand-over

Backups, nightly: server/data, outputs/, server/uploads, server/.env, server/.env.key, and a pg_dump of NetBox's Postgres. Once: Models/ and the Caddy data volume (certificates). Updates: rsync then up -d --build; a plain restart keeps serving the old client bundle. Rollback: tag each image with its build stamp and start the previous tag. Hand-over: the owner login, the deployment register entry (tab 6), and the list of what needs internet.

a restore of last night's backup on a scratch machine brings the app up with the same accounts and scans.
