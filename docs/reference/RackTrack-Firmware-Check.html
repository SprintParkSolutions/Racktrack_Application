RackTrack · Feature report

Firmware Check

How it works, which vendors it can actually answer for, which need a login, and which it gets wrong. Tested against the live system on 14 July 2026.

Read this first — the honest status

Firmware Check does not work today, for any vendor. Not because it is badly built — but because the step that loads real firmware data has never been run.

The cache holds 16 rows, and all 16 are junk — regex guesses scraped off random web pages. One of them records HPE Aruba's “firmware version” as 802.3af, which is a PoE standard. The release-notes table holds zero rows, so the “what changed” section is always empty, for every vendor, every time.

So a technician gets one of two answers: “We couldn't confirm the latest version” — which is honest — or a confident “An upgrade is available” pointing at a version that does not exist.

The good news: three real, working fetchers are already written (MikroTik, Ubiquiti, NVIDIA). Nobody has ever run them. One command starts fixing this — see How to fix it.

What it is for

You give RackTrack a make, a model and the version you are running. It tells you whether there is something newer, and what changed in it. That is the whole feature. (Security-vulnerability reporting was removed from the product, so it no longer lists CVEs.)

How it works

What happens when you press “Check firmware”

The browser posts to /api/firmware. The server shells out to a Python agent (Agent/Agent_scrap, run as --firmware, 60-second timeout). The agent has three tiers, tried in order:

TierWhat it isCoversState today
Tier 1 Real fetchers. Proper sources with real changelogs — MikroTik's CHANGELOG file, Ubiquiti's public JSON API, NVIDIA's docs site. 3 vendors: MikroTik, Ubiquiti, NVIDIA Never run. Zero rows in the database.
Tier 2 Login-gated. Stop, and point at the vendor's portal. Honest by design. 22 vendors (Cisco, Juniper, …) Works — but only for 6 of the 22. See below.
Tier 3 A web search and a regex. Search the open web, grab the highest-looking number on the page, cache it, return it. Everyone else (~110 vendors) This is what every user actually hits. It is the source of every wrong answer.
Tier 3 never produces release notes

A regex scraping a web page cannot tell you what changed. Only Tier-1 fetchers populate the release-notes fields — and there are zero Tier-1 rows. That is why the “what's new” section is empty for every vendor.

What “up to date” actually means

The comparison is a plain string equality between what you typed and what the agent found (server/app.js:6234). 16.12.1 vs 16.12.01 reads as out of date. And if the cached “latest” is older than your version, it still says “An upgrade is available.”

The vendors that need a login

For these, the maker puts firmware and release notes behind a support account. RackTrack cannot read them, and does not pretend to — it hands you a link to the vendor's portal and says “Check vendor portal”. This is correct behaviour, not a failure.

But only 6 of the 22 actually behave that way

LOGIN_GATED_VENDORS lists 22 vendors, but the matching DEFAULT_GATED_NOS table (firmware.py:593) has only 6 entries: Cisco, Juniper, Arista, HPE Aruba, Dell, Fortinet. For the other 16 — Huawei, H3C, Extreme, RUCKUS, Alcatel-Lucent, Nokia, ZTE, Lenovo and the rest — the gate is silently skipped. They fall through to the Tier-3 scraper, and the user gets a junk version instead of the portal link RackTrack already knows.

And the portal link is never shown on this page anyway

Even for the 6 that gate correctly, FirmwarePage.jsx never renders portalUrl — I checked; it appears zero times in the file. So a Cisco lookup on the Firmware Check page shows “We couldn't confirm the latest version” with no link to Cisco at all. The portal link only appears on the rack-scan Switches card (SwitchInformationPage.jsx:849).

Two names, two answers

Typing “Aruba (HPE)” gates correctly. Typing “HPE Aruba” resolves to a different canonical name, misses the gate, and returns 16.6.54 — scraped from a PDF. Same vendor, two behaviours.

All 16 rows are marked train='live-discovered' — every one came from the Tier-3 regex, not a real fetcher. The security_advisories table has 0 rows. There is no good data in this system at all.

The agent's own code knows this data is untrustworthy. vendor_latest_any() (firmware.py:192) carries a trust filter whose comment reads “deliberately strict — accuracy beats coverage”. It refuses any cached row with no release notes attached, because “its version could be a sample, demo, or random number on the page.” Since no row has release notes, that filter rejects the entire cache.

The bug, in one sentence

The live scraper bypasses the trust filter. _try_live_firmware() (firmware.py:703 and :845) returns its result straight to the user without ever passing through vendor_latest_any() — so precisely the junk the filter exists to block is what reaches the screen.

Where the junk came from

scripts/prefetch_firmware.py sweeps every vendor through the Tier-3 regex and writes the results to the cache. Running it is what poisoned the database. It should not be run again.

The practical effect: a technician on MikroTik RouterOS 7.11 is told “An upgrade is available. Latest is 25.6196C16.” That is worse than silence, because it looks like an answer.

How to fix it

In rough order of value. The first two could be done this afternoon.

  • 1 — Empty the poisoned cache. DELETE FROM firmware_versions WHERE train='live-discovered'; That is all 16 rows. Nothing of value is lost.
  • 2 — Run the fetchers that already exist. cd Agent/Agent_scrap && python3 scripts/fetch_firmware.py. This populates real versions and real release notes for MikroTik, Ubiquiti and NVIDIA. Nothing schedules this today — no cron, no startup hook — so it also needs to be put on a timer to stay current.
  • 3 — Make the live scraper honest. Route _try_live_firmware() through the same trust filter, or drop Tier 3 entirely. A number with no release notes behind it should be reported as unknown, not as a version.
  • 4 — Give the other 16 gated vendors their gate back. Add them to DEFAULT_GATED_NOS, so Huawei, Extreme, RUCKUS and the rest return their portal link instead of a scraped number.
  • 5 — Render portalUrl on the Firmware Check page. It is already in the API response and is simply never shown, so gated vendors dead-end with no link.
  • 6 — Clean up the leftover CVE wording. A Cisco lookup still says “Couldn't fetch release notes: No security advisory data available for Cisco IOS-XE.” That describes a feature you removed.

What you need to set up

No credentials, for anyone. There is no credential store, no vendor login automation, no API key anywhere in the firmware path. A Cisco or Juniper support account would not help — nothing in the code can consume one. Gated vendors are simply linked out to.

What the server needs: Python 3 on the PATH (or PYTHON_PATH set), the agent's dependencies (pip install -r Agent/Agent_scrap/requirements.txt), and the vendor spreadsheet Switch_Vendors_Websites.xlsx at the repo root, which feeds the 111-vendor type-ahead.

One caveat on the type-ahead

Earlier in this session /api/specs/vendors returned HTTP 500; it now returns 200 with all 111 vendors. I could not pin down the cause and will not guess — if it 500s again, the likely culprits are a wrong PYTHON_PATH or a missing openpyxl in that interpreter, both of which produce an empty result the route turns into a 500. Note the vendor field is free text anyway: the dropdown is a convenience, and nothing validates what you type against it.

What to tell users today

Until steps 1 and 2 above are done, the honest guidance is blunt: do not act on a version number from Firmware Check. Treat “Latest version unknown” as the truthful answer it is, and treat any version it does show as a number scraped off a web page — because that is exactly what it is. Check the vendor's own site.

This is a data problem, not a design problem

The architecture is sound: three real fetchers are written and working, the gating logic is right, and the trust filter that would have prevented all of this already exists. What is missing is that nobody ever ran the loader. That is a good position to be in.

How this was tested

Every vendor in the table was put through the live /api/firmware on 14 July 2026, and the cache and code were read directly. Note that the lookup is a write-through cache — asking about a vendor causes the Tier-3 scraper to store what it finds. So testing added a few rows to switches.db; the junk rows listed above predate it, and the clean-up in step 1 clears all of them.
