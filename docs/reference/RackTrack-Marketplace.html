Marketplace

What it's for, what's built, how it works end to end, and a prioritised list of what to add next. Ground truth from the code, 14 July 2026.

Where it stands, in three lines

The core works. You can list gear, browse and filter it, open a detail view, and mark items sold — all backed by real routes and a real table.

It stops at the handshake. There is deliberately no checkout, no payments and no messaging — a buyer contacts the seller through their RackTrack username, out of band.

The biggest quick win is already half-built: the “list this from a scan” prefill is fully wired on the receiving side, but nothing links into it yet. One button finishes it.

5 · How it works, end to end

Creating a listing
  • Create — the sell form optionally POSTs a photo to /uploads (multer writes uploads/marketplace/<uuid>.<ext>, ≤8 MB), then POSTs the listing. The server validates kind/category/condition/title/price and inserts a row.
  • Browse &amp; filter — every keystroke re-runs GET /listings?kind=&category=&q=. Filtering is 100% server-side SQL (WHERE status='active' AND kind=… [AND category] [AND title/vendor/model LIKE]), newest first.
  • Contact — the detail view shows the seller's @username and tells the buyer to reach them through their RackTrack profile. No messaging, no checkout, no payments — this is a noticeboard, not a store.
  • Sell / delete — the owner marks a listing sold (PATCH status) or deletes it, both ownership-checked server-side and confirm-gated in the UI.
  • Partner search — the top bar and the detail view build plain deep-links to eBay, Amazon, FS.com and Curvature from the vendor+model. No API, no affiliate tag — just a pre-filled search URL.

6 · What to add next

In priority order. The first two are decisions as much as code; the greenfield items at the end are real projects.

High

Wire “Sell this” from a scan

The prefill target is fully built — /marketplace/new?vendor=&model=&category=&rackId= reads all of it and stamps source_rack_id on the listing (the detail modal even shows “From scan RK-…”). But nothing links into it. No button anywhere navigates there. Add one on the Switches or Results page: navigate('/marketplace/new?vendor=…&model=…&rackId=…'). This is the highest-value, lowest-effort win — the receiving half already works.

High

Decide who the marketplace is for

The UI is admin-only (AdminRoute, App.jsx:261; isAdmin nav gate, DesktopShell.jsx:186) — regular members can't list or even browse from the app. But the backend browse is public and cross-org. If it's meant to be member-wide, loosen both gates. If it's meant to be org-scoped, add a tenant filter to the browse query (marketplace_routes.js:246).

Medium

Add UI pagination

The backend already accepts ?limit=&page= (marketplace_routes.js:265), but the client never sends them and has no pager — Browse silently shows only the first 30 listings. fetchListings (MarketplacePage.jsx:240) just needs to pass them and render a “next page” control.

Medium

Clean the data before launch

8 rows exist and most are test junk — hfhhvbhncn, dfgdfg, a bare cisco, a $0.21 switch, plus four [demo] seeds. There are zero real ‘Wanted’ listings and zero sold ones. Clear the junk so Browse looks credible.

Medium

Fix the isMine soft-auth on public routes

Browse and detail compute viewerId = req.user?.id and comment “so isMine works even on public routes” — but no middleware sets req.user on these routes, so isMine is always false on Browse. Owner actions only appear via the My listings tab. Either apply a soft-auth middleware or accept the current behaviour and drop the misleading comment.

Low

Harden image upload

Server validates the photo by filename extension only (marketplace_routes.js:165) — no magic-byte check. A non-image renamed .png passes. Add MIME/content sniffing.

New build

Add in-app messaging (greenfield)

Today a buyer contacts the seller out-of-band via their RackTrack @username. No messaging table, endpoint or UI exists. To build it: a self-provisioning marketplace_messages table (mirror the listings table at marketplace_routes.js:44), authed POST/GET routes, and a thread UI replacing the contact hint (MarketplacePage.jsx:212). Seller identity is already on listing.seller.{id,username}.

New build

Add checkout / payments (greenfield)

No payment provider, order table or stock decrement exists — quantity is informational only, never modified. price_cents/currency already model money. Adding a buy flow means an orders table, a payment integration, and swapping the “contact via username” hint for checkout.
