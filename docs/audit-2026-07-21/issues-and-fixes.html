Issues & Fixes — Detailed Record

Every defect found during the full-codebase audit, written in plain language: what was wrong, what it meant for users, how it was fixed, and how the fix was proven. Followed by an honest list of what is still open.

How to read this. Each entry states the user-visible symptom first, because that is what matters — the code detail is secondary. Nothing here is theoretical: every item was confirmed by reading the source, and the important ones were reproduced against a running server.

Fixed — blocking defects

These stopped the product working. All are fixed and verified.

P0-1Every scan failed, and blamed the user's photoCriticalFixed
Symptom
Uploading any rack photo returned "Please upload a clearer photo of the rack." A perfect photo failed the same way, so users retried endlessly.
Cause
A variable was declared inside a block that had already closed, so the scan endpoint threw an internal error on every request. The error handler caught it and returned the generic "bad photo" message.
Why missed
Introduced hours earlier by an unrelated change. The failure looked exactly like a camera/lighting problem, so it read as user error rather than a bug.
Fix
Moved the declaration so it is in scope where it is used.
C-3Two-rack video scanning had never workedCriticalFixed
Symptom
Scanning two racks from a video always failed. Only the two-photo path worked.
Cause
The video splitter looked up a model configuration key that has never existed in the config file, so it errored on every call — since the feature was written.
Fix
Read the key that actually exists, keeping a fallback for the old spelling.
C-1A failed component start-up froze the whole app silentlyCriticalFixed
Symptom
If the image-processing engine failed to start, every scan, port lookup and detection request would hang forever — no error, no timeout. Health checks stayed green, so the server looked perfectly healthy while nothing worked.
Cause
A start-up failure was logged but never surfaced: waiting requests were never failed and the component was never restarted.
Fix
A start-up failure now fails the waiting requests immediately and triggers the existing restart-with-backoff path.

Fixed — security

Each was verified against a running server before and after the fix.

S-1Anyone could read any scan's data without logging inCriticalFixed
Symptom
With no account and no password, anyone who knew (or guessed) a rack's short ID could download that rack's full device inventory, network topology, CMDB records and stored switch console transcripts.
Cause
Scan folders were published as plain static files, before any login check. This bypassed the secure-sharing system built for exactly this purpose.
Fix
Only genuine images are published now; all data files go through the logged-in API, which applies per-customer checks. Rack photos still load normally, so nothing in the app changed for users.
Proof
before → device_unit_map.json 200 OK, 15 devices after → device_unit_map.json 404 blocked after → original_image.jpg 200 OK (app still works)
S-2Accounts could be taken over by guessing the reset codeCriticalFixed
Symptom
The 6-digit password-reset code could be guessed an unlimited number of times, with no lockout. An attacker could take over any account, including the owner, without ever knowing the password.
Cause
The rate limit was applied to sign-in and password reset, but the endpoint that checks the code was left off the list.
Fix
All code-checking endpoints are now rate limited.
Proof
30 rapid attempts → 20 accepted, then 429 Too Many Requests (guessing stopped)
S-3Login codes were written into the system logCriticalFixed
Symptom
Every verification and password-reset code was recorded in plain text in the application log, which staff can read in the app. Anyone with log access could request a reset for any account, read the code, and take that account over.
Fix
The log now records only that a code was sent, never the code.
S-5Anyone could force the server to connect to your switchesCriticalFixed
Symptom
One endpoint had no login requirement at all. Any stranger could trigger the server to open SSH sessions to every monitored switch using the stored credentials, repeatedly.
Fix
Restricted to owners and administrators.
Proof
anonymous request → 401 Unauthorized
S-4The customer-separation check approved requests it should have deniedHighFixed
Symptom
The shared function that decides "may this person see this rack?" answered yes when there was no logged-in user, and again for accounts with no assigned site. Every protection built on it was therefore ineffective in those cases.
Fix
Both cases now deny by default. See R-5 below — this fix had a real consequence for installed apps.
S-6The CMDB "Approve" button skipped approval entirelyHighGated
Symptom
The app tells users that inventory is only written to the configuration database after a Service Request is approved. In reality the Approve button wrote to the database immediately and invented a fake ticket number when none existed. This contradicted the product's core compliance promise.
Fix
The instant-approval path is now off unless explicitly enabled for demos, and is owner-only. The genuine approval flow is unaffected. The dialog now explains that the Service Request must be approved in ServiceNow.
S-7Sellers could buy their own marketplace listingsHighFixed
Symptom
The guard preventing self-purchase was commented out, with the note "TODO: re-enable before production". Self-purchases created real orders, accrued platform fees and inflated revenue figures.
Fix
Guard re-enabled.

Fixed — crashes and correctness

C-4The Topology "Back" button never workedHighFixed
Symptom
Tapping "← Back" on the Topology screen did nothing, in every state. Users were stranded and had to navigate away manually.
Cause
The back action was defined in the parent screen, not the one drawing the button, so the button referenced something that did not exist.
C-5Marketplace orders could white-screen the appHighFixed
Symptom
Closing an order while a message or status update was still sending crashed the app to a blank page, recoverable only by a full reload. There is no error boundary, so any such crash takes down the whole interface.
Fix
Both paths now handle the closed-panel case; the message list defaults to empty rather than undefined.
C-2One bad photo could take down the processing engineHighFixed
Symptom
A photo where no devices were detected shut down the whole image-processing worker instead of failing that one request. Everyone's scans stalled for ~10 seconds while it restarted, and a bad configuration could make it restart in a loop.
Fix
The pipeline now raises a normal error the request handler can catch.
C-6Nine app requests carried no proof of identityMediumFixed
Symptom
Port selection and every feedback action were sent without credentials, so the server could not tell who made them and could not apply customer separation.
Fix
All nine now use the authenticated request wrapper.
P-1The owner console scanned the whole activity table every 5 secondsPerformanceFixed
Symptom
Fine today, but the cost grows with every recorded action — the dashboard would get progressively slower and eventually stall the server.
Fix
Added the three missing database indexes.

Regressions caused by these fixes — and corrected

Six fixes broke something else. All were caught by re-auditing the fixes and checking every caller of what changed. Recorded here in full, because this is the part a reviewer will most want to see handled honestly.

R-5"Rack not found" when searching for a port (reported by a tester)RegressionCorrected
Symptom
On installed app builds, Find Port returned "Rack not found" and every feedback action failed silently. The web app was unaffected.
Cause
Fix S-4 made the access check deny requests without credentials. Fix C-6 added those credentials — but only in the web client, after the app build had already shipped. Installed apps therefore sent nothing and were denied.
Lesson
Server-side authentication tightening breaks installed clients, not just the website. The client must ship first and be adopted before the server tightens.
Correction
Restored the previous behaviour for those six endpoints so installed apps work again. To be re-tightened once testers are on the newer build. All other hardening was re-verified as still in force.
R-1Feedback requests hung forever instead of answeringRegressionCorrected
Symptom
An anonymous feedback request never received any response — the connection stayed open until the client gave up. Left unfixed this is a way to exhaust the server's connections.
Cause
The newly-reachable denial branch tried to read a property of the (absent) user record and threw. Because of how this framework version handles errors in asynchronous handlers, no response is ever sent.
Proof
before → hung until timeout after → 404 in 0.0028 s
R-4Drift stopped working for everyone except administratorsRegressionCorrected
Symptom
Restricting the switch-monitoring endpoints to owners broke the member-facing Drift tab, which reads them — it would sit on "Waiting for first poll…" forever.
Correction
Reads are available to any signed-in user again; only the action that makes the server connect to a switch is restricted.
R-2iPhone photos vanished from marketplace listingsRegressionCorrected
Symptom
Uploading a listing photo from an iPhone appeared to succeed, but the image was permanently broken everywhere it appeared.
Cause
The new asset filter did not include HEIC — the default photo format on iOS.
R-3The lockdown missed the rendered reportIncompleteCompleted
Symptom
Fix S-1 blocked the raw data files but still served the generated report page and PDF — the same information, formatted — to anyone who guessed a rack ID.
Correction
Both are blocked. The app never used those URLs; it uses the secure sharing route.

Still open — honest list

O-1Switch inventory is not separated by customerHigh
Meaning
Any signed-in user can read the list of monitored switches belonging to any customer — names, locations, models, serial numbers.
Why open
The table has no customer column, so a correct fix is a database migration. Gating it instead would break the Drift feature for normal users (see R-4), so it was not bolted on.
O-2Rack photos are still reachable by guessing a rack IDHigh
Meaning
Data files are protected, but the photographs themselves are not.
Why open
Images are loaded by the browser in a way that cannot carry a login token. The proper fix is time-limited signed links, which requires a coordinated app change.
O-3Two integration routes lack per-rack ownership checksHigh
Meaning
The network-discovery and CMDB-ticket routes accept a rack ID without confirming the caller owns that rack.
O-4Four read-only endpoints need no loginMedium
Meaning
Incident lists and aggregate accuracy statistics are readable anonymously; two of them also consume processing capacity per request.
O-5eBay and Amazon "Connected" is not realMedium
Meaning
Connecting a seller account succeeds and shows "Connected", but the access token is discarded and no listing is ever published. The feature is unimplemented rather than broken — the interface should not claim otherwise.
O-6 · O-7 · O-8Three performance issues that grow with usagePerformance
Meaning
The scan list re-reads every scan from disk on each request; the dashboard re-reads the whole feedback log every 5 seconds; and the live camera view sends about 150 requests per minute into a 20-per-minute limit, so most are rejected and live detection stops working after a few seconds. All are acceptable at today's data volumes and degrade as they grow.
O-9 · O-10Dependencies and test coverageMedium
Meaning
Five dependency advisories (the one marked critical affects build tooling only, and is miscategorised as a runtime dependency). More importantly there are 3 automated tests for 214 endpoints — which is why a one-line change was able to break all scanning unnoticed.
