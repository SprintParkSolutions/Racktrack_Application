01 — Vision / Active learning

Cable identification on every connected port

Previously the app only classified the cable in the single port a user tapped. Now it identifies the connector and colour of the cable in every occupied port of the rack.

What it does Whole-rack cable inventory

After a scan completes, each connected port is tagged with its cable type, connector (RJ-45, LC, SC…) and colour. The device cards show these grouped as chips — e.g. RJ-45 Blue ×12, LC Aqua ×2 — with a real colour swatch.

How it works Background enrichment

  • Runs as a background pass after analyze, so the scan response stays fast; chips appear a moment later once enrichment lands.
  • Reuses the existing cable classifier and the exact 4× crop recipe already used for the single-port path — applied to every port whose status is connected (RJ-45 on copper, LC/SC on fibre). Empty and synthesised “ghost” ports are never given a fake cable.
  • Idempotent — a cables_enriched flag prevents redundant re-runs.
Under the hood
Pipelinepipeline/runner.py — new enrich_cables_on_map() + --enrich_cables mode; worker command enrich_cables in pipeline/worker.py
Classifierpipeline/cable.py · model Models/cable_eff_best (EfficientNet-B0, connector+colour)
ServerscheduleCableEnrichment(rackId) in server/app.js, fired from the canonical refresh; rewrites scan_result.json when done
ClientcableChips() + per-device chips in ResultsPage.jsx; short poll so enrichment appears without a manual refresh
02 — Vision / Active learning

Port-type correction that sticks

Technicians can now correct a port's physical type, and the system remembers and re-applies that correction on future scans of the same port.

What it does Tag & correct the port type

In the selected-port panel, a control lets the user set/correct the physical type from nine options — RJ45, SFP, QSFP, CONSOLE, AUX, MANAGEMENT_PORT, USB_A, USB_B, USB_C. Each correction is saved and feeds retraining.

How it works Closed learning loop

  • The correction is logged to feedback.jsonl and persisted as a perceptual-hash + embedding memory, keyed to the port's cropped image.
  • On a later scan, detection looks the port crop up in that memory and applies the learned type — mirroring the existing cable-colour learned-correction path.
Under the hood
Storeport_type added to VALID_MODELS in pipeline/active_learning/store.py
EndpointPOST /api/feedback/port-type — crops the port, logs feedback, fires the memory correction
Consumptionpipeline/runner.py select path — find_match("port_type", crop) applies the learned type
ClientPort-type tag/correct control in ResultsPage.jsx
03 — Vision / Active learning

Stop re-detecting a rack you've already confirmed

Once a technician confirms a rack is correct, re-scanning it serves the confirmed result instantly instead of re-running detection.

What it does Confirm once, reuse forever

A Confirm rack button fingerprints the rack photo. A later upload that perceptually matches returns the confirmed rack's result — no pipeline run — so the fixes already made are exactly what's shown.

How it works A perceptual cache

  • Extends RackTrack's existing content-hash cache into a perceptual one: a re-shot photo gets a new content hash (misses the plain cache), but a perceptual hash + ResNet embedding match it to the confirmed rack.
  • Safety: deliberately strict (near-duplicate only, 0.96 embedding threshold), organisation-scoped, and only paid for when the org actually has confirmed racks. A forceFresh flag always allows a fresh detection.
Under the hood
Storeadd_confirmed_rack / find_confirmed_rack in store.py (pHash + embedding); CLI commands in cli.py
EndpointPOST /api/scan/:rackId/confirm-layout
BypassGuarded lookup in /api/analyze (hasConfirmedRacks() gate + forceFresh escape); response carries servedFromConfirmed
ClientConfirmRackButton in the All Components header
04 — Input handling

Reject non-racks at the door

A photo of a person, laptop, or random object is now turned away before the full pipeline runs.

  • After the tilt/quality check, a fast detect-only pass runs. If zero rack devices are found, the upload is rejected with a clear message (kind: "not_a_rack") instead of spinning through a full analysis that returns nothing.
  • Runs on the normalised frame, so it works for both photos and videos. Best-effort: if detection errors, it falls through to the pipeline (whose own zero-device check still catches it).
Under the hood
ServerRack-presence gate in /api/analyze (server/app.js) using the worker's detect_only command
05 — New feature

Two-rack scan & inter-rack topology

Scan two racks — as two photos or one video — and see them side by side in 3D with the cabling that runs between them.

What it does Combined view with cross-rack links

The app detects each rack, groups them, and renders both in one 3D scene with the uplink cables spanning between racks plus a panel listing every inter-rack connection (device, port, cable type).

How it works Realistic synthesised uplinks

  • Most cabling stays inside each rack; only a realistic handful (2–3 core-to-core / ToR uplinks) cross between racks — deterministic, so the same racks always produce the same wiring.
  • Each rack's uplink end is its aggregation/core switch; adjacent racks are chained.
  • Optionally pushed to ServiceNow CMDB as dummy “Connects to” relationships between the two racks' switch CIs.

08 — Procurement

Sharper SFP procurement advice

The transceiver advisor is now more honest about when it can help — and more useful when there's no exact match.

  • Requires make & model. Without both it can't identify the switch, so it prompts for them (status: need_make_model) instead of guessing.
  • “No SFP required.” When a real datasheet shows only copper ports and no fibre/SFP slots, it returns status: no_sfp and the UI shows a clear message — it never claims “no SFP” without datasheet evidence.
  • Nearest match. When there's no exact listing, it falls back to a vendor-only search and then a generic reference model for the slot type, returning real, compatible modules (status: nearest_match).
Under the hood
Pipelinepipeline/sfp_recommend.py — make/model gate, specs_have_sfp() copper-only detection, restored two-stage fallback (search_sfp_vendor_only + generic reference)
EndpointPOST /api/sfp/analyze now requires both vendor and model
ClientSfpAdvisor.jsx — prompt / “No SFP required” / nearest-match note
Detection nuance: the copper-only check keys on concrete optical signals (SFP, QSFP, fibre, …BASE-SR/LR/LX/SX, combo) — deliberately not the word “uplink”, since copper uplinks exist. A 10GBASE-T (copper) switch correctly reads as “no SFP required.”
