RackTrack for NetBox

How a rack scan should reach NetBox: the technician compares the rack with NetBox, RackTrack identifies what is different, and the differences go to the NetBox administrator, who approves before anything is written.

Every fact is Verified with its proof under "Read more", or marked Estimate or To build.

Step 1 · TechnicianPartly exists

Compare

Scan the rack, then put the scan next to what NetBox already says about that rack.

What RackTrack does

  • Reads the rack back from NetBox: the devices, their positions, their ports and cables.
  • Lines each photographed device up with a NetBox device, strongest clue first: serial, then name, then model and U position, then port count.
  • Writes nothing. This step is read-only.

Step 2 · RackTrackPartly exists

Identify

Turn the comparison into a short list a person can act on, one line per difference.

The five kinds of difference

  • New: in the rack, not in NetBox.
  • Changed: in both, but moved, renamed or a different model.
  • Missing: in NetBox, not seen in the rack.
  • Conflict: the camera and the switch disagree. Never written to NetBox.
  • Unconfirmed: camera only, no switch reading. Written as "planned", not "connected".

Step 3 · AdministratorNot built

Pass to admin

The list goes to the person who owns NetBox. They approve, and only then RackTrack writes.

What RackTrack does

  • Stores the list as a pending request and emails the administrator.
  • On approval, creates and updates in NetBox. Never deletes. Safe to run twice.
  • A missing device is marked offline only if the administrator ticks it.
  • Records who approved what, and when, in the audit log.

Rules that never change

  • Preview before write. Every write is shown as a list first, and the list is exactly what will happen.
  • Never delete. A device that vanished from the rack is reported, not removed.
  • Conflicts are never written. A disagreement between the camera and the switch is a finding for a person.
  • Safe to repeat. Every object RackTrack writes carries its own tag, so writing the same rack twice updates instead of duplicating.
  • Nothing invented. A value no source stated stays blank.
Read more: proof these rules are in the code
server/lib/netbox/writer.js:1-20, the four rules: "1. IDEMPOTENT … 2. DRY-RUN FIRST. plan() performs no writes and returns the exact diff push() would apply. 3. NEVER DELETE. There is no delete path in this module or in the client it uses. 4. CONFIDENCE → STATUS. Proven becomes connected, camera-only becomes planned, and a CONFLICT is not exported at all". server/lib/netbox/netbox.js:8 "There is deliberately NO delete method on this class". The tag is the racktrack_uid custom field, netbox.js:15. "Nothing is invented" is reconcile.js:16 and the ReviewPage header.

Who does what

  • Technician: scans, compares, reads the list, sends it. Cannot write to NetBox.
  • Administrator (organisation admin or owner): sets up the NetBox connection once, receives requests, approves or rejects, decides about missing devices.
  • RackTrack: reads, matches, lists, waits, writes on approval, records.

This is the same shape the ServiceNow bridge already has: raise a request, wait for approval, then synchronise. NetBox gets the same gate.

Read more: the ServiceNow pattern this copies
docs/features/cmdb-registration-reconciliation-users.md §1: "RackTrack first raises a request (a ServiceNow Service Request) and only pushes the inventory once that request is approved. That approval gate is the whole point." server/cmdb_ticket_proxy.js: routes create, refresh, cancel, poll; a 5-minute poller sweeps open tickets.

Most of the machinery exists. What is missing is the middle and the end: a comparison against records the customer typed into NetBox themselves, one plain list of differences, and the administrator's approval. Today the report's Export sheet shows a preview and then writes straight away, and only the account owner can use it.

What the owner's own plan said

Verified

The NetBox build plan already asked for this shape. It called Review "the trust step: a tool that writes into a customer's system of record without showing its working will not survive its first mistake." It asked for a dry run before every write, for conflicts to be surfaced and never silently settled, and for files a person can read "before it touches their system of record". The compare and approval steps in this document are that plan carried to its end.

Read more: proof
/Volumes/Racktrack/racktrack_netbox/docs/PLAN.md, M2 Export: "Dry-run first. A diff of what would change, before anything is written"; "Universities want a file a human can review before it touches their system of record". M4 Reconcile: "CONFLICT — sources disagree — not exported … Surface it. Never silently pick a winner." M5 Review: "This is the trust step." The same repo has no compare module: its server/lib holds 19 entries (v1's server/lib/netbox holds 22), none named compare.

Six pieces, in this order. The first two make Compare and Identify honest; the next three make Pass to admin real; the last opens it to the people who will use it. Effort figures are estimates.

1. Compare against what the customer already has 3 days

Today the comparison only recognises objects RackTrack wrote earlier. A customer whose racks are already in NetBox, typed by hand, gets "everything is new" and a second copy of each device on write.

Build: read the rack's devices from NetBox by rack, then match each photographed device to a NetBox device strongest clue first: serial, name, model plus U position, port count. Adopt a match by writing RackTrack's tag onto that existing NetBox device, so the next scan recognises it. This is the same order the build plan set for reconcile.

2. One list of differences 2 days

The facts exist but are spread over the Preview counts, the Review page, the missing-device list and the warnings.

Build: one screen, five groups: New, Changed, Missing, Conflict, Unconfirmed. Each line says the device, the U position, and what is different, in words. Two buttons: Send to admin, Download as file.

3. Send to admin, approve, write 3 days

Nothing between Preview and Export today.

Build: a pending request stored on the server with the exact list; an approvals page for organisation admins and the owner; Approve runs the existing write and records the outcome on the request; Reject records the reason. The technician sees the request's state on the report: waiting, approved, written, rejected.

4. Tell the administrator 1 day

Nobody is told a rack is waiting.

Build: one email through the existing mail transport when a request is sent, and one back to the technician when it is approved or rejected. A badge on the admin's menu with the number waiting.

5. Audit trail and the missing-device decision 1 day

No audit entry says who wrote to NetBox, and a missing device can only be reported.

Build: audit entries for sent, approved, rejected, written, with counts. On the approval page, a tick box per missing device: "mark offline in NetBox". Only ticked devices are changed, and only to offline, never deleted.

6. Open it to technicians and admins 2 days

The whole NetBox area is owner-only because its scan and switch records are not yet tied to an organisation.

Build: apply the organisation guard that already exists in the code but is not yet used, then mount the area for every signed-in user, with write actions limited to admins and the owner. Until this is done, only the owner can run the flow at all.
Read more: proof
server/app.js:611-613 explains the owner-only gate and its reason. server/routes/netbox/scope.js exists (guards requireRack, visible() built on canAccessRack) and is not referenced by any other router: grep -rn "scope" server/routes/netbox/*.js shows only the file itself. Organisation admins already manage Data Sources at /api/org-connections.

Our firm positions

  • The technician never writes to NetBox. Only an administrator's approval does.
  • RackTrack never deletes in NetBox, and marks a device offline only when the administrator ticks it.
  • A conflict is shown, never resolved by the software.
  • Every write is preceded by a list, and the list is what gets written.
  • Records the customer typed into NetBox themselves are matched, never duplicated.

Total and order

Estimate about twelve working days, in the order above. Steps 1 and 2 can be shown on our own rack and NetBox on the demo box. Step 3 onward needs two accounts, a technician and an admin, which the seeded demo already has.

The ServiceNow bridge keeps its own request-and-approve flow. Both CMDBs end up with the same three steps, which is what the customer sees as one product.
