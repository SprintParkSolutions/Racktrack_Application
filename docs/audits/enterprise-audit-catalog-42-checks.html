1

Automated scanning

Robot checks that run every time the code changes. This is the area we've covered best — most of it is already green.

✓Static code scan (SAST) — reads our own code hunting for attack doors

Why we need it — Most break-ins happen because code accidentally trusts bad input. This scanner reads every line looking for those exact mistakes (database injection, file-path tricks, unsafe commands) before anyone can exploit them.

Where we are — Done. We ran it in two passes, including the full OWASP security ruleset. It raised alarms; we checked each by hand and confirmed no real holes in our code.

How it's done — The tool Semgrep scans the whole codebase in a couple of minutes. Next small step: make it run automatically on every change (about an hour of setup).

✓Library scan (SCA) — checks the borrowed code we build on

Why we need it — Every app is built on hundreds of pieces of free code written by others. When a security hole is found in one of them, everyone using it is exposed. This check compares our pieces against the public list of known holes.

Where we are — Done, both languages. Everything with an available fix was updated, and we re-ran all 240 tests to prove nothing broke. Two holes have no fix anywhere yet and can't be reached by an attacker — both written down.

How it's done — npm audit for the app/server, pip-audit for the AI. To keep it effortless, a robot called Dependabot can open the fix automatically the day a hole is patched (see "auto-update robot" below).

✓Secret scan — makes sure no passwords or keys hide in the code

Why we need it — If a password or key is ever pasted into code, anyone who can read that code can use it. This is one of the most common ways small teams get breached.

Where we are — Done. The current code is clean, and we checked every kind of sensitive file individually.

How it's done — The tool gitleaks reads the code and its whole past. It already runs on every change and blocks anything that looks like a secret, so this stays clean automatically.

○Live-app attack scan (DAST) — attacks the running app from outside

Why we need it — The code scan reads the blueprints; this one rattles the doors of the finished building. It catches problems that only appear when the app is actually running — bad security settings, session handling, misconfigured pages.

What's left & why — Not started, because it needs the whole app running live on a server with a database. We can't do it on a laptop.

How it's done — Once a test server exists, the tool OWASP ZAP points at it and fires real attack traffic, then reports anything that got through. Runs monthly.

◐Container scan — checks the shipping box the app runs in

Why we need it — The app ships inside a "container" — a packaged mini computer with its own operating system. That system can have its own holes, separate from our code.

Where we are — Partly. By hand we already found that the container runs as the all-powerful "root" user (it should run as a limited one) — but the automatic scan isn't wired in.

How it's done — The tool Trivy scans the container image on every build and flags holes and misconfigurations, including the root-user issue. About half a day to set up.

○Auto-update robot — fixes a library the day a hole is announced

Why we need it — New holes in borrowed libraries are found constantly. Without a robot watching, you only find out when someone runs a scan. With one, the fix is waiting for you the same day.

What's left & why — Not started. It's a single switch we simply haven't flipped yet.

How it's done — Turn on Dependabot in GitHub — one setting, about 30 minutes. From then on it opens a ready-made fix automatically.

—Infrastructure scan — checks cloud setup files

Why it exists — Big systems describe their servers in code ("infrastructure as code"). A scanner checks those files for insecure defaults before they go live.

Where we are — Doesn't apply. RackTrack runs on one server set up by hand, with no infrastructure code to scan. Revisit this only if you move to a cloud setup like AWS with Terraform.

2

Human-led security

The judgment work a robot can't do — a skilled person attacking the app and thinking about its design.

○Penetration test — a paid expert tries to break in

Why we need it — Scanners find known patterns; a human finds clever chains — logging in as one company and reaching another's data, or bypassing a check in a way no tool expects. This is also the report enterprise buyers ask for.

What's left & why — Not started. It needs the live app and an outside firm; it can't be faked on a laptop.

How it's done — Hire a security firm for about a week (a few thousand dollars). They follow a standard playbook (PTES / OWASP testing guide), include an explicit "can one company reach another's data?" test, write up findings, and re-test after you fix them. Done yearly.

◐Manual code review (security) — an expert reads the most sensitive code

Why we need it — Some things only a human understands — is the login logic sound? Are payments handled safely? A scanner can't reason about intent; a reviewer can.

Where we are — Partly. This week I read the login guard, token handling, sessions, sharing rules, upload limits and encryption by hand. What's not done is a full path-by-path review of the payment flow and every admin page.

How it's done — A security-minded engineer walks the critical paths line by line, ideally on every important change. No tool required — just focused time.

○Threat modeling — list what could go wrong, by design

Why we need it — Cheaper to imagine attacks on a whiteboard than to discover them in production. You map how data flows, then ask "how could each step be abused?" and add defenses up front.

What's left & why — Not started. It's a design exercise we simply haven't run yet; most valuable before big new features (like the payment or tenant model).

How it's done — A structured session using a standard method (STRIDE for security, LINDDUN for privacy across companies), producing a short list of risks and the fix for each. A day or two.

3

Security standards to measure against

These aren't tools — they're official checklists you formally sign off against, so "probably fine" becomes "checked, item by item."

◐OWASP Top 10 — the 10 most common web risks

Why we need it — It's the industry's shared list of the ten ways web apps most often get hurt. Everyone maps their security to it; buyers expect you to know it.

Where we are — Partly. Our scans and manual review touch most of the ten, but nobody has walked the list and formally signed off each item.

How it's done — Go through the current list (the 2025 edition) one risk at a time and record how RackTrack handles each. Half a day of documentation.

◐OWASP API Top 10 — the same, for the behind-the-scenes API

Why we need it — The app talks to a server through an "API" (the messenger between phone and server). APIs have their own top-10 risk list; the #1 is one user reaching another user's data by changing an ID in the request.

Where we are — Partly. We have ownership checks on data requests (good), but haven't formally tested every endpoint against the full list.

How it's done — Replay real requests as a different user / different company and confirm each one is refused, checked against the 2023 API list.

○ASVS Level 2 — the detailed 350-point security checklist

Why we need it — The Top 10 is awareness; this is the thorough version — about 350 specific, testable requirements. "Level 2" is the right depth for an app with logins, personal data and payments.

What's left & why — Not started. It's the structured way to turn our scattered checks into a signed, complete record — the kind of evidence a serious buyer or auditor wants.

How it's done — Work through the OWASP ASVS 5.0 Level 2 list, marking each requirement pass/fail/not-applicable, fixing the fails. A focused multi-day effort, usually paired with the pen test.

○MASVS (mobile) — the security checklist for the phone app

Why we need it — Phone apps have their own risks — how they store data on the device, use the keychain, handle the network. The web checklist doesn't cover these.

What's left & why — Not started. Matters more as the iPhone/Android app moves from testers to real customers.

How it's done — Verify against the OWASP MASVS mobile standard using its companion testing guide, typically as part of a mobile pen test.

○SAMM — how mature is our security process itself

Why we need it — This one scores your habits, not one app — do you threat-model, train, review, respond to incidents? It gives you a maturity grade and a roadmap to improve.

What's left & why — Not started. It's an organizational self-assessment, useful once the team and process grow.

How it's done — A yearly self-scoring against the OWASP SAMM model across five areas (governance, design, build, verify, operate).

4

Logins & who-can-see-what

How users prove who they are and stay locked to their own data. This is the area corporate IT scrutinizes hardest.

◐Password & session security — how logins are stored and kept safe

Why we need it — If passwords are stored carelessly or login tokens can be stolen, everything else fails. This checks hashing, expiry, and defenses against rapid guessing.

Where we are — Partly. Verified by hand: passwords are scrambled properly, login tokens are built and checked correctly, and guessing is throttled. One known weak spot: the login token sits in browser storage a script could read — the standard is a protected cookie instead.

How it's done — Review against the OWASP session-management standard; move the token to a protected cookie (best done together with company sign-in, below).

◐Company isolation test — can one company reach another's data?

Why we need it — Many companies share one system. The one thing that must never happen is company A seeing company B's data. It's the first question every buyer asks.

Where we are — Partly, and strongly. An automatic test proves the wall holds and re-proves it on every change. What's left is a deliberate outside attempt to break it (part of the pen test), not just our own test.

How it's done — Keep the automatic test; add a tester who deliberately tries to cross the wall by tampering with IDs in requests.

○Company sign-in (SSO) — "Sign in with Microsoft"

Why we need it — Staff use their existing company account instead of a new password. IT insists on it because when someone leaves, disabling one account locks them out of everything — including RackTrack. Without it, many companies literally cannot buy.

What's left & why — Not started, and it's the single biggest sales blocker on this whole page.

How it's done — Add sign-in through Microsoft using the standard protocols (OIDC / SAML). About 1–2 weeks; our customers are Microsoft shops, so start there.

○Auto account provisioning (SCIM) — create and remove staff accounts automatically

Why we need it — The step beyond sign-in: when a company adds or removes an employee in their own system, RackTrack accounts appear or disappear automatically. Big companies expect it so nobody is left with access after leaving.

What's left & why — Not started. Usually added after sign-in, when a large customer asks.

How it's done — Implement the SCIM standard so the company's directory can manage RackTrack accounts.

○Two-factor login (MFA) — a second check beyond the password

Why we need it — A stolen password alone shouldn't be enough to get in. A second factor (a code from an app, or a passkey) stops the vast majority of account takeovers.

What's left & why — Not started. Often comes for free once company sign-in is added, because the company's own two-factor applies.

How it's done — Support app-based codes or passkeys; aim for the standard "AAL2" level and avoid text-message codes (now discouraged).

5

Code quality, structure & staying up

Is the code clean, is the design sound, and can the system stay running under real use?

✓Code checker (lint) — flags mistakes and messy code

Why we need it — Consistent, mistake-free code is cheaper to maintain and less likely to hide bugs. The checker enforces it automatically so quality doesn't rely on memory.

Where we are — Done. Zero errors across the app and server, and the warning count is locked so it can only go down.

How it's done — ESLint runs on every change. A deeper option (SonarQube) can add complexity and duplication grades later.

✓Automatic tests — 240 checks that prove the app works

Why we need it — Tests catch a broken change before it reaches users. The more of the important behavior they cover, the safer every update is.

Where we are — Done. 240 tests across the app, server and AI all pass, plus a robot that clicks through all 13 screens in a real browser.

How it's done — Vitest, node:test, pytest and Playwright, all run on every change.

◐Test coverage — how much of the code the tests actually touch

Why we need it — "240 tests pass" is good, but which parts of the code do they actually exercise? A coverage number turns that from a guess into a fact, and shows the thin spots.

Where we are — Partly. The important parts are tested; the marketplace and integration bridges have few tests. The percentage is simply unmeasured.

How it's done — Switch on the built-in coverage counter, read the number, then lock it as a floor so it can only rise. About a day.

○Mutation testing — checks the tests actually catch bugs

Why we need it — A test can run a line of code without really checking it. This tool deliberately breaks the code and watches whether the tests notice — proving they have teeth, not just presence.

What's left & why — Not started. It's an advanced, optional depth check — worth it for the most critical logic once coverage is measured.

How it's done — The tool Stryker introduces small bugs and reports how many the tests caught. Run weekly, not on every change (it's slow).

◐API design & contract — is the server's interface clean and documented

Why we need it — The API is the contract between the app and the server (and any future integrations). A consistent, documented, rate-limited interface is easier to maintain and safer to expose.

Where we are — Partly. The API works and has rate limits, but there's no formal written spec that documents every endpoint.

How it's done — Write an OpenAPI spec (a machine-readable menu of every endpoint) and lint it for consistency. Ongoing as the API grows.

◐Architecture & data-safety review — can a crash lose or corrupt data?

Why we need it — The most damaging failures aren't hacks — they're a design where a crash at the wrong moment corrupts or loses customer data.

Where we are — Partly, and this found something real: a scan is saved in two separate steps (the images, then the ownership record). A crash between them leaves a scan with no owner — the code even carries repair scripts because it has happened.

How it's done — Move to a proper database where both steps save as one all-or-nothing action (see "real database" in domain notes on the status report). This is the highest-value fix on the roadmap.

◐Speed & load-time check — how fast the app feels

Why we need it — A slow app frustrates technicians standing in a datacenter aisle on weak signal. There's a standard score for load speed and responsiveness.

Where we are — Partly. The browser robot catches layout problems, and we flagged that the app downloads one oversized code bundle. No formal speed score exists yet.

How it's done — Run Google Lighthouse for a score, set a bundle-size budget, and split the code by screen so each loads only what it needs.

○Load / stress test — how many users before it strains

Why we need it — The AI scan is heavy work. Nobody yet knows whether 30 technicians scanning at 9 a.m. is fine or crashes the one server. Sales will eventually be asked "how many users does it support?"

What's left & why — Not started; it needs the test server first, so the real system isn't disturbed.

How it's done — A tool like k6 fires many pretend users at once and measures where it slows or breaks. A few days.

○Monitoring & recovery — know when it breaks; be able to recover

Why we need it — Today, if the app goes down at 2 a.m., a tester tells you hours later. Real customers expect it to be watched, and expect proof you could recover from a disaster.

What's left & why — Not started. The measuring instruments (logs, performance meters) already exist — they just don't alert anyone yet.

How it's done — An uptime monitor that messages your phone in a minute, plus crash reporting (Sentry). Set target uptime goals and do a practice recovery. About 2 days for the basics.

○Database & backup check — is data safe, and can we restore it?

Why we need it — A backup nobody has ever restored is just a hope. This confirms the data is stored soundly and can actually be brought back after a disaster.

What's left & why — Not started, and important: right now nothing is backed up at all. If the disk dies, everything is gone.

How it's done — Move to a proper database, turn on nightly off-site backups, then do one real restore drill to prove it works. Part of the "real database" project.

◐Delivery health (DORA) — how smoothly we ship updates

Why we need it — There are four well-known measures of a healthy team: how often you ship, how fast, how often a release breaks, and how quickly you recover. They reveal whether delivery is smooth or risky.

Where we are — Partly. Automated checks are strong, but deploys are still by hand with no undo — which these measures would score low, and which the roadmap fixes.

How it's done — Track the four numbers from your GitHub history; they improve automatically once staging and one-button deploys exist.

◐App-store readiness — meets Apple & Google's rules

Why we need it — Apple and Google reject apps that break their rules — crashes, missing privacy details, outdated targets. A rejected app can't ship.

Where we are — Partly. The app is already on TestFlight and builds as a signed Android app. One firm deadline to note: Google requires apps to target the latest Android by Aug 31, 2026.

How it's done — Run through Apple's and Google's published checklists before each submission; keep a crash-reporting tool watching the live crash rate.

6

Compliance & paperwork

The certificates and documents enterprise buyers and regulators ask for. Mostly process, not code — and correctly started when a real deal appears, not before.

○SOC 2 — the security report buyers ask for first

Why we need it — In North America it's the entry ticket to selling to big companies — an independent report saying your security controls are real and working. Buyers ask for it before signing.

What's left & why — Not started, and that's fine now. It's a months-long program with real cost; you start it when a genuine enterprise deal is on the table.

How it's done — Adopt a controls-tracking tool (Vanta / Drata), run for a 3–12 month observation window, then a licensed auditor writes the "Type II" report. Roughly $20K–$150K all-in the first year.

○ISO 27001 — the international security certificate

Why we need it — The global counterpart to SOC 2 — a pass/fail certificate that EU, UK and Asian buyers prefer. It proves you run a real security management system, not just ad-hoc controls.

What's left & why — Not started. It overlaps ~70% with SOC 2, so many companies do both together; pursue when selling internationally.

How it's done — Document a security management system, pick your controls, then an accredited body audits and certifies you (3-year cycle with yearly check-ins).

○PCI (card payments) — SAQ A — the light payment-security form

Why we need it — Taking card payments legally requires a yearly security self-assessment. The good news: because Stripe handles the card details, you qualify for the lightest version.

What's left & why — Not started, but it's a quick win — as long as you keep card entry fully hosted by Stripe (their checkout or redirect), you stay on the short form.

How it's done — Fill in the "SAQ A" questionnaire once a year and get Stripe's written confirmation that their embedded payment is protected. Mostly internal time; near-zero cost.

○Privacy (GDPR / CCPA) — how personal data is handled

Why we need it — If you store data about people in Europe or California, the law requires clear rules on how it's collected, stored, and deleted — and the ability to honor deletion requests. Fines are large.

What's left & why — Not started. It's law, not a buyer preference, and applies as soon as you have EU or California users.

How it's done — With privacy counsel: a data-processing agreement, a record of what data you hold, a deletion process, and a risk assessment for anything sensitive.

○Vendor security questionnaire — the form buyers actually send you

Why we need it — Before signing, a company's risk team emails a long spreadsheet of security questions. Having good answers ready wins deals faster; having none stalls them.

What's left & why — Not started. Comes with your first serious enterprise conversation.

How it's done — Pre-fill the two standard ones (SIG, CAIQ) and host a "trust page" so buyers can self-serve. SOC 2 makes these far easier.

○Parts list (SBOM) — a signed list of everything you ship

Why we need it — Like an ingredients label for software — a complete list of every component inside. Increasingly required in regulated and government sales (the EU makes it mandatory by end of 2027).

What's left & why — Not started, but it's a genuine quick win — it generates automatically from files you already have.

How it's done — A one-step tool (Syft or Trivy) produces the list on every release in a standard format. Under an hour to wire in.

7

Accessibility & our specific field

Usable by everyone, and correct for the datacenter world RackTrack operates in.

◐Web accessibility (WCAG) — usable with a screen reader & keyboard

Why we need it — People with disabilities must be able to use the app — enough contrast, keyboard navigation, screen-reader labels. It's increasingly the law: the EU's Accessibility Act took effect June 2025 and reaches US companies with EU customers.

Where we are — Partly. The browser robot already enforces some of it (readable text sizes, no sideways scrolling), but a full audit with a screen reader hasn't been done — and automated tools only catch about a third of the criteria.

How it's done — Automated scan (axe / Lighthouse) plus manual testing with a screen reader, against the WCAG 2.2 AA standard. Produces a "VPAT" statement buyers ask for.

○Mobile accessibility — works with VoiceOver & TalkBack

Why we need it — Phones have their own screen readers (VoiceOver on iPhone, TalkBack on Android). The app needs to work with them, tested on a real device.

What's left & why — Not started. Done per release once the mobile app has real users.

How it's done — Walk the core journeys on a device with the screen reader on, plus large-text and high-contrast modes.

◐AI accuracy report — how often the scanner is right

Why we need it — RackTrack's core promise is that the AI reads racks correctly. Enterprise buyers of an AI product will ask, in writing, "how accurate is it, and how often is it wrong?"

Where we are — Partly. A ground-truth set and pipeline tests exist, but there's no published accuracy / false-alarm report.

How it's done — Measure the model against a labeled truth set (precision, recall, false-positive rate), publish the numbers, and watch for "drift" over time — governed by the NIST AI risk framework.

○Integration data quality — is the data we send ServiceNow clean?

Why we need it — RackTrack feeds a customer's IT database (ServiceNow). If it creates duplicates or wrong entries, it damages trust in the whole system.

What's left & why — Not started. Matters as real customers connect their live ServiceNow.

How it's done — Check the data against ServiceNow's completeness/correctness rules and tune the matching so it never creates duplicate entries; a formal "Built for ServiceNow" certification exists for listing in their store.
