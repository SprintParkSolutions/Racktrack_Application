B

Findings — stated plainly, before anyone else finds them

A serious audit turns up things. Here is everything the deep scans surfaced — two small items to fix, and the scary-looking alarms that proved harmless on inspection.

▲M1 · The shipping container runs as the top-level "root" user — hardening gapMEDIUM

What we found: the Docker container that runs RackTrack starts as root — the all-powerful user. Recommended practice is to run the app as a limited user with only the permissions it needs.

Why it matters: if an attacker ever got in, running as root would let them do far more damage inside the container than a limited user could.

The fix: add two lines to the Dockerfile — create a normal user and switch to it before the app starts. About 1 hour, and a container scanner (Trivy, below) checks for it automatically.

▲L1 · A printed report builds HTML by hand in a few spots — low risk, worth tidyingLOW

What we found: the combined "two-rack" printable report assembles its HTML by hand. The user-entered values (rack labels) are properly cleaned before insertion — we checked. One spot inserts an internal error message without cleaning.

Why it is low: that report is generated for, and viewed by, the same signed-in user who owns those racks — there is no path for one user's input to reach another user's screen. The realistic worst case is a user affecting only their own printout.

The fix: run the error text through the same cleaning function already used two lines above. About 15 minutes.

✓The scary-looking alarms that proved harmless — every one checked by handCLEARED

Flagged by the scanners, then individually verified as safe — so nobody has to wonder about them later:

9 "database injection" alarms — four are log messages the tool mistook for database commands; the rest use fixed, code-defined column names with safe parameter binding. No user input builds a query.

17 "file path" alarms — every one is guarded upstream: a rack ID must match a strict pattern (RK- then letters/numbers) and the caller must be proven to own that rack before any file is touched.

1 "weak encryption" alarm — the code uses AES-256-GCM (a strong, modern standard) correctly, with the authentication tag properly set. Safe.

4 "weak hash (SHA-1)" alarms — SHA-1 is used only to name cache files and de-duplicate lookups, never to protect anything. A normal, safe use.

1 "cross-origin" alarm — the sharing rules are strict by design: same-origin only, and login tokens are never attached as ambient cookies. Correct as written.

1

Security

Strong foundations, verified by scanners and by hand.

✓Login is protected against password-guessing — per-account rate limiting

Verified by reading the code: login and password-reset endpoints throttle attempts per account (about 10 a minute). An attacker cannot rapidly guess passwords — and because it is keyed per account, not per network, real testers sharing one office connection do not lock each other out. The reset path is throttled too.

✓Login tokens are correctly built and checked — hardened against a known trick

Verified: login tokens are signed with a strong random secret, they expire, and the code checks them with an explicit list of allowed signing methods — closing a well-known attack where a forged token claims "no signature needed." The developer left a comment explaining exactly why. That is security maturity, not luck.

✓Passwords hashed, device logins encrypted, responses hardened — nothing readable at rest

User passwords stored scrambled (bcrypt) — unreadable even with the whole database in hand. Saved device logins encrypted with AES-256-GCM, verified correct. Every response carries helmet's standard browser protections. Uploads are size-capped so one huge file cannot exhaust the server. Secret scan of the shipping code: clean.

→Outside attack test + security paperwork — pen test, SLA, SOC 2

Missing: a paid outside firm attacking the live app and writing the report buyers ask for (a pen test, ~a week, a few thousand dollars, yearly), a written uptime promise (SLA, possible once monitoring exists), and the SOC 2 certificate (months long — start when a real deal demands it). At pilot stage, "not yet — here is the plan" is a fine answer; this report is that plan.

2

Access

The right people see only their own company's data — mostly built and proven; company sign-in is the missing piece.

✓Company walls — proven, not promised — company A can never see company B

Many companies share one system; each sees only its own racks, scans, and people. An automatic test creates two companies and proves one cannot read the other — re-proven on every change. On top, every request carrying a rack ID must pass an ownership check before any data is returned.

✓Roles and a full record of actions — owner / admin / member + audit log

Admin pages check who is asking before answering — an organization's dashboard responds only to its owner or admin. The server records who did what and when, including failed logins — the exact trail security teams ask to see.

→Company sign-in (SSO) — the one feature that blocks corporate sales

What it is: "Sign in with Microsoft" — staff use their existing company account. IT departments require it because disabling one account instantly locks a departing employee out of everything, and company password/2FA rules apply automatically.

The firm truth: a yes/no box on corporate purchase forms — without it, many companies cannot buy. Fix: Microsoft sign-in first (our customers are Microsoft shops), and move the login token into a browser-protected cookie at the same time. ~1–2 weeks.

3

Code quality

Clean and tested — machines enforce it on every change, so quality cannot slip backwards.

✓0 errors — and the code can only get cleaner — an enforced ratchet

The standard checker read every file — zero errors. Minor warnings are counted and locked at today's number: add one and the build fails; fix one and the lock drops. The code can only improve, enforced by the machine.

✓240 automatic tests — all passing — app, server, and AI, each proven separately

App (53): safety logic — checking uploads, safe storage, refusing dangerous links. Server (86): company walls, caching, crash recovery, attachments, full start-up wiring. AI (101): port numbering, panel counting, device matching — pure math, no GPU. A change that breaks any of these cannot reach users.

✓A robot tests every screen on every change — real app, real browser, phone-sized

A robot builds the real app, opens it at iPhone width, logs in, and visits all 13 screens. It fails the build on a blank screen, an icon shown as text, sideways scrolling, any browser error, or an input small enough to trigger annoying zoom. Normal tests can pass while the app looks broken on a phone — this catches exactly that.

✓One codebase → iPhone, Android, web, clean 3.3 s build — fix once, fixed everywhere

One codebase ships as iPhone (TestFlight), signed Android, and web. Same screens, same logic. The build is clean in 3.3 seconds, and the phone build refuses to package itself if pointed at the wrong server.

→Measure test coverage & speed up first load — two known tidy-ups

Coverage: 240 tests pass, but the percentage of code they touch is unmeasured; the important parts are covered, the marketplace and integration bridges less so. Switch on the built-in counter and lock it as a floor — ~1 day.

Load speed: the app downloads one large code package on first load, heavier than recommended. Split it by screen so each loads only what it needs — ~2–3 days.

4

Vulnerability scanning

Five scanner types, five angles: borrowed libraries (JS + Python), our own code, the container, and the live app. Three ran today; two more need wiring.

✓Borrowed libraries (JS + Python) — clean or patched — npm audit + pip-audit

JavaScript: every library checked against the public hole-list; everything fixable was fixed, then all 240 tests re-run. Two exceptions documented — one has no fix anywhere (install-time only, no attacker reach), one needs a planned framework upgrade. Python: the AI's full library set — zero known holes, clean first run.

✓Our own code — deep scan done, 2 items caught — Semgrep OWASP + container rules

Two passes of Semgrep — the basic security set, then the full OWASP-Top-Ten plus Python and container rules — raised ~60 items. Every one was reviewed by hand: it caught the container-runs-as-root issue (M1) and the hand-built report HTML (L1) above; everything else cleared. Next: make this scan run automatically on every change — ~1 hour.

→Two more scanners + an update robot to switch on — container, live-app, auto-updates

Trivy scans the shipping container for operating-system holes and would flag the root-user issue automatically — ~half a day. OWASP ZAP attacks the running app monthly like a real attacker — needs the test server first. Dependabot opens a ready-made fix the day any library patches a hole — one GitHub setting, ~30 minutes.

5

Running it for real customers

Where the serious gaps are. The code is proven good; the machinery around it is still pilot-stage. Each gap has a clear fix and price.

✓Quality enforced automatically on every change — 4 gates + a weekly self-check

Every change must pass four gates before it lands — secret hunter, all tests + checker + build, the robot browser sweep, and the AI tests on a fresh machine. Every Monday the whole set re-runs untouched, catching a library that quietly broke during a calm week. The logs and performance meters are already installed — the only missing half is sending an alert to a human.

→A real database, with backups — the most serious operations gap

Today: account data lives in a single database file, and each scan is a folder of images on disk. Saving a scan takes two separate steps — folder, then owner record. A crash between them leaves a scan with no owner. Not a theory: the code carries repair scripts written because it happened, plus a cleanup job that can delete a scan it wrongly thinks is garbage.

Worse: nothing is backed up. If the disk dies today, every scan and account is gone forever.

Fix: PostgreSQL, where scan and owner save as one unbreakable step, plus nightly off-site backups and one practice restore. ~2–3 weeks. The highest-value work on this page.

→Alerts, a test server, and load testing — the reliability trio

Alerts: today, if RackTrack goes down at 2 a.m., a tester tells you hours later. An uptime monitor + crash reporter (Sentry), wired to the logs that already exist, fix that — ~2 days.

Test server + safe deploy: updates are copied by hand to the one server testers use, with no undo. A staging copy, a deploy button in the automation we already have, and one-command rollback — ~3–4 days.

Load test: nobody yet knows if 30 technicians scanning at 9 a.m. works or crashes the server. A load-test script finds the ceiling — the number sales will be asked for — ~2–3 days, after staging exists.

→Back up the Android signing key — one copy, one laptop

Every Android update must carry the same signature as the first install, and the key that makes it exists on exactly one laptop with no copy. If that disk dies, no install can ever be updated — every tester reinstalls from scratch. Fix: copy the key and its password to a password manager and one offline place. ~1 hour — the cheapest risk removal in this report.

The fix order — highest risk and lowest effort first

  1. Back up the Android signing key ~1 hour
  2. Run app as non-root (M1) + tidy report HTML (L1) ~1.5 hours
  3. Switch on Semgrep-in-CI, Dependabot, Trivy ~1 day
  4. Alerts — uptime monitor + crash reports ~2 days
  5. Test server + one-button deploy with undo ~3–4 days
  6. Measure test coverage, lock the floor ~1 day
  7. Real database + nightly backups + restore drill ~2–3 weeks
  8. Company sign-in (SSO) + safer login tokens ~1–2 weeks
  9. Load test for the capacity number ~2–3 days
  10. Paperwork — pen test → SLA → SOC 2 ongoing

The bottom line: twelve professional audit methods examined this codebase. The code quality and test results are green with nothing to argue about. The security review turned up exactly two findings — one medium, one low — both named here, both fixable in hours. Everything else is operations and access work: about six weeks, listed in order. There are no unknowns left on this page — which is the point of a real audit.
