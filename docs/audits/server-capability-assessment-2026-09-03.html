Server capability gaps

Thirteen claims about what the RackTrack server cannot do, each checked in the source and probed against the live API before being written down. Ten are confirmed, two were right in substance but wrong in detail, and one was refuted and struck.

2

Remediation plan

Ordered by what it unblocks per day of work. The four small items in stage one carry no schema migration between them and each closes a hole a customer meets in their first week.

Stage 14 items · ~3 days
SRV-01, SRV-02, SRV-03, SRV-04

Role and scope corrections. No migrations. Each is a handler or a scope change in a file that already contains the pattern to copy. Together they make the manager and site manager roles usable as sold.

Stage 22 items · ~1 week
SRV-05, SRV-07, and SRV-12 alongside

Appointing a manager, and the device index. The index is the one gap that changes what the product can claim, and its read side reuses a cross-rack walk that is already written. The poller status field is an hour of work and should ride along.

Stage 33 items · ~2 weeks
SRV-06, SRV-08, SRV-09

Durable schema decisions. Rack placement and alerting each need a policy answer before code: what a rescan inherits from the cabinet it replaced, and what is worth waking somebody for. Site rename is small and belongs in the same pass as placement.

Stage 4When sold
SRV-10 scheduling, SRV-11 single sign-on

Neither blocks a customer today. Both are large, and both are better specified against a signed requirement than against a guess.

3

Findings

SRV-01

No organization scope on the audit log

BlockingEffort S

The audit log offers three scopes: your own events, one site, or everything. There is nothing in between, and the two wider scopes are unlocked by a username listed in an environment variable rather than by the role on the account.

What exists

GET /api/audit accepts scope=self, tenant or all. The second and third check AUDIT_ADMINS, a comma-separated list of usernames. A caller not on it is dropped one level silently, with no error.

Observed impact

  • An org admin on the shared default site sees two unrelated customers' users and none of their own sixteen technicians
  • No per-organization activity view is possible
  • An owner not on the list is downgraded to their own events

References

  • server/app.js:3191 the gate is AUDIT_ADMINS.includes(req.user.username), with no reference to role
  • server/app.js:3205 only userId and tenantId reach the query; there is no organization branch
  • server/audit.js:221 query() accepts those two filters only, with no join to tenants or users

Remediation

Add a fourth scope, org, and gate the ladder on role: owner may request everything, org admin is capped at their organization, everyone else remains on self. Audit rows already carry tenant_id, so the organization filter is a join to tenants. No migration.

SRV-02

A site manager cannot list their own people

BlockingEffort S

A site manager may create a technician, deactivate one, reset a password and remove an account, all correctly scoped to their own site. They cannot see who is on it, so every write they are permitted is addressable only by an id they have no way to look up.

What exists

Three write routes admit a site manager and authorise against their own site. The single listing route, GET /api/orgs/:orgId/members, is restricted to owner and org admin and answers a site manager with 403.

Observed impact

  • A site manager cannot find anyone an org admin added
  • They cannot deactivate a leaver they did not create themselves
  • No site-scoped people view is possible in any client

References

  • server/auth.js:1957 the route is requireRole('owner', 'org_admin')
  • Live probe as a site manager on site 14: GET /api/orgs/13/members returned 403
  • server/*.js the only two :siteId routes in the server are both POST

Remediation

Add GET /api/sites/:siteId/members beside the existing POST, guarded by the canManageSite helper already in the file, running the same query with WHERE u.tenant_id = ?. No migration.

SRV-03

Invites cannot be listed or revoked

LimitingEffort S

An invite link is returned exactly once, in the response that creates it. After that the invite is invisible: nobody can see who has one outstanding, resend a link that never arrived, or cancel one sent to the wrong address.

What exists

Three routes: create for a site, read a single invite by its code, and accept. The invites table already stores email, role, site, sender, creation time, expiry and acceptance time.

Observed impact

  • No pending-invites view in any client
  • A lost link cannot be resent, only replaced
  • An invite sent in error cannot be cancelled

References

  • server/auth.js:2123 creates the invite and returns the code once, at line 2144
  • server/auth.js:2148 reads one invite by code; there is no collection form
  • server/auth.js:392 the table already carries every column a listing needs

Remediation

Two handlers beside the existing block: a list for a site and a delete for a code. No migration.

SRV-04

Multi-rack captures are scoped by site, not by role

LimitingEffort S

Every rack-group route compares the group's site id to the caller's own and never consults their role, so a supervisor is shown the groups of whichever customer shares the legacy default site and receives a 404 on their own organization's two-rack scans.

What exists

Five read routes, each guarded by one hand-written equality on tenant_id. The scan list beside them already scopes correctly by role using the shared tenant helpers.

Observed impact

  • The two-rack feature fails for the people who supervise it
  • The combined report 404s for the same user whose rack list shows the member racks
  • Groups from another organization appear in the list

References

  • server/app.js:5419 if (group.tenant_id !== req.user.tenant_id) return 404, no role or membership test
  • server/app.js:5460 the list passes one tenant id into WHERE g.tenant_id = ?
  • server/lib/rack_groups.js:45 the query has no scope parameter

Remediation

Replace the equality with the scope helper the scan list already uses: a set of site ids for an org admin, unrestricted for the owner. Both columns exist. No migration.

SRV-05

Org admin cannot be granted through the API

BlockingEffort S

Role changes are capped at site manager and member for every caller, including the platform owner. An organization therefore has exactly the one org admin created with it, and a second manager can only be appointed by creating another organization.

What exists

POST /api/orgs creates an organization together with its first org admin. PATCH /api/orgs/:orgId/members/:memberId accepts a role but validates it against a two-value list.

Observed impact

  • A deputy manager cannot be appointed
  • Handover when a manager leaves has no supported path
  • A manager account created for a customer has to be made at organization-creation time or not at all

References

  • server/auth.js member PATCH: if (!['site_manager','member'].includes(role)) return 400 'Role must be member or site_manager'
  • Live probe as platform owner, promoting a site manager to org admin: 400 with that same message
  • The handler does distinguish an owner caller elsewhere, so the ceiling is the validation list, not the permission model

Remediation

Admit org_admin to the accepted list when the caller is an owner, and keep the existing rule that an org admin may not edit another org admin. One line of validation, plus a test. No migration.

SRV-06

A rack has no name, row or height

BlockingEffort M

A rack is the content hash of the photograph that produced it. There is nowhere to record what the cabinet is called, which row it stands in, or how many units tall it is, so two scans of one cabinet are unrelated rows in a list ordered only by time.

What exists

Four rack tables, all of them ownership: which site claimed the rack and when. The scan result describes the inside of the rack in detail, including per-device unit positions, while the rack itself has no identity beyond its hash.

Observed impact

  • No floor plan or spatial view
  • No cabinet name on a report
  • No sorting or filtering by site, row or position
  • 254 unrelated rows on the live server where there are far fewer cabinets

References

  • auth.db holds 22 tables; none is a placement or cabinet table
  • server/auth.js:276 the rack record is (tenant_id, rack_id, created_by, created_at)
  • server/app.js:864 the rack id is derived from the image bytes, so a rescan produces a new id
  • server/demo_topology.js:10 already names a future rack_placement table as the intended fix

Remediation

A rack_placement table keyed on site and rack, holding name, building, floor, row, position and height, with a helper module modelled on the existing tenant scoping. The second half is the real work: because the id follows the photograph, a durable cabinet identity is needed so a rescan inherits the placement of the cabinet it replaced.

SRV-07

No device inventory across racks

BlockingPartly builtEffort M

Devices are files, not rows. Every device lives inside its own rack's result on disk and there is no devices table, so a question as ordinary as how many switches the estate holds means fetching every rack result into the client and adding them up.

What exists

More than the claim allowed for. GET /api/ground-truth/queue already walks every rack a caller may see and returns devices across all of them, with correct role scoping. It is owner-only, hides reviewed devices and caps at 500 rows, so it cannot serve as an inventory, but the cross-rack walk does not need writing from scratch.

Observed impact

  • No asset list across the estate
  • No search by make, model, firmware or serial
  • No counts by vendor or class per organization or site
  • Measured cost of the client-side alternative: about 4 MB and roughly a minute

References

  • server/app.js:6528 the scan list returns per-rack totals only, never device rows
  • server/app.js:7084 the only route returning device identity serves exactly one rack, from a file
  • server/app.js:6708 the ground-truth queue already carries role-correct rack scoping

Remediation

Begin with the read side, reusing the existing walk: a paged GET /api/devices with filters. That alone unblocks the client. A devices table written at scan time is the durable answer and can follow, since it indexes data the pipeline already produces.

SRV-08

A site can be created but never changed or removed

LimitingEffort M

There is no route to rename a site, move it between organizations, or delete it. A site created with a typo carries it permanently, and the only way to remove one is to delete its entire organization along with every member, invite and rack claim.

What exists

Two site routes: list and create. Organizations by contrast have a full lifecycle, with rename, status, approve, reject and delete.

Observed impact

  • A mistyped site name is permanent
  • A closed location cannot be retired
  • A site cannot follow a reorganization

References

  • server/auth.js:1932, 1944 are the only two org-scoped site routes; neither is PATCH or DELETE
  • server/*.js searching for :siteId returns exactly two hits, both POST
  • Sign-in matches a site by slug or name, so a rename must leave the slug alone

Remediation

Rename is one route and one update. Delete is what makes this medium: eight tables carry a site id and a policy is needed for a site that still holds members and scans. A move must also re-point its members' organization.

SRV-09

Nothing raises an infrastructure alert

BlockingPartly builtEffort L

No one is told when anything breaks. A switch that stops answering backs off quietly and, once it recovers, leaves no record that it ever failed, so an overnight outage is invisible by morning.

What exists

Two pieces, both real and both pointed elsewhere. A rules engine with named thresholds and severity levels runs at report time for a single rack and persists nothing. A complete alert table with raise, deduplicate, read and dismiss already exists for the marketplace. Neither ever sees a switch or a scan.

Observed impact

  • No notification, by mail or in the product
  • No unread count for infrastructure
  • A failure that self-heals leaves no evidence

References

  • auth.db the only table with alert in its name belongs to the marketplace
  • server/lib/report_insights.js:31 five named thresholds producing critical, warning and clear verdicts, then discarded
  • server/lib/port_poller.js:227 a failing switch enters backoff without recording an event

Remediation

An alerts table copying the raise-and-deduplicate shape the marketplace already uses, fed from the three places that already know something is wrong: the poller, the scan pipeline and the report rules. Delivery by mail is a separate decision and should not hold up the record.

SRV-10

Reports stop at one rack

LimitingPartly builtEffort L

Four report routes exist and every one is a single rack or a single capture. Nothing aggregates across a site or an organization, and there is no scheduler anywhere in the server.

What exists

One renderer with five outputs selected by a format parameter: a summary, a self-contained web page, a PDF, JSON including the device list, and a CSV covering ports and feedback but not devices. The claim that there is no device export was wrong for JSON.

Observed impact

  • No estate-wide or site-wide report
  • No device inventory export to a spreadsheet
  • No weekly digest or scheduled delivery

References

  • server/app.js:5689, 6833, 6843, 6910 are the only four report routes; all single-rack or single-group
  • No scheduler exists: searching for schedule, cron or digest across the server returns nothing
  • Live probe every plausible organization or site-wide report URL returned 404 as the platform owner

Remediation

Three separable pieces, smallest first. Add a devices section to the existing CSV, a change to one function. Then an organization-wide report, which depends on SRV-07. A scheduler is the largest part and is genuinely new ground.

SRV-11

Security policy is server-wide

LimitingEffort L

Password rules, session lifetimes and the sign-on provider list are constants shared by every organization. There is no API token facility and no webhooks. The organizations table holds an id, a slug, a name, a creator, a timestamp and a status.

What exists

One organization-level control that does work: an owner can switch a whole organization off, and every request from its users is refused until it is switched back on.

Observed impact

  • No customer can be told their own security rules apply
  • No enterprise sign-on onboarding
  • No integration can authenticate as the organization rather than a person

References

  • server/auth.js:460 password validation is a fixed ladder taking one argument, so no organization can reach it
  • server/auth.js:61 session lifetimes are two environment variables, server-wide
  • auth.db has no policy, token or webhook table

Remediation

An org_policies table keyed on the organization, threaded through the six places that validate a password and the two that mint a session, with separate tables for tokens and webhooks. Split this: password and session policy is useful on its own, and single sign-on is a project.

SRV-12

A skipped poll is not distinguishable from a silent one

QualityPartly builtEffort S

The poller stamps a poll time on switches it never contacted, 900 times on the live server. It does not report them as healthy, because every screen derives health from the separate last-seen clock, but nothing records why a switch is silent, so no client can say that credentials are missing rather than that the device is down.

What exists

Two clocks, correctly kept apart: one for when the poller reached the row, one for when a poll actually returned data. Missing credentials and a missing vendor recipe both stamp the first and leave the second, which is the right behaviour, silently.

Observed impact

  • Four switches on the live server read as silent with no reason given
  • An operator cannot tell a configuration problem from an outage
  • A poll that connects but parses nothing is still recorded as a success

References

  • server/lib/port_poller.js:200 missing credentials: stamp the poll time and return
  • server/lib/port_poller.js:184 missing vendor recipe takes the identical shape
  • server/lib/port_history_db.js:242 the stamp updates one column and touches neither last-seen nor the failure count

Remediation

Add a last_attempt_status column to the monitored device row, written on every path: read, no credentials, no recipe, read nothing, failed. The column list already applies itself through a lazy migration, so there is no migration step. One hour of work that turns four unexplained rows into four actionable ones.

SRV-13

Cross-tenant access to a scan

RefutedNo work

The concern was that a signed-in user who knows a rack id could read another organization's scan. They cannot. A single guard is registered once against the rack id parameter and therefore runs before every route that takes one, including the scan, the merged result and the rack images.

What exists

The owner sees every rack, an org admin sees racks held by their sites, and everyone else is answered with 404 rather than 403, so the guard does not confirm that the rack exists.

Residual action

  • Add a regression test asserting a 404 for a member on another site's rack, so a future refactor cannot quietly remove the guard

References

  • server/app.js:302 the guard is registered globally against the rack id parameter
  • server/app.js:7066, 7084 both routes in the claim carry that parameter, so the guard fires before either handler
  • server/lib/rack_access.js:48 the policy: owner unrestricted, org admin by site set, otherwise the racks that user claimed

Method

Each claim was given to an independent reviewer with three instructions: quote a file and a line for every statement, probe the live server read-only to confirm the behaviour, and return one of three verdicts rather than agreeing with the claim. A statement without a line reference was not accepted.

Probes used the tester organization on demo.racktrack.ai and were read-only apart from the sign-in required to obtain a session. Effort is read from the amount of schema and code each change touches, not from a planning session. The process refuted one claim outright and corrected the detail of three more, in each case because machinery reported as missing already exists elsewhere in the codebase.
