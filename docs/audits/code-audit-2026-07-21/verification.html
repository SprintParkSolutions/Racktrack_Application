Scope of this attestation

This report does not claim the software is defect-free — no audit can, and any document that does invites a single counter-example to discredit it. It states something narrower and stronger: these specific properties were tested, and these are the results. Known open items are listed in full at the end rather than omitted, because a report that hides them is worth less than one that does not.

Debug leftovers in production paths
  • Database access is fully parameterised. Every statement across authentication, audit, marketplace, port history and logging uses bound parameters. The only string interpolation uses fixed, code-controlled column lists.
  • No shell command is built from user input. Every external process is invoked with an argument array, never a shell string.
  • All 137 application requests resolve against the 214 registered endpoints — no dead links, no wrong methods, no typos. A user will not hit a "not found" from a mis-wired screen.
  • Session handling is sound — tokens are signed with a strong secret generated and stored with restricted permissions; there is no fallback or default secret.
  • Interface code obeys the framework's correctness rules across every screen, including the largest (4,900 lines) — verified because an earlier crash of this class had been fixed and could have regressed.
  • Outbound integrations cannot be redirected — the ServiceNow and network-discovery integrations build their addresses from configuration, not from user input.

Findings that were investigated and rejected

Three reported issues did not survive verification and were not acted on: a suspected email-header injection (the address validation already rejects the characters required), a suspected exposure of demo data routes (confirmed disabled in production by live request), and a suspected weak session secret (no weak fallback exists). Each was checked in the source rather than assumed.

The most significant single finding: every scan was failing and returning a message blaming the user's photograph. It was introduced hours before the review and would have reached testers as "the camera doesn't work".

Six of the fixes broke something else — all were caught

This is disclosed deliberately. Changes that tighten access will break clients that were relying on the looser behaviour, and one of these reached a tester before it was found (port search stopped working on installed app builds). Each was identified by re-reviewing the fixes adversarially and checking every consumer of what changed. The full account is in the accompanying Issues & Fixes record.

Assessment

The security building blocks were already present — role checks, customer ownership checks, share tokens, rate limiting. The failures were consistency failures: a check applied to four routes and not the fifth, a function that returned "allow" where it meant "deny", a file mount added ahead of the login layer. That is a materially better position than missing controls, and it is why most corrections were a few lines each.

Two systemic observations, stated plainly. Automated testing is effectively absent, which is why a one-line change disabled all scanning without detection — this is the highest-value investment available. And customer separation is enforced route by route rather than structurally, which is why isolation gaps surface one endpoint at a time; enforcing it at the data-access layer would close the category rather than the instances.
