1 · What each tool actually looks at

The clearest way to judge an audit toolchain is by surface coverage — which parts of the system get inspected, and by what. The proposal covered the Python layer, dependencies and secrets. The rows in blue are the parts it did not reach, which have since been covered.

2 · Tool by tool — what each one found

The five proposed tools that are now live, with what each checks, where it runs, and the result it reports today.

Ruff✓ LIVEPython code qualityAll checks passed
What it checks
Formatting and style against PEP 8, docstrings against PEP 257, import order, plus common bug patterns.
What it changed
Reformatted 35 files to a single consistent style and fixed 173 issues automatically. The 101 pipeline tests pass unchanged either side of it.
How it runs
A blocking gate on every code change, and again before each commit.
Bandit✓ LIVEPython security0 issues
What it checks
Insecure Python patterns — unsafe subprocess calls, weak cryptography, unvalidated input handling.
What it found
Three categories, each individually reviewed and judged safe: SHA-1 used only to name cache files, model loading that only ever reads our own files, and two outbound calls without an explicit timeout.
Why that matters
The exemptions are documented with reasons rather than silently switched off — anything new is still caught.
Semgrep✓ LIVEApplication security (SAST)0 real findings
What it checks
Our own code for the classic attack routes — database injection, file-path manipulation, unsafe commands — using the OWASP rule sets.
What it found
It raised alarms, and every one was examined by hand. All proved false: log messages mistaken for database queries, and file paths already protected by strict ID checks and ownership verification.
How it runs
On every change, across the API, the app and the pipeline.
pip-audit✓ LIVEDependency securityNo known vulnerabilities
What it checks
Every Python package we rely on, against the public database of known vulnerabilities.
Result
Clean on the first run and every run since — including the machine-learning stack.
How it runs
A blocking gate on every change; Dependabot separately opens a fix the day a patch is published.
Gitleaks✓ LIVESecret scanning0 leaks
What it checks
Keys, tokens and passwords — not only in today's code but across every commit ever made.
Why history matters
A key removed from a file still lives in the project's past. Scanning history is the only way to know.
How it runs
On every change, and again before a commit is recorded — so a secret is stopped at the desk.
SonarQube○ NOT SET UPProject-level dashboardneeds a hosting decision
What it would add
Not a new check — a dashboard. It tracks quality trends over time (bugs, duplication, coverage) in one visual place for review.
Why it is not done
It requires either a hosted account or a server of our own. That is a decision, not engineering work.
Honest assessment
A visibility improvement, not a missing safeguard — the underlying checks it would display are already running and passing.

Rather than assert that these pass, here is the actual output, produced by running each tool against the codebase.

$ pip-audit -r requirements.txt      # dependency vulnerabilities
No known vulnerabilities found

$ pytest pipeline/tests -q           # the pipeline test suite

The wider suite — the surface beyond Python

$ npm run lint          # app & server code checkers
0 errors

$ npm test              # app + server test suites
53 passed  ·  86 passed

$ node e2e/sweep.mjs    # robot walks every screen, phone-sized

$ npm run build         # the package that ships to users

Where these run: all of the above are wired into the automated build and execute on every code change — not as a one-off exercise. A failure blocks the change from landing. The formatting, lint and secret checks additionally run before a commit is recorded.

4 · What was added beyond the proposal

The proposal concentrated on the Python layer. RackTrack is roughly half JavaScript and ships as a container, so these were added to close the remaining surface.

CodeQL+ ADDEDa second security engine
Why a second one
Semgrep matches known-bad patterns; CodeQL traces how untrusted data moves through the code. They miss different things, so running both is genuinely additive rather than duplicated effort.
Coverage
Both languages, on every change and weekly — so newly published attack patterns are re-run against unchanged code.
ESLint · Prettier+ ADDEDthe JavaScript equivalent of Ruff0 errors
Why it was needed
The proposal's Python focus left roughly half the codebase — the app screens and the API server — without a quality gate.
How it is enforced
Zero errors required, and the warning count is capped at today's number, so the code can only get cleaner.
Accessibility linting+ ADDEDbarriers for screen-reader users4 found · 4 fixed
What it found
Four genuine issues. Three form labels were not connected to the fields they described — a screen reader would announce the field with no name. One image carried a redundant description.
What was done
All four fixed. Two labels linked to their controls, one custom dropdown given a proper accessible name, and the image description corrected.
Why it matters
Accessibility is increasingly a procurement requirement, not only good practice. Catching these as code is written is far cheaper than a retrofit.
Trivy+ ADDEDthe shipping container
What it checks
The container ships with its own operating system, which carries its own vulnerabilities — entirely separate from our code.
Also produces
A parts list (SBOM) — an itemised inventory of everything shipped, increasingly requested in enterprise procurement — and a licence report.
npm audit · Dependabot+ ADDEDJavaScript dependencies, kept current
What it checks
The JavaScript counterpart to pip-audit. Every dependency with an available fix has been patched.
Dependabot's role
Opens a ready-made fix the day a patch is published, rather than waiting for someone to remember to scan.
Playwright browser sweep+ ADDEDthe running application13 / 13 clean
What it does
A robot signs in and walks all 13 screens at phone size on every change.
Why no scanner replaces it
It catches blank screens, icons rendering as raw text, layout breaking on a narrow display — none of which any code scanner can see.

5 · Test coverage — now measured, and reported honestly

"The tests pass" is only half the picture. Coverage measurement was added so we can state how much of the code those tests actually reach. These are the real figures.

Server — the APIwhere the security-critical logic lives
48%
Solid. Logins, the walls between customer companies, and crash recovery are all covered.
AI pipelinethe scanning engine
12%
The pure-logic parts are tested — port numbering, panel reconciliation, model matching. The image analysis itself cannot be unit-tested without model files and a graphics card; it is validated by real scans instead.
App screenswhat technicians see
2% — and low by design. The screens are verified by the robot browser sweep on every change, which for a user interface is a more meaningful check than unit tests.
Stated plainly, because it will be asked: two of these three figures are low. That is not a hidden failure — it reflects where the testing lives. The layer holding the security-critical logic is the well-covered one, and the other two are checked by methods better suited to them. Now that the numbers are measured rather than unknown, a floor can be set so they only rise.

6 · Licence compliance

Enterprise buyers ask which open-source licences a product ships. This was previously unchecked; it now runs automatically on every build.

Permissive — no obligations for commercial use Worth documenting for legal review

The one item to note: a single LGPL-licensed package — the native image-processing library used for photo handling. Acceptable for our use, as we call the library rather than modify or bind it into our own code, but worth recording for a legal review.

A genuine gap was found and closed: RackTrack's own packages carried no licence declaration at all. To any auditing tool — including a prospective buyer's — that reads as "unknown licence". All three are now explicitly marked private and UNLICENSED (proprietary).

7 · Summary for review

The proposed toolchain was sound. Independently, the work already underway had arrived at the same set of tools — a useful signal that two separate assessments reached the same conclusion about what RackTrack needs.

Five of the six proposed tools are now live, enforced automatically on every code change rather than run as a one-off, and all are passing. Eight further checks were added to cover the JavaScript layer, the shipping container, accessibility and the running application — surface the proposal did not reach.

The single open item is SonarQube, which is a visibility improvement rather than a missing safeguard, and awaits a decision on hosting rather than engineering effort.

Correctly excluded, and worth restating: code auditing does not validate scanning accuracy, device detection, rack-unit correctness or CMDB reconciliation. Those require functional and machine-learning evaluation — tracked separately as the AI accuracy report, scheduled once a live environment exists.
